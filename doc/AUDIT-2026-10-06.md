## 2. Критические дефекты продакшн-кода (исправлены)

### 2.1. REST-слой был написан против несуществующего сервисного API

Коммит `08be95d "feat: implement REST API for UI (PHASE-21-25)"` добавил контроллеры и тесты,
но сервисный слой под них не создан. **26 из 31 эндпоинта были заглушками**
(`throw new UnsupportedOperationException`). Реализованы `ProcessService.createProcess/getById/
listProcesses/recall`, создан `ProcessViewService` и `ProcessDecisionController`.

### 2.2. `BaseEntity` объявляет `@Id` без генерации

`domain/common/BaseEntity.java` — `@Id` без `@GeneratedValue`, id генерирует приложение.
Ряд бинов id не проставлял → `Identifier of entity ... must be manually assigned`:

* `RecordDecisionAction` — ломало **все** сценарии принятия решения;
* `RecordCommentAction` — ломало комментарии и агрегацию этапа;
* `RouteGenerationService` — ломало создание процесса (`ProcessInstance`, `StageInstance`,
  `StageIteration`, `Participant`).

### 2.3. Схема `status_registry` не допускала один код статуса для разных агрегатов

`V1` объявлял `code` глобальным PK, хотя коды повторяются (`InProgress` у PROCESS и REMARK,
`Draft` у PROCESS и REMARK, `Active` у STAGE и REMARK). Миграции сеяли статусы с
`on conflict (code) do nothing`, поэтому строки для «второго» агрегата **молча не вставлялись**:
переходы замечаний падали с `InvalidTargetStatusException`, процесс не мог завершиться.
**Исправлено:** составной PK `(code, entity_type)` + `@IdClass(StatusRegistryId.class)`.

### 2.4. Уникальность переходов была по `(config_id, code)`

`V11` создавал `ux_transition_config_code on transition_config(config_id, code)`, из-за чего
второй INSERT перехода с тем же кодом и другим `from_state` **молча отбрасывался**:

* `RecallProcess` из `OnRework` — отзыв процесса из доработки не работал;
* `ReactivateStage` из `Approved`/`ApprovedWithComments` — возврат на пройденный этап не работал.

**Исправлено:** уникальность по `(config_id, code, from_state)` — `TransitionEngine` ищет
кандидатов по `(fromState, trigger)`, поэтому несколько строк с одним кодом и разными
`from_state` — штатная ситуация.

### 2.5. `V20`/`V21`: агрегация решений не была подключена

`V21` добавляла `EvaluateAggregation` в actions перехода `Decide`, но применяется **раньше**
`V20`, которая этот переход создаёт: `UPDATE` затрагивал 0 строк. Агрегация не запускалась,
этап не закрывался, процесс не завершался. **Исправлено:** реестр действий и переход описаны
в `V20`.

### 2.6. Неоднозначный выбор перехода при равном приоритете

`ModelFactory` сортирует кандидатов по `priority`, затем по `code`. Там, где из одного
состояния доступны два перехода с разными намерениями, побеждал лексикографически меньший код:

| Пара | Что происходило | Исправление |
|---|---|---|
| `ProcessRemark`/`RejectRemark` из `InProgress` | `rejectRemark` давал статус `Processed` | guards `IsRemarkRejection`/`IsRemarkResolution` — исход выбирается по параметру вызова (`reason`/`resolution`) |
| `ResumeProcess`/`RecallProcess` из `OnRework` | возобновление превращалось в отзыв | приоритет `ResumeProcess` + guard `IsRecallRequest` |
| `ProcessApprovedWithComments`/`ProcessApproved` | процесс терял признак «с замечаниями» | приоритет 10 у «с замечаниями» |
| `StageApprovedWithComments`/`StageApproved` | этап терял признак «с замечаниями» | приоритет 10 у «с замечаниями» |
| `MarkNotRequired` из `Active` | перехватывал обработку замечания | перенесён в состояние `Proposed` |

### 2.7. Actions читали состояние связанных сущностей до его записи

`TransitionEngine` выполняет actions перехода и только затем пишет новый статус. Из-за этого:

* `PreviousStageCompletedGuard` видел предыдущий этап ещё `Active` → следующий этап не активировался;
* `AllStagesCompletedGuard`, `HasCommentsGuard` видели закрываемый этап ещё `Active`;
* `HasStageOnReworkGuard` не видел этап в `OnRework` → `ProcessRework` не срабатывал;
* `EvaluateAggregationAction` брал устаревшую копию этапа (статус `Pending`) → агрегация уходила
  «из Pending» и молча не срабатывала.

**Исправлено:** статус фиксируется **до** выполнения actions; guards читают статусы связанных
сущностей из репозиториев (а не из ленивых коллекций), источник истины для агрегации —
записи `decision`. `EvaluateProcessCompletionAction` запускает оценку завершённости
**только для последнего этапа** маршрута.

### 2.8. Прочие дефекты

* `RemarkService.createRemark` / `RecordCommentAction` не заполняли обязательный `author_role`
  (`NOT NULL`) → `DataIntegrityViolationException`.
* `RouteGenerationService` создавал процесс в состоянии `Pending` вместо `Draft` → процесс
  нельзя было запустить.
* `RouteGenerationService` не проставлял `StageIteration.startedAt` (`NOT NULL`).
* Атрибуты запроса игнорировались при подборе шаблона (`EntityAdapterStub` подменял их).
* Шаблон → этап: не переносились `mandatory`, `orderMandatory`, `allowedReturnStages`, `name`.
* `RouteValidatorService` не сверялся с обязательными слотами шаблона.
* `IsTargetStageAllowedGuard` требовал `orderIdx >= 1` при нумерации этапов с 0.
* `ReactivateStage` вызывал `AssignStageTasks` (process-level action) из контекста этапа →
  `ClassCastException`; процессные guards падали так же вместо возврата `false`.
* Маппинг в DTO выполнялся вне сессии (`open-in-view=false`) → 500 с `LazyInitializationException`.
  Решение: `ProcessViewService` — read-only транзакция **только вокруг чтения** (пометка
  read-only самого write-эндпоинта подавляет flush и ломает запись статусов).

## 7. Валидация карты переходов (реализовано)

`engine/validation` — валидатор карты переходов и его вызовы:

| Компонент | Назначение |
|---|---|
| `TransitionMapValidator` | проверки; возвращает полный список нарушений |
| `TransitionMapErrorCode` | 10 кодов нарушений (4 из §7.2 спеки + 6 структурных) |
| `TransitionMapViolation` | нарушение: код, место, описание последствий |
| `InvalidTransitionMapException` | исключение со всеми нарушениями сразу |
| `KnownEventTypes` | перечень событий из `06_event_contract.md` §18 |
| `TransitionMapStartupValidator` | проверка всех `PUBLISHED` карт при старте приложения |

Точка вызова: `POST /api/v1/admin/state-machines/{configId}/validate` и старт приложения.
Отдельной операции «публикация карты» в текущем объёме нет — карты приходят из сид-миграций,
поэтому валидация на старте закрывает именно этот путь. Когда появится публикация через API,
тот же валидатор должен вызываться в её транзакции перед сменой статуса на `PUBLISHED`.

### 7.1. Что валидатор нашёл сразу после включения

**Реальный дефект:** в `V20` состояние `Assigned` карты `PARTICIPANT` не было помечено
`is_initial` — ни одного начального состояния, движку неоткуда начать. Исправлено.

**Семь событий вне контракта** — `emits` в сидах не совпадали с `06_event_contract.md` §18:

| Было в сидах | Стало (контракт) |
|---|---|
| `approval.process.on_rework` | `approval.process.rework-required` |
| `approval.remark.in_progress` | `approval.remark.activated` |
| `approval.remark.processed` | `approval.remark.resolved` |
| `approval.remark.not_required` | `approval.remark.marked-not-required` |
| `template.published` | `approval.config.published` |
| `template.deprecated` | `approval.config.deprecated` |
| `template.archived` | события в контракте нет → `emits` оставлен пустым |

Последняя строка — осознанное решение: изобретать несуществующий тип события нельзя, его
сначала нужно добавить в контракт.

### 7.2. Уточнение семантики `AMBIGUOUS_TRANSITION`

Первая версия проверки помечала как дефект **любые** два активных перехода из одной пары
`(from_state, trigger)` с разными `to_state`. На сидах это дало 6 ложных срабатываний
(`ProcessApproved`/`ProcessApprovedWithComments`, `ResumeProcess`/`RecallProcess`,
`StageApproved`/`StageOnRework`, `ProcessRemark`/`RejectRemark`): во всех этих парах исходы
различаются **guards**, а `priority` задаёт порядок проверки — это законная конфигурация.

Проверка уточнена: неоднозначность — это разные `to_state` при **одинаковом** наборе guards.
Именно такой случай (а не различающиеся guards) приводил к тому, что исход зависел от
лексикографического порядка кодов.

### 7.3. Ложное срабатывание из-за общего состояния тестов

`TransitionMapValidatorIntegrationTest` падал в полной сборке и проходил изолированно.
Причина: `TransitionEngineIntegrationTest` сохраняет в общую БД Testcontainers синтетическую
карту со статусом `PUBLISHED` и тестовым событием `IT_EVT_APPROVED`, а стартовая валидация
законно её отвергала.

Исправлено: (1) валидируются только карты в статусе `PUBLISHED`, (2) тестовый конфиг движка
переведён в `DRAFT` — он и не должен считаться опубликованным. Побочно это вскрыло общую
слабость набора: интеграционные тесты делят одну БД и не изолированы друг от друга.

### 7.4. Тесты

* `TransitionMapValidatorTest` — 18 тестов: по одному на каждый код нарушения, плюс
  отсутствие ложных срабатываний (разные guards, одинаковые `to_state`, неактивные переходы,
  пустой `applicable_entities`) и проверка, что возвращаются **все** нарушения сразу.
* `TransitionMapValidatorIntegrationTest` — 7 тестов на реальных картах из Flyway: все
  опубликованные карты валидны, все `emits` в контракте, `validateOrThrow` не падает,
  стартовая валидация проходит, неоднозначность обнаруживается на реальной карте, а
  исключение собирает все нарушения.

## 8. Рантайм-проверка в локальном Docker

**Дата:** 2026-10-10. Развёртывание: `docker compose up -d` (Postgres 16 + RabbitMQ 3.13 +
собранный образ приложения).

Состояние при первом запуске: Flyway применил **25 миграций**, стартовая валидация карт
переходов прошла («5 карт(ы)»), приложение поднялось на 8080. То есть миграции и валидация
корректны на чистой БД.

Однако проверка HTTP-эндпоинтов выявила **три дефекта, которые не ловились тестами** —
все они жили именно в тех GET-эндпоинтах, у которых не было ни одного теста.

### 8.1. `StateMachineConfig.states` — `LazyInitializationException` (500)

`GET /api/v1/admin/state-machines` и `/{configId}` отвечали 500: методы контроллера не были
транзакционными, а `toDto` обходит ленивые коллекции `states`/`transitions` при
`spring.jpa.open-in-view=false`. Ровно тот же класс дефекта, что был исправлен в
`ProcessController`, но здесь остался незамеченным.

**Исправлено:** `@Transactional(readOnly = true)` на методах чтения.

### 8.2. `process_type = null` у карты шаблона — `NullPointerException` (500)

После исправления 8.1 вскрылся следующий слой: `config.getProcessType().name()` падал с NPE,
потому что карта шаблона (`entity_type = TEMPLATE`) не привязана к типу процесса — в `V25`
`process_type` равен `null`. Это **корректные данные**, к которым маппер не был готов.
Проверка `config.getProcessType() == null ? null : …` добавлена также в `ProcessMapper` и
`TemplateMapper` (там она дешёвая страховка).

### 8.3. `GET /api/v1/processes` без фильтров — 400 «Other specification must not be null»

`ProcessService.equalsIfPresent` возвращал `null` для отсутствующего фильтра, а
`Specification.allOf` null-элементы не принимает. В результате список процессов без параметров
отвечал 400, хотя все фильтры необязательны. Мок-тест `listProcesses_withFilters_success`
всегда передавал хотя бы один фильтр, поэтому дефект не проявлялся.

**Исправлено:** нейтральный элемент — `Specification.unrestricted()` вместо `null`.

### 8.4. Почему эти дефекты дожили до рантайма

Корень один: **шесть GET-эндпоинтов не имели ни одного теста**. Точечные тесты на
`ProcessController`/`DecisionController` были, а административные эндпоинты (карты переходов,
шаблоны, реестры) — нет. Добавлены интеграционные тесты, вызывающие методы контроллера
напрямую (без MockMvc и без `@Transactional` на тесте) — ровно в тех условиях, что HTTP-вызов:
`StateMachineConfigControllerIntegrationTest` (5), `TemplateControllerIntegrationTest` (6),
`GuardActionRegistryControllerIntegrationTest` (2), `ProcessListIntegrationTest` (6).

## 9. Реализация TemplateController (2026-10-10)

Реализованы все эндпоинты шаблонов (`07_api_contract.md` §10) плюс форк:

| Метод | Эндпоинт | Поведение |
|---|---|---|
| POST | `/api/v1/admin/templates` | создаёт `DRAFT`, `version = 1`, отдаёт `201` + `Location` |
| PUT | `/api/v1/admin/templates/{id}` | `DRAFT` правится на месте; `PUBLISHED` создаёт новую версию (ADR-023) и снимает прежнюю с публикации |
| POST | `/{id}/publish` | `DRAFT → PUBLISHED`, валидация структуры движком |
| POST | `/{id}/deprecate` | `PUBLISHED → DEPRECATED` |
| POST | `/{id}/archive` | `DEPRECATED → ARCHIVED`, guard `NoActiveProcesses` |
| POST | `/{id}/fork` | новая строка `version + 1` + `parentTemplateId`, исходная не меняется |
| GET | `/api/v1/admin/templates` | фильтры `status`, `processType`, `name` |

Добавлены `TemplateRequestMapper` (API-DTO со строковыми перечислениями → сервисные DTO с
типизированными enum-ами), `ForkTemplateRequest` и метод `TemplateService.fork`.

### 9.1. Дефекты, найденные при реализации

**Подбор шаблона выбирал самый старый подходящий шаблон.** `MatchService.findMatchingTemplates`
сортировал кандидатов только по `ruleIdx`, а в кандидаты попадали **все опубликованные версии**
цепочки. При равном приоритете порядок был недетерминирован: на практике выбиралась самая старая
строка, поэтому вновь созданные шаблоны не использовались вовсе. Обнаружено при повторном
прогоне сквозного сценария: три разных шаблона — три процесса, но все на одном старом шаблоне
(участники получали один и тот же `userId` из его слота). Исправлено: кандидаты дедуплицируются
по корню цепочки версий с сохранением только лучшей версии (ADR-023), добавлен детерминированный
tie-break — `ruleIdx`, затем версия по убыванию, затем дата создания по убыванию.

**`TemplateService.publish()` молча выполнял депрекацию.** Предусловия по статусу не
проверялись, а движок выбирает переход по **текущему** состоянию: из `PUBLISHED` по
`USER_ACTION` доступна только депрекация, поэтому вызов «опубликовать» на уже опубликованном
шаблоне снимал его с публикации вместо отказа. Исправлено явными предусловиями в
`publish`/`deprecate`/`archive` — та же защита, что в `ProcessService.startProcess`/`resume`.

**`TemplateService.updateInPlace` падал на уникальном ключе.** Очистка `stages` и повторное
заполнение внутри одной транзакции: Hibernate выполняет `INSERT` раньше `DELETE`, поэтому новые
этапы вставлялись до удаления старых и падали на `ux_stage_template_order
(template_id, order_idx)`. Исправлено `entityManager.flush()` после очистки.

**Проверки `duration`/`allowedReturnStages` срабатывали слишком поздно.** `duration <= 0`
ловил констрейнт БД `stage_template_duration_check` (клиент получал 500 вместо 400), а
`allowedReturnStages > orderIdx` констрейнтом не покрыт вовсе. Проверки перенесены в
`applyStages` — до записи.

**Ошибки клиента отдавались как 500.** Действия карты переходов бросают
`IllegalArgumentException` как сигнал о неверном запросе, но внутри транзакции Spring переводит
его в `InvalidDataAccessApiUsageException`, и обработчик `IllegalArgumentException` его не
ловил. Добавлен `@ExceptionHandler(DataAccessException)` с разворачиванием причины
(`ExceptionCauses`), а разбор значений фильтров вынесен из лямбд `Specification` — внутри лямбды
исключение всплывало уже во время выполнения запроса.

### 9.2. Сквозной сценарий проверен в рантайме

```
POST /api/v1/admin/templates              -> 201 DRAFT, version=1
POST /api/v1/admin/templates/{id}/publish -> 200 PUBLISHED, publishedAt заполнен
POST /api/v1/processes                    -> 201 Draft (шаблон подобран по правилу применимости:
                                             entityType=CONTRACT, subtype=SUPPLY, amount >= 1000)
POST /api/v1/processes/{id}/start         -> 200 InProgress, этап Active, участник Assigned
POST /…/participants/{id}/decide APPROVE  -> 200
GET  /api/v1/processes/{id}               -> Approved, этап Approved, completedAt заполнен
```

Проверены и коды ошибок: невалидные перечисления → 400, отсутствие `createdBy` → 400
(`VALIDATION_ERROR`), неизвестный шаблон → 404, повторная публикация → 409, публикация без
этапов → 409, `duration = 0` и `allowedReturnStages > orderIdx` → 400 с указанием этапа.

# Соглашение о комментариях в коде

Документ описывает, **как** в этом репозитории документируется исходный код и **на что**
ссылаться в комментариях. Он же — рабочее задание для ветки `docs/javadoc-coverage`
(см. §8 «Как проверяется результат»).

## 1. Зачем это

Поведение сервиса задаётся **данными** в БД (`state_machine_config`, `transition_config`,
`guard_registry`, `action_registry`), а не кодом (ADR-002, ADR-028). Из-за этого по классу
`AggregationApprovedGuard` невозможно понять, в каком переходе он участвует, кто его
вызывает и почему он читает данные именно так. Комментарий в коде — единственное место,
где эта связь фиксируется рядом с реализацией.

Второй источник проблем — решения, принятые **вопреки** первому прочтению спецификации
(порядок записи статуса в `TransitionEngine`, исключение текущего участника из счётчиков в
`AllParticipantsDecidedGuard`, `Specification.unrestricted()` вместо `null` в
`ProcessService.listProcesses`). Такие решения без комментария выглядят как ошибка и
«исправляются» обратно при следующем рефакторинге.

## 2. Язык, стиль, формат

| Правило | Значение |
|---|---|
| Язык прозы | русский; идентификаторы, коды переходов, статусы, имена таблиц — как в коде (`{@code InProgress}`, `{@code guard_registry}`) |
| Формат | Javadoc (`/** ... */`) для типов, полей, методов, компонентов record |
| Длина | 1–3 предложения на класс; `<p>` для второго абзаца; `<ul>/<li>` для перечислений |
| Ссылки | `{@link TypeName}`, `{@link #method}` — только на существующие типы, иначе `{@code ...}` |
| Разметка | `<p>` (не пустая строка), `<b>жирный</b>` для акцента, `<i>курсив</i>` |
| Запрещено | `@author`, `@since`, даты в заголовке, `TODO` без номера фазы/тикета, дублирование кода словами |

Комментарии внутри метода (`//`) — только там, где решение неочевидно (§5). Не комментируйте
то, что видно из кода: `// возвращаем результат` — шум.

## 3. Что обязательно документировать

| Тип | Класс | Публичные методы | Поля/компоненты record |
|---|---|---|---|
| Движок, сервисы (`engine`, `service`) | обязательно | обязательно | только неочевидные константы |
| Guards и actions (`service.guard`, `service.action`) | обязательно | `evaluate`/`execute` — если логика не тривиальна | — |
| Контроллеры (`api.controller`) | обязательно | обязательно | — |
| Мапперы, view-сервисы (`api.mapper`, `api.service`) | обязательно | обязательно | — |
| Доменные сущности (`domain.*`) | обязательно | только методы с логикой | обязательно для полей, смысл которых не ясен из имени |
| DTO (`api.dto.*`, `service.dto`, `dto.*`) | обязательно (1–3 строки) | — | компоненты record — одной строкой, если имя не самоочевидно |
| Repositories (Spring Data) | обязательно | — | — |
| Исключения (`*Exception`) | 1 строка (когда бросается) | — | — |
| Enum и константные классы | обязательно | — | константы — только если значение не очевидно |
| Конфигурация (`config`, `api.config`) | обязательно | — | — |
| Тестовые классы (`src/test`) | по желанию: класс + неочевидные сценарии | — | — |

**Приоритет.** Сначала `engine`, `service`, `service.guard`, `service.action`, `api.controller`,
`api.*` (сервисы/мапперы), затем `domain`, DTO, конфигурация. Полный охват DTO и исключений —
дешёвый способ поднять цифру покрытия, но начинать надо с первых групп.

## 4. Из чего состоит хороший Javadoc

### 4.1 Класс: что это, откуда требование, почему так

```java
/**
 * G-S-002 «Все участники текущей итерации приняли решение» — предусловие агрегации решений
 * этапа ({@code 05_guards_actions_registry.md} §4.2). Резолвится
 * {@code guard_registry.handler = 'allParticipantsDecidedGuard'} (миграция V21).
 *
 * <p><b>Почему источник истины — записи {@code decision}, а не {@code participant.status}.</b>
 * ... (неочевидное решение и его причина)
 */
```

Порядок частей:

1. **Идентификация** — буквенный код из спецификации (`G-S-002`, `A-S-004`) и/или имя
   перехода, в который компонент включён, плюс ссылка на раздел спецификации.
2. **Контракт** — что означает `true`/`false` (для guard) или какое побочное действие
   выполняется (для action).
3. **Почему так** — только если реализация отклоняется от первого прочтения спецификации
   или от очевидного варианта. Это самая ценная часть.

### 4.2 Метод

- Для публичного API-метода: что делает, при каких условиях, что бросает.
- `@param` — когда имя параметра не объясняет роль (например `configId` — «версия конфига,
  зафиксированная вызывающим кодом»).
- `@return` — когда возвращаемое значение имеет нетривиальный смысл (`performed == false`
  означает «ни один переход не прошёл guards»).
- `@throws` — для исключений, которые вызывающий обязан обработать.

### 4.3 Границы: что НЕ надо писать

- Пересказ реализации («проходит по списку и вызывает...»).
- Список полей класса, если у полей есть свои Javadoc.
- История изменений — для этого есть `git log` и `doc/`.

## 5. Комментарии внутри кода

Пишутся там, где есть ответ на вопрос «почему», и удаляются, когда ответ устарел:

| Ситуация | Пример из репозитория |
|---|---|
| Порядок операций важен | `TransitionEngine.execute` — статус пишется **до** actions, иначе guards вложенных переходов видят старое состояние |
| Значение по умолчанию не очевидно | `ProcessService.equalsIfPresent` — `null` запрещён в `Specification.allOf`, нейтральный элемент — `unrestricted()` |
| Ветка защищает от известного дефекта | `ProcessService.startProcess` — проверка статуса вместо опоры на отсутствие перехода |
| Заглушка | `// TODO(PHASE-12): публикация события в outbox` — с фазой/тикетом |

Не оставляйте в комментариях ссылки на строки кода («см. строку 42») и на удалённые
классы.

### 6.2 Тикеты фаз (`doc/tickets/`)

Каждая фаза реализована по самодостаточному тикету; в нём есть «Объём фазы», «Критерии
приёмки» и «Открытые вопросы». В Javadoc классов, появившихся в фазе, полезно указывать
`PHASE-NN` и решение открытого вопроса:

- `PHASE-02` — движок, реестры, `TransitionEngine`;
- `PHASE-03` — `StartProcess`, первые guard/action;
- `PHASE-04` — активация этапа (`AssignStageTasks`, `ActivateStage`);
- `PHASE-05` — решения участников (`DecisionService.decide`);
- `PHASE-06` — агрегация решений и закрытие этапа;
- `PHASE-07` — завершение процесса и активация следующего этапа;
- `PHASE-08` — возврат на доработку и возобновление;
- `PHASE-11` — замечания (`RemarkService`);
- `PHASE-14` — управление шаблонами (`TemplateService`, `ValidateTemplateStructureAction`);
- `PHASE-15` — генерация маршрута (`RouteGenerationService`, `MatchService`);
- `PHASE-21-25-REST-API` — контроллеры, DTO, view-сервисы.

Пример ссылки: `(PHASE-06, критерий приёмки 3; {@code 05_guards_actions_registry.md} §4.2)`.

### 6.3 Что ссылать нельзя

В `README.md` и тикетах отмечено: спецификации `00_vision_scope.md` … `12_test_scenarios.md`
и ADR живут в Claude Project, но их копии **экспортированы в `doc/arch/`** — ссылаться на
имена файлов можно. А вот ссылки на «Claude Project», внешние URL, номера PR и коммитов в
Javadoc не нужны: они не переживут перенос репозитория. Единственное исключение — коммит,
если он объясняет дефект (как в `ProcessService`), и то лучше пересказать суть.

## 7. Примеры: как надо и как не надо

**Плохо** (пересказ кода):

```java
/** Метод evaluate проверяет, все ли участники проголосовали. */
@Override
public boolean evaluate(TransitionContext context) { ... }
```

**Хорошо** (контракт + причина):

```java
/**
 * {@code true}, если все участники текущей итерации, кроме инициатора перехода, уже имеют
 * запись в {@code decision}. Инициатор исключён из счётчиков, потому что
 * {@code TransitionEngine} записывает его новый статус до выполнения actions перехода.
 */
@Override
public boolean evaluate(TransitionContext context) { ... }
```

**Плохо** (шум в DTO):

```java
/** DTO. */
public record ProcessDto(UUID id, String status) {}
```

**Хорошо** (роль DTO и источник данных):

```java
/**
 * Детальное представление процесса для UI: агрегирует {@code ProcessInstance} вместе с
 * этапами, итерациями и участниками (ADR-020; {@code 07_api_contract.md} §6).
 */
public record ProcessDto(UUID id, String status) {}
```

## 8. Как проверяется результат

1. **Компиляция** — комментарии не должны ломать сборку:

   ```bash
   ./gradlew verifyTestCompilation   # main + test, Docker не нужен
   ```

   Javadoc с некорректной ссылкой (`{@link}` на несуществующий тип) компилятор пропускает
   молча, поэтому ссылки проверяются глазами: каждый `{@link}` должен указывать на тип или
   метод, которые есть в проекте.

2. **Покрытие** — скрипт `doc/tools/CommentCoverage.ps1` считает долю задокументированных
   типов, методов и полей:

   ```bash
   powershell -ExecutionPolicy Bypass -File doc/tools/CommentCoverage.ps1 -Details
   ```

   Базовая линия на момент создания ветки (`docs/javadoc-coverage`, от `main` `aec7ef4`):

   | Метрика | Было | Цель |
   |---|---|---|
   | Типы с Javadoc | 118 / 215 (54,9 %) | ≥ 95 % |
   | Методы с Javadoc | 26 / 177 (14,7 %) | ≥ 80 % |
   | Поля класса с Javadoc | 29 / 380 (7,6 %) | ≥ 50 % |

   Локальные переменные и параметры скрипт считает отдельной строкой (`locals/params`) и в
   знаменатель покрытия полей не включает: соглашение их не документирует (§3).

3. **Ревью** — проверяется не объём, а то, что комментарий отвечает на вопрос «почему» и не
   противоречит коду. Комментарий, который повторяет сигнатуру метода, — дефект ревью.

## 9. Порядок работы в ветке

Ветка `docs/javadoc-coverage` отведена от `main`; изменения затрагивают **только
комментарии**. Любая правка логики в этой ветке — вне объёма: если при написании
комментария обнаружен дефект, он фиксируется в тексте комментария как известное ограничение
и выносится в отдельную задачу, а не исправляется здесь.

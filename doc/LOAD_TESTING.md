# Нагрузочное тестирование

**Назначение:** как воспроизводимо нагрузить сервис согласования, что именно измеряется и как
читать результат. Инструмент — Gatling 3.16 (Java DSL) в source set `src/gatling/java`, запуск
через Gradle-задачу `gatlingRun`.

Документ описывает три этапа: **1) бенчмарк и поиск узких мест**, **2) фиксация SLO**,
**3) регрессионный гейт в CI**. Этап 1 реализован, этапы 2–3 — по результатам первого прогона.

---

## 1. Что нагружаем и почему именно это

Эндпоинты сервиса распадаются на четыре группы с разной стоимостью. Покрыты три: самая частая
(чтение для UI), самая дорогая (запись жизненного цикла) и административная работа с шаблонами.

| Профиль | Сценарий | Что проверяет |
|---|---|---|
| **UI-чтение** | `UiReadSimulation` | `GET /approval-view/entities/{entityId}` (целевое требование §25.2 — быстрее 500 мс), `GET /approval-view/tasks/my`, `GET /processes/{id}`, `GET /processes` |
| **Жизненный цикл** | `LifecycleSimulation` | `POST /processes` (подбор шаблона + генерация маршрута), `POST /processes/{id}/start` (активация этапа + выдача задач), `POST /processes/{id}/recall` |
| **Шаблоны (админ)** | `TemplateLifecycleSimulation` | `POST /admin/templates` (шаблон + этапы + слоты), `POST …/{id}/publish` (валидация структуры движком), `GET /admin/templates`, `POST …/{id}/fork` (новая версия, ADR-023) |
| Решения (не входит) | — | `.../participants/{id}/decide`: конкурентные записи и `@Version` на `ProcessInstance` (409 при гонке). Следующий этап |
| Фон (не входит) | — | `GET /admin/state-machines`, `GET /admin/registry/*` — дешёвое чтение, на потолок не влияет |

**Чего в нагрузке быть не должно.** Семь эндпоинтов замечаний и комментариев — заглушки, они
бросают `UnsupportedOperationException` (см. `README.md`). Нагружать их нельзя: прогон мерил бы
500-е, а не работу сервиса.

**Возврат на доработку (`resume`) сознательно не включён.** Состояние `OnRework` достижимо только
через отклонение решения участником, то есть через профиль решений. Вызов `resume` из недостижимого
состояния вернул бы 200 с прежним статусом (guard не пропустил переход, а контроллер это не
проверяет) — такой прогон «зелёный» ровно ни о чём.

## 2. Стенд

Приложение и Postgres — локально, генератор нагрузки — отдельным процессом (Gradle форкает для
Gatling собственную JVM). Так генератор не отбирает heap и CPU-потоки у сервиса, иначе замеры
показывают производительность машины, а не сервиса.

```bash
docker compose up -d                       # Postgres :5433 + RabbitMQ
# Postgres в compose публикуется на 5433: порт 5432 занят нативным PostgreSQL, см. README

# терминал 1 — сервис (генератор и приложение должны быть в разных процессах)
$env:DB_URL='jdbc:postgresql://localhost:5433/coordination'; ./gradlew bootRun
# профиль perf дополнительно включает статистику Hibernate (см. §5):
$env:DB_URL='jdbc:postgresql://localhost:5433/coordination'; ./gradlew bootRun --args='--spring.profiles.active=perf'

# терминал 2 — прогоны
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.SeedSimulation
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.UiReadSimulation
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.LifecycleSimulation
```

Проверка, что сервис жив перед прогоном:

```powershell
(Invoke-WebRequest http://localhost:8080/actuator/health -UseBasicParsing).Content
```

> **Особенности окружения.** В этом окружении нативный TLS не работает (`curl`/`Invoke-WebRequest`
> падают с `SEC_E_NO_CREDENTIALS`), а Java-TLS работает: Gradle скачивает зависимости нормально.
> Gradle-кэш при этом надо держать внутри проекта — `GRADLE_USER_HOME=.gradle-home` (каталог уже в
> `.gitignore`), иначе обёртка не может писать в пользовательский `~/.gradle`. Docker из
> изолированной сессии требует разового одобрения доступа.
>
> Если Gradle пишет в stderr `Couldn't open current thread, error = 5` и завершается ненулевым кодом
> при успешной сборке — это его файловый вотчер, которому запрещён доступ к процессу-владельцу.
> Лечится флагом `--no-watch-fs` (в CI его стоит указывать всегда): на результат сборки это не
> влияет, но код возврата становится достоверным.

## 3. Порядок прогона

### 3.1 Сидирование (обязательный первый шаг)

```bash
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.SeedSimulation
# сколько процессов создать (по умолчанию 200) и сколько этапов в шаблоне (по умолчанию 3):
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.SeedSimulation \
  -Ploadtest.seed.processes=1000 -Ploadtest.seed.stages=10
```

Сидер создаёт и публикует шаблон STANDARD с `seed.stages` этапами (слоты этапов заполняются
согласующими по кругу), затем создаёт и запускает N процессов. Идентификаторы процессов и
сущностей складываются в `build/loadtest/seed.csv` — этот файл читают сценарии чтения.

Почему через API, а не SQL: прямая вставка создала бы процессы без сгенерированного маршрута,
этапов и задач участников — то есть не то состояние, которое читает UI. Сценарии чтения мерили бы
пустые агрегаты.

### 3.2 Профиль «UI-чтение»

```bash
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.UiReadSimulation
# интенсивность и длительность (разгон):
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.UiReadSimulation \
  -Ploadtest.read.usersPerSec=50 -Ploadtest.read.durationSeconds=300
```

Нагрузка растёт линейно от 1 до `usersPerSec` за `durationSeconds` — это разгон для поиска потолка,
а не полка. Каждый виртуальный пользователь выполняет 4 запроса с паузами 300/200/200 мс: примерно
`4 × usersPerSec` запросов в секунду на выходе.

Для сравнения конфигураций между собой (например, размера пула соединений) нужна полка — тогда
разница видна как разница в задержке при одной и той же интенсивности:

```powershell
# PowerShell: свойства обязательно в кавычках, см. примечание ниже
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.UiReadSimulation `
  "-Ploadtest.read.mode=constant" "-Ploadtest.read.usersPerSec=25" `
  "-Ploadtest.read.durationSeconds=60" "-Ploadtest.read.warmupSeconds=10"
```

### 3.3 Профиль «жизненный цикл»

```bash
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.LifecycleSimulation
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.LifecycleSimulation \
  -Ploadtest.write.usersPerSec=5 -Ploadtest.write.durationSeconds=300
```

По умолчанию интенсивность на порядок ниже чтения: одна итерация — это генерация маршрута, вставка
этапов, активация первого этапа и создание задач участникам в одной транзакции.

### 3.4 Профиль «шаблоны» (административный)

```bash
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.TemplateLifecycleSimulation
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.TemplateLifecycleSimulation \
  -Ploadtest.template.usersPerSec=2 -Ploadtest.template.durationSeconds=60
```

Итерация: создать черновик шаблона → опубликовать (структура проверяется движком) → прочитать
список опубликованных → форк (новая версия). Интенсивность по умолчанию 1 польз./с на 30 с: шаблоны
создаёт администратор, а не поток пользователей, и профиль отвечает на вопрос «не деградировали ли
админские транзакции и не мешают ли они чтениям», а не ищет на них потолок. SLO на этот профиль не
зафиксирован — только грубые guardrail'ы.

Профиль создаёт по строке шаблона на итерацию (имена `loadtest-tpl-*`), поэтому после него стоит
выполнять очистку (§9): накопленные опубликованные шаблоны участвуют в подборе для новых процессов.

### 3.5 Свойства прогона

| Свойство Gradle | По умолчанию | Смысл |
|---|---|---|
| `-Ploadtest.baseUrl` | `http://localhost:8080` | Адрес сервиса под нагрузкой |
| `-Ploadtest.entityType` | `LOADTEST` | Тип сущности нагрузочных данных (изолирован от боевых) |
| `-Ploadtest.seed.processes` | `200` | Сколько процессов создаёт сидер |
| `-Ploadtest.seed.stages` | `3` | Сколько этапов в шаблоне прогона; `10` — под требование §25.2 |
| `-Ploadtest.read.mode` | `ramp` | `ramp` — разгон (поиск потолка), `constant` — полка (сравнение конфигураций и SLO) |
| `-Ploadtest.read.usersPerSec` | `20` | Интенсивность профиля чтения (пиковая для разгона, постоянная для полки) |
| `-Ploadtest.read.durationSeconds` | `120` | Длительность замеряемой части профиля чтения |
| `-Ploadtest.read.warmupSeconds` | `10` | Прогрев перед полкой (режим `constant`) |

| `-Ploadtest.slo.*` | измеренная база | Пороги SLO-гейта (§8): `shelfUsersPerSec`, `failedPercent`, `aggregateP95Ms`, `aggregateP99Ms`, `globalP95Ms`, `globalP99Ms` |

Пользователи сценариев фиксированы (`LoadTestConfig`): инициатор `…1a01`, согласующие `…ab01`–`…ab03`,
администратор `…ad01`. Иначе после каждого пересоздания данных `/tasks/my` возвращал бы пустую
страницу, и сценарий проверял бы не то, что задумано.

> **Windows PowerShell: свойства обязательно в кавычках.** Без кавычек PowerShell 5.1 разбивает
> `-Ploadtest.baseUrl=http://localhost:8081` на два аргумента, и Gradle падает с
> `Cannot locate tasks that match '.baseUrl=http://localhost:8081'`. Правильно:
> `"-Ploadtest.baseUrl=http://localhost:8081"`.

## 4. Что смотреть в отчёте

Отчёт Gatling: `build/reports/gatling/<simulation>-<timestamp>/index.html`.

Клиентская сторона:

- **p95 и p99 по каждому запросу** (не среднее: на нагрузке среднее скрывает хвост);
- **доля ошибок** — отдельно 500 (дефект) и 409/404 (осмысленный конфликт);
- **throughput** (запросов в секунду) и его просадка к концу прогона: если RPS падает при растущей
  нагрузке, система на пределе;
- **время до первого ответа против полного времени** — рост первого при стабильном втором означает
  переполнение пула соединений или очереди потоков.

Серверная сторона (без неё видно только следствие, а не причину):

```powershell
# пул соединений, HTTP-метрики, JVM — в том числе hikaricp_connections_pending
(Invoke-WebRequest http://localhost:8080/actuator/prometheus -UseBasicParsing).Content -split "`n" |
  Select-String 'hikaricp_connections|http_server_requests|jvm_gc|tomcat_threads'
```

Что смотреть в первую очередь:

| Признак | Где видно | Вероятная причина |
|---|---|---|
| `hikaricp_connections_pending` > 0 | `/actuator/prometheus` | Пул на 10 соединений (`DB_POOL_MAX_SIZE`) — потолок записи |
| Один медленный эндпоинт при быстрых остальных | отчёт Gatling | N+1 в агрегате: проверяется статистикой Hibernate (§5) |
| Рост p99 без роста среднего | отчёт Gatling | Блокировки строк, `@Version` на `ProcessInstance`, GC-паузы |
| Потолок на плоском участке разгона | отчёт + `pg_stat_activity` | Упор в CPU/диск Postgres, а не в сервис |

На самой БД полезны `pg_stat_statements` (топ запросов по суммарному времени), `pg_stat_activity`
(сколько сессий в `active`/`idle in transaction`) и `pg_locks`.

## 5. Диагностика: сколько SQL на один HTTP-вызов

Один и тот же HTTP-вызов может порождать десятки запросов, и именно это, а не CPU, определяет
потолок сервиса. Ниже два способа посчитать — оба проверены на стенде 2026-10-10.

### 5.1 Сводка по сессиям (профиль `perf`)

```powershell
$env:DB_URL='jdbc:postgresql://localhost:5433/coordination'
./gradlew bootRun --args='--server.port=8081 --spring.profiles.active=perf'
```

Профиль включает `hibernate.generate_statistics` и ставит на DEBUG категорию
**`org.hibernate.session.metrics`**: именно она в Hibernate 7.4 печатает сводку по сессии
(сообщение `HHH000401: Logging session metrics`). В логе ищите строку
`N ns executing M JDBC statements` — `M` и есть число SQL в этой сессии.

> **Грабли, на которые я потратил несколько прогонов.** Очевидные варианты не работают:
> `org.hibernate.stat` — это другая категория (в 7.4 она печатает `HHH000117: Query: …`, то есть
> статистику по отдельным запросам, тоже полезную, но не сводку по сессии), а
> `org.hibernate.engine.internal.SessionMetricsLogger` — имя класса из `hibernate-core`, которое
> в качестве категории логирования не используется вовсе. Признак того, что статистика вообще
> включилась: при старте в логе на DEBUG видны строки `HHH000401`; если их нет — свойство не
> доехало (проверяется через `--management.endpoints.web.exposure.include=…,env` и
> `/actuator/env/spring.jpa.properties.hibernate.generate_statistics`).

### 5.2 SQL-лог: точный список запросов

```powershell
./gradlew bootRun --args='--server.port=8081 --logging.level.org.hibernate.SQL=DEBUG --spring.jpa.properties.hibernate.format_sql=false'
```

`format_sql=false` обязателен: с форматированием один запрос печатается несколькими строками, и
счёт по строкам ломается. Считать так:

```powershell
(Select-String -Path build\loadtest\app.log -Pattern 'org\.hibernate\.SQL\s*:' | Measure-Object).Count
```

### 5.3 Сколько SQL на вызов (набор 30 процессов × 10 этапов)

Оба способа дают одинаковые числа (сводка сессии и подсчёт строк SQL-лога сверены). Колонка
«стало» — после исправлений из §5.4 и появления `view=summary` (§5.5):

| Эндпоинт | SQL было | SQL стало |
|---|---|---|
| `GET /approval-view/processes/my?size=20` | 1 | 1 |
| `GET /admin/registry/guards` | 1 | 1 |
| `GET /admin/state-machines` | 11 | 11 |
| `GET /approval-view/tasks/my?size=20` | 47 | **5** |
| `GET /processes/{id}` (карточка процесса с 10 этапами) | 32 | **5** |
| `GET /processes?status=InProgress&size=1` | 33 | 6 |
| `GET /approval-view/entities/{entityId}` (агрегат, 10 этапов) | **56–60** | **8** |
| `GET /processes?status=InProgress&size=20` (полное представление) | **622** | **31** |
| `GET /processes?status=InProgress&size=50` (полное) | 939 | **48** |
| `GET /processes?view=summary&status=InProgress&size=20` | — | **3** |
| `GET /processes?view=summary&status=InProgress&size=50` | — | **2** |

Что из этого следовало:

- **`GET /processes` — это N+1 в чистом виде:** 622 запроса на страницу из 20 строк и 33 на
  страницу из 1 строки, то есть ~31 запрос на строку. Ровно столько же (32) стоила карточка одного
  процесса — значит, список грузит полный агрегат на каждую строку. Отсюда и линейный рост
  задержки по размеру страницы (§7.1).
- **Агрегат `/approval-view/entities` тоже не batch:** 56 запросов на процесс с 10 этапами, из них
  30 — отдельные запросы за решениями участников.
- **`/approval-view/processes/my` — то, как надо:** 1 запрос на страницу из 20 строк, потому что
  отдаёт короткий `ProcessSummaryDto`.

### 5.4 Что было исправлено

Причина N+1 оказалась не в количестве запросов сервиса (он уже батчил участников, решения,
замечания и комментарии), а в двух местах:

1. **`DecisionMapper.hasDecision(Participant)`** спрашивал наличие решения **по одному участнику за
   раз** (`findById`), причём для участника без решения каждый повторный вызов снова шёл в БД —
   отрицательного кеша у Hibernate нет. Маппер обходит участников несколько раз (в самом процессе и
   в этапах с решениями), поэтому агрегат делал 30 лишних запросов. Заменено на пакетный запрос
   `DecisionRepository.findParticipantIdsWithDecision(Collection<UUID>)` (проекция только
   идентификаторов), а сам `hasDecision` удалён — чтобы N+1 нельзя было вернуть случайно.
   `ProcessMapper.toParticipantDto` теперь принимает готовый набор.
2. **Ленивые коллекции без пакетной подгрузки.** Добавлен
   `spring.jpa.properties.hibernate.default_batch_fetch_size: 50` (`application.yml`): обращения к
   итерациям и участникам идут запросами `... where id in (?, ?, ...)` вместо запроса на строку.

Эффект того же профиля нагрузки (полка 3 польз./с, 30 с, пул 20, тот же набор данных):

| Метрика | До | После |
|---|---|---|
| p50 профиля | 92 мс | **24 мс** |
| p95 профиля | 994 мс | **130 мс** |
| p95 агрегата (`/approval-view/entities`) | 127 мс | **33 мс** |
| p99 агрегата | 352 мс | **48 мс** |
| максимум | 1 392 мс | 267 мс |

Проверено и на корректность: после реального решения участника `hasDecision` равен `true` и в
карточке процесса, и в агрегате (раньше флаг считался тем же запросом, теперь — из набора). Правки
прогнаны полным набором тестов: `./gradlew test` — 305 тестов, 0 падений, 0 ошибок (на момент правки
N+1 было 298; четыре web-теста и три интеграционных добавлены для `view=summary`, §5.5).

**Что осталось не исправленным.** `GET /processes` без параметра `view` по-прежнему отдаёт полный
`ProcessDto` на каждую строку страницы: пакетная подгрузка снизила цену с 622 до 31 запроса, а
`view=summary` (§5.5) убирает и её — но для клиентов, которым список нужен целиком, полное
представление осталось сознательно. Кроме того, в `ProcessRepository` лежит неиспользуемый
`findByEntityTypeAndEntityIdWithStagesAndIterations` (fetch join для этого же случая) — после
пакетной подгрузки он даёт выигрыш в один запрос, но остаётся мёртвым кодом.

### 5.5 `view=summary` у списка процессов

Замеренная причина: список — самый частый запрос UI, и он собирал полный агрегат на каждую строку
страницы. Добавлен параметр `view` (`full` по умолчанию, `summary` — краткая карточка
`ProcessSummaryDto` без этапов и участников), реализация — `ProcessListView`,
`ProcessMapper.toSummaryDto`, `ProcessViewService.listSummaries`.

Замеры на том же наборе (30 процессов × 10 этапов), последовательные запросы без конкуренции:

| Запрос | SQL/запрос | мс/запрос |
|---|---|---|
| `GET /processes?status=InProgress&size=20` (полное) | 31 | 133 |
| `GET /processes?view=summary&status=InProgress&size=20` | **3** | **33** |
| `GET /processes?status=InProgress&size=50` (полное) | 48 | 184 |
| `GET /processes?view=summary&status=InProgress&size=50` | **2** | **34** |

То есть 31 → 3 запроса и 133 → 33 мс на страницу из 20 строк; на странице из 50 строк разрыв
больше (48 → 2 запроса, 184 → 34 мс), потому что пакетная подгрузка накрывает всю страницу одним
запросом.

Детали, которые стоит знать:

- **Порядок значений без учёта регистра:** `ProcessListView.parse` принимает и `summary`, и
  `SUMMARY`; неизвестное значение — `400 BAD_REQUEST`, а не молчаливый откат к `full`.
- **Заодно исправлен ответ на неверный тип параметра:** `?initiatorId=not-a-uuid` раньше давал `500`
  (исключение попадало в последнюю ветку `GlobalExceptionHandler`), теперь `400` — добавлена ветка
  для `MethodArgumentTypeMismatchException`.
- **Спецификация §12.2 описывает в списке именно краткое представление**, поэтому `summary` —
  движение к контракту, а `full` сохраняет прежнее поведение. Параметр `view` в спеке пока не
  описан: при следующей правке `doc/arch/07_api_contract.md` его стоит внести.
- **SLO-гейт по-прежнему гоняет полное представление** (`UiReadSimulation`): это самая тяжёлая ветка,
  и менять её вместе с появлением параметра нельзя без пересмотра порогов. Когда UI перейдёт на
  `view=summary`, профиль стоит переключить и перемерить базу (§7.3).

Профиль `perf` — диагностический: сводка пишется на каждую сессию и сама искажает замеры
(в §7.1 p95 агрегата вырос с 64 до ~90 мс только из-за включённой статистики), поэтому для цифр
производительности его включать не нужно.

**Про `pg_stat_statements`.** В текущем `docker-compose.yml` расширение не предзагружено
(`show shared_preload_libraries` пуст), поэтому `CREATE EXTENSION pg_stat_statements` не сработает.
Чтобы получить топ запросов по суммарному времени, в сервис `postgres` нужно добавить
`command: postgres -c shared_preload_libraries=pg_stat_statements`, пересоздать контейнер и выполнить
`CREATE EXTENSION`. Для подсчёта SQL на вызов это не требуется — хватает §5.1–5.2.

## 6. Оговорки: что эти прогоны не доказывают

- **Генератор и сервис на одной машине.** Даже разными процессами они делят CPU, диск и сетевой
  стек. Цифры годятся для сравнения конфигураций между собой, но не как абсолютная ёмкость
  продакшена.
- **Размер маршрута задаётся сидером.** Прогоны 1–3 шли на трёх этапах, свип и всё дальнейшее — на
  десяти (`-Ploadtest.seed.stages=10`); сравнивать цифры разных наборов нельзя, и в отчётах это
  указано.
- **Разгон, а не полка.** Результат показывает, где деградация начинается, но не подтверждает
  устойчивость на постоянной нагрузке. Полка есть в режиме `constant`, но целевые пороги
  (этап 2) пока не зафиксированы.
- **Аутентификации нет** (ADR: `actorId` в теле запроса), поэтому в нагрузке нет ни логинов, ни
  токенов. Когда появится Spring Security, профиль придётся дополнить и цифры переснять.
- **Нет асинхронной части.** Публикация событий (Outbox → RabbitMQ) не реализована, поэтому
  нагрузка целиком синхронная: HTTP → транзакция → Postgres.

## 7. Этапы 2 и 3

**Этап 2 — фиксация SLO: сделано.** SLO зафиксирован по фактическим замерам полки и проверяется
`assertions` сценария в режиме `constant` (§7.4). Прогон падает при выходе за пороги — проверено на
перегрузке.

**Этап 3 — регрессионный гейт в CI: не начат.** Запускать профиль чтения на короткой полке против
сервиса, поднятого в пайплайне, и падать при выходе за SLO. Требуется: сервис из `docker compose`,
время прогрева, отдельная задача Gradle (например `loadTest`), не входящая в `build`.

### Базовая линия

Машина: 24 CPU, Windows 11; Postgres 16 в Docker (`docker-compose.yml`), приложение — `bootRun`
(JDK 21). Дата прогонов — 2026-10-10/11. Прогоны 1–3 — на шаблоне из 3 этапов и 30 процессах, пул

### 7.1 Что показал первый прогон

**Потолок задаёт пул соединений, а не CPU.** Во время третьего прогона снятые серверные метрики:

| Метрика | Значение | Что означает |
|---|---|---|
| `hikaricp_connections_active` | **10** (потолок) | Все соединения заняты всё время прогона |
| `hikaricp_connections_pending` | **189** | 189 потоков ждут соединение из пула |
| `jvm_threads_live_threads` | **217** | Потоки Tomcat (по умолчанию 200) выстроились в очередь |
| `process_cpu_usage` | **≈0,005** | Приложение почти не работает — оно ждёт БД |

То есть деградация с 355 мс (p95) до 43 111 мс произошла не из-за нехватки CPU и не из-за ошибок
(их 0), а потому что запросы держат соединение и очередь растёт быстрее, чем пул её разбирает.
Проверяемая гипотеза для следующего шага: увеличение `DB_POOL_MAX_SIZE` поднимает потолок чтения
пропорционально, пока не упрёмся в Postgres.

**Медленный эндпоинт — не агрегат, а список.** Замеры по одному запросу последовательно (без
конкуренции, прогретый JIT):

| Эндпоинт | мс/запрос |
|---|---|
| `GET /approval-view/processes/my` (size=20) | 7 |
| `GET /processes/{id}` | 26 |
| `GET /approval-view/entities/{entityId}` (целевой, порог 500 мс) | **51** |
| `GET /approval-view/tasks/my` (size=20) | 122 |
| `GET /processes?status=InProgress&size=20` | **362** |

**`GET /processes` масштабируется линейно по размеру страницы — это N+1:**

| `size` | 1 | 5 | 10 | 20 | 50 |
|---|---|---|---|---|---|
| мс/запрос | 32 | 90 | 178 | 377 | 577 |

Для сравнения: `GET /approval-view/processes/my` (тот же список, но `ProcessSummaryDto`) — 7 мс и
при `size=1`, и при `size=20`.

Причина видна из DTO: `ProcessController.listProcesses` возвращает `Page<ProcessDto>`, то есть на
каждую строку страницы — полный агрегат с этапами, итерациями и участниками, а маппинг обходит
ленивые коллекции построчно. При `size=20` один HTTP-запрос занимает соединение ~380 мс, поэтому
даже с большим пулом потолок этого эндпоинта ~26 rps на соединение.

**Ограничение требования §25.2.** Агрегат уложился в 64 мс (p95) — но на шаблоне из 3 этапов и 30
процессах. Требование говорит про 10 этапов, поэтому порог 500 мс пока проверен не полностью:
для честной проверки нужен шаблон на 10 этапов (параметр сидера).

**Счётчик запросов найден** (см. §5): сводка по сессии включается категорией
`org.hibernate.session.metrics`, а до этого профиль `perf` молчал из-за неверного имени логгера и
уровня. Оба способа — сводка сессии и SQL-лог — дают одинаковые числа, поэтому вопрос «сколько SQL
на запрос» больше не догадка: `GET /processes?size=20` — это 622 запроса, агрегат на 10 этапах — 56,
а `/approval-view/processes/my` — 1.

### 7.2 Свип размера пула соединений

**Зачем.** Первый прогон показал упор в пул (10 соединений, очередь 189 потоков). Свип проверяет,
растёт ли потолок чтения пропорционально пулу, и где узким местом становится что-то другое.

**Как измерялось.** Набор: 30 процессов × **10 этапов** (`-Ploadtest.seed.stages=10`, требование
§25.2), шаблон `loadtest-loadtest-s10-*`. Нагрузка одинаковая во всех трёх прогонах:
`-Ploadtest.read.mode=constant -Ploadtest.read.usersPerSec=25 -Ploadtest.read.durationSeconds=60`
(спрос ≈ 100 запросов/с, 4 запроса на пользователя), прогрев 10 с отдельной сценой. Менялся только
`DB_POOL_MAX_SIZE`.

| `DB_POOL_MAX_SIZE` | Достигнуто, rps | p50, мс | p95, мс | p99, мс | Очередь за соединением (max) | CPU приложения (max) |
|---|---|---|---|---|---|---|
| 10 | 31,5 | 15 781 | 39 795 | 42 459 | 189 | 0,7 % |
| 20 | 44,6 | 8 737 | 18 954 | 22 207 | 179 | 1,1 % |
| 40 | 47,6 | 7 599 | 17 230 | 18 914 | 159 | 6,3 % |

Ошибок ни в одном прогоне нет: сервис не отказывает, а копит очередь.

**Выводы.**

1. **Пул работает, но только до ~20 соединений.** 10 → 20 даёт +42 % пропускной способности и
   вдвое меньшую задержку; 20 → 40 — только +7 %. Дальше добавление соединений почти ничего не
   меняет, то есть узкое место уехало за пул.
2. **Приложение по-прежнему простаивает** (CPU ≤ 6,3 % на всех прогонах), а очередь за соединением
   не исчезает даже при 40 соединениях (159). Значит, запросы ждут не потока, а времени
   обслуживания в БД: при спросе ~100 rps система отдаёт ~48 rps, и разрыв закрывается очередью.
3. **Потоки Tomcat упираются в потолок** во всех трёх прогонах (217 при дефолтных 200), поэтому
   следующий вопрос — что именно ограничивает: способность Postgres (CPU/IO контейнера) или
   исчерпание потоков Tomcat. Разделяются двумя прогонами: поднять `server.tomcat.threads.max`
   при пуле 40 и снять `pg_stat_activity`/`docker stats` во время нагрузки.

**Набор данных после свипа:** 30 процессов × 10 этапов (300 этапов, 300 участников) помечены
`entity_type = LOADTEST`; шаблон — `loadtest-loadtest-s10-*`. Очистка — §9.

**Проверка требования §25.2 на 10 этапах (без насыщения).** Полка 3 польз./с (≈ 11 запросов/с) на
пуле 20, 30 с: целевой агрегат `GET /approval-view/entities/{entityId}` — p95 **127 мс**, p99
**352 мс**, то есть требование «быстрее 500 мс на процессе с 10 этапами» выполняется. При этом
общий p95 профиля — 994 мс: его вытягивает не агрегат, а `GET /processes?size=20` и карточка
процесса (у последней p95 ≈ 595 мс). Это ещё раз показывает, что «узкое место» профиля чтения —
не тот эндпоинт, под который написано требование. Замеры этого раздела сделаны **до** исправления
N+1 (§5.4), поэтому цифры здесь — историческая точка отсчёта, а не текущее состояние.

### 7.3 SLO профиля чтения (этап 2)

**Рабочая полка:** 40 пользователей в секунду (≈155 запросов/с), пул соединений 20, набор
30 процессов × 10 этапов. Полка выбрана по свипу интенсивности: на 40 польз./с система держит
p99 224 мс, на 80 польз./с уходит в секунды. На полке занято 8 соединений из 20, очередь за
соединением нулевая, CPU приложения 2,5 % — это устойчивая рабочая точка, а не край возможностей.

| Метрика | Порог (`assertion`) | Замер на полке | Запас |
|---|---|---|---|
| Доля ошибок | < 0,1 % | 0 % | — |
| Агрегат `/approval-view/entities`, p95 | < 150 мс | 24 мс | 6× |
| Агрегат, p99 | < 500 мс (это и есть требование §25.2) | 35 мс | 14× |
| Весь профиль, p95 | < 300 мс | 112 мс | 2,7× |
| Весь профиль, p99 | < 800 мс | 224 мс | 3,6× |

Пороги заданы в `UiReadSimulation` (константы `SLO_*`) и применяются **только в режиме полки**: на
разгоне остаются мягкие guardrail'ы, потому что разгон специально доводит систему до отказа и
жёсткие пороги падали бы всегда, ничего не сообщая.

```powershell
# SLO-прогон (эталон; свойства в кавычках — требование PowerShell, см. §3.5)
./gradlew gatlingRun --simulation=ru.coordination.approval.loadtest.UiReadSimulation `
  "-Ploadtest.read.mode=constant" "-Ploadtest.read.usersPerSec=40" `
  "-Ploadtest.read.durationSeconds=60" "-Ploadtest.read.warmupSeconds=5"
```

Если интенсивность отличается от SLO-полки, сценарий печатает предупреждение: пороги рассчитаны
именно на 40 польз./с.

**Что гейт действительно ловит (проверено).** Тот же сценарий на 80 польз./с валит четыре порога из
пяти: агрегат p95 1 946 мс, p99 2 018 мс, профиль p95 1 949 мс, p99 2 187 мс — сборка падает
(`BUILD FAILED`). Доля ошибок при этом осталась нулевой: перегрузка на этом сервисе проявляется
очередью и задержкой, а не отказами, поэтому гейт обязан проверять перцентили — по одним ошибкам
деградация не видна.

Пороги читаются из свойств (`-Ploadtest.slo.*`), а значения по умолчанию — это измеренная база выше.
Настраиваемость нужна не для того, чтобы «ослабить, пока не позеленеет», а потому что на другой
машине (раннер CI, стенд) абсолютные цифры иные: базу там перемеряют и фиксируют заново. Длительность
полки тоже часть определения SLO: прогон на 15 с вместо 60 с даёт p95 346 мс и p99 1 026 мс вместо
112 и 224 — короткое окно не выходит на установившийся режим.

### 7.4 Что делать дальше

1. **Откалибровать пороги на раннере CI.** Гейт готов и проверен (§8), но его пороги измерены на
   машине 24 CPU. Первый ночной прогон на раннере GitHub — это калибровка: посмотреть артефакт,
   зафиксировать базу для этого класса машин и передать пороги явно в workflow.
2. **Список разгружен параметром `view=summary`** (31 → 3 запроса, 133 → 33 мс, §5.5). Осталось
   организационное: согласовать с UI переход на `view=summary` как основной для списка, внести
   параметр в контракт §12.2 и после этого переключить SLO-профиль на краткое представление с
   пересмотром порогов.
3. **Перемерить потолок после исправления N+1.** Свип §7.2 сделан до правки: тогда потолок был
   48–68 rps и упирался в пул, сейчас проба на 80 польз./с даёт 232 rps, то есть колено уехало.
   Полезно повторить свип пула (10/20/40) и отделить ограничение Postgres от потоков Tomcat
   (`pg_stat_activity`, `docker stats`, `server.tomcat.threads.max`).
4. **Профиль записи под нагрузкой.** `LifecycleSimulation` прогнан только на разгоне 1→2 польз./с
   (§7, прогон 2), админский профиль шаблонов добавлен (§3.4, прогон 7). Открытыми остаются
   профиль решений и `resume`: без отклонения решения состояние `OnRework` недостижимо, поэтому
   `resume` нельзя проверить честно. Заодно это единственный непокрытый путь конкурентной записи
   (`@Version` на `ProcessInstance`).

## 8. Гейт в CI (этап 3)

Гейт — это не отдельная программа, а две Gradle-задачи, поэтому он одинаково работает локально и в
любой CI-системе:

| Задача | Что делает |
|---|---|
| `loadSeed` | Создаёт набор, на котором зафиксирован SLO: шаблон + 30 процессов × 10 этапов |
| `loadTest` | Запускает SLO-полку 40 польз./с на 60 с и падает, если нарушен хотя бы один порог |

`loadTest` зависит от `loadSeed`, поэтому в CI достаточно одной команды:

```bash
./gradlew loadTest                     # сервис ожидается на http://localhost:8080
./gradlew loadTest -x loadSeed         # повторный прогон по уже созданным данным
./gradlew loadTest -Ploadtest.baseUrl=http://localhost:8081   # другой адрес
```

Что **нельзя** менять в гейте без пересмотра SLO: интенсивность полки (`loadtest.read.usersPerSec`),
длительность (`loadtest.read.durationSeconds`) и размер набора (`loadtest.seed.*`). Пороги привязаны
к этой комбинации; всё это — часть определения SLO, а не «настройки прогона». Если нужно мерить
другое, это уже не гейт, а исследовательский прогон.

**Workflow:** [.github/workflows/performance.yml](.github/workflows/performance.yml) — ночной прогон
(`cron: 0 3 * * *`) и ручной запуск (`workflow_dispatch`). Шаги: `bootJar` → `docker compose up -d
--build` → ожидание `/actuator/health` → `./gradlew loadTest` → артефакт с отчётом Gatling → `docker
compose down -v`. Том Postgres удаляется на выходе, поэтому каждый прогон стартует с чистой базы и
одинакового набора данных.

Почему ночью, а не на каждый push: прогон поднимает стек и грузит сервис ~2 минуты, а на общих
раннерах результат чувствителен к соседям — в PR это дало бы ложные падения. Деградацию гейт ловит
за сутки, а перед релизом его можно запустить вручную.

**Калибровка под новую машину.** Значения по умолчанию измерены на машине 24 CPU (§7.3). Раннер
GitHub слабее, поэтому первый прогон там — калибровка: смотрите артефакт `gatling-report`, меряете
свою базу и передаёте пороги явно:

```bash
./gradlew loadTest \
  -Ploadtest.slo.aggregateP95Ms=... -Ploadtest.slo.aggregateP99Ms=... \
  -Ploadtest.slo.globalP95Ms=...    -Ploadtest.slo.globalP99Ms=...
```

Правило то же, что и в §7.3: сначала замер, потом порог. Молча ослабленный порог превращает гейт в
зелёную лампочку.

**Проверено на стенде.** `./gradlew loadTest` на SLO-полке — `BUILD SUCCESSFUL`, все пять порогов
пройдены (агрегат p95 69 мс, p99 250 мс, профиль p95 194 мс, p99 423 мс, ошибок 0). Тот же вызов с
`-Ploadtest.read.usersPerSec=80` — `:loadTest FAILED` и ненулевой код возврата: четыре порога из пяти
нарушены. Именно ненулевой код и роняет job в CI.

**Чего гейт не делает.** Он не ищет потолок (для этого разгон), не проверяет профиль записи и
шаблоны (`LifecycleSimulation` запускается вручную), не покрывает решения и `resume`, и работает на
одной машине с сервисом — то есть ловит регрессию относительно своей же базы, а не абсолютную
ёмкость.

## 9. Очистка данных прогона

Нагрузочные данные помечены отдельным типом сущности (`LOADTEST`), поэтому удаляются одним
условием. Порядок обязателен: внешние ключи идут от процессов к участникам, поэтому удалять нужно
от листьев к корню — иначе Postgres отклонит удаление (`violates foreign key constraint`). Запрос
ниже проверен на стенде: удаляет данные прогона и не трогает процессы других типов.

```sql
-- выполнять на стенде, а не на боевой БД; одной транзакцией, чтобы при ошибке ничего не осталось
begin;
create temp view lt_proc  as select id from process_instance where entity_type = 'LOADTEST';
create temp view lt_stage as select id from stage_instance where process_id in (select id from lt_proc);
create temp view lt_iter  as select id from stage_iteration where stage_id in (select id from lt_stage);
create temp view lt_part  as select id from participant where stage_iteration_id in (select id from lt_iter);
create temp view lt_tpl   as select id from template where name like 'loadtest-%';

delete from additional_approver where participant_id in (select id from lt_part);
delete from comment             where process_id in (select id from lt_proc);
delete from decision            where participant_id in (select id from lt_part);
delete from remark              where process_id in (select id from lt_proc);
delete from final_decision      where process_id in (select id from lt_proc);
delete from archive_metadata    where process_id in (select id from lt_proc);
delete from participant         where id in (select id from lt_part);
delete from stage_iteration     where id in (select id from lt_iter);
delete from stage_instance      where id in (select id from lt_stage);
delete from process_instance    where id in (select id from lt_proc);
-- шаблоны прогона: слоты → этапы шаблона → правила применимости → сам шаблон
delete from slot_template       where stage_template_id in (select id from stage_template where template_id in (select id from lt_tpl));
delete from stage_template      where template_id in (select id from lt_tpl);
delete from applicability_rule  where template_id in (select id from lt_tpl);
delete from template            where id in (select id from lt_tpl);
commit;
```

Проверить состав до и после (второй запрос после очистки должен вернуть ноль по LOADTEST):

```sql
select entity_type, status, count(*) from process_instance group by 1, 2 order by 1, 2;
select count(*) from template where name like 'loadtest-%';
```

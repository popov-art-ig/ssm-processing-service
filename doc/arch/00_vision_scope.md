
## 1. Назначение

**Approval Service** — самостоятельный, абстрактный сервис управления процессами согласования, утверждения и подписания сущностей внешних систем.

Сервис управляет:
- шаблонами маршрутов;
- экземплярами процессов;
- этапами и итерациями этапов;
- ревизиями документа (агрегат);
- участниками и доп. согласующими (с иерархией);
- решениями, замечаниями, комментариями;
- сроками и автосогласованием;
- финальными решениями (UNIFIED);
- событиями для задач, уведомлений и аудита;
- автоматической архивацией завершённых процессов.

Сервис **не хранит** бизнес-сущности и работает через `EntityRef` + `EntitySnapshot`.

## 2. Ключевые принципы

| Принцип | Описание |
|---|---|
| Абстрактность | Модуль не знает о типах сущностей и ревизий |
| Событийная модель | Задачи и уведомления — вне сервиса, через доменные события |
| Настраиваемая карта переходов | Состояния и переходы — данные, не код |
| Фиксация версии при запуске | Snapshot-on-Start |
| Изоляция версий | Fork & Drain |
| Аудит | Каждое действие и изменение конфига фиксируется |
| Автоматическая архивация | Через 180 дней после завершения |

## 3. Границы

**Входит:** шаблоны, подбор шаблонов, генерация маршрута, процессы, этапы, итерации этапов, ревизии документа, участники, доп. согласующие с иерархией, решения, замечания, комментарии, сроки, автосогласование, финальное решение, карта переходов, аудит, доменные события, автоматическая архивация, восстановление из архива.

**Не входит:** хранение документов, создание задач и уведомлений, справочники сотрудников и ролей, КРИП/КРиП, ЭЦП, замещения сотрудников, бизнес-логика типов сущностей.

**Замещения (ADR-024).** Функциональность замещения участников (отпуск, больничный и т.п.) убрана из модуля целиком на текущем этапе — не только из границ (было заявлено «не входит» и здесь), но и из документации guards/actions/событий/адаптеров/архитектуры, где ранее оставались недоведённые до конца следы этого механизма (guard `SubstitutionActive`, ссылавшийся на несуществующую в схеме БД сущность `Substitution`). Подробности и обоснование — см. `11_adr.md` ADR-024.

## 4. Внешние интеграции

| Система | Направление |
|---|---|
| Entity System | Вход |
| Directory | Вход |
| Role Registry | Вход |
| KRIP | Вход |

| Notification System | Выход (события) |
| Audit System | Выход (события) |

**Убрано (ADR-024):** `Substitution System` (Вход) — эта строка противоречила §3, где замещения уже были заявлены как «не входит». Модуль не интегрируется с системой замещений.

## 5. Роли

| Роль | Действия |
|---|---|
| Инициатор | Создать, редактировать, запустить (STANDARD), отправить ответственному (UNIFIED), отозвать, создать ревизию, выбрать целевой этап |
| Ответственный | Согласовать маршрут, финальное решение (UNIFIED), может быть участником этапа |
| Согласующий | Approve, ApproveWithComments, Reject, добавить доп. согласующего, замечания |
| Доп. согласующий | Рекомендация, замечания, комментарии, может добавить другого доп. |
| Подписант | Подписать, отклонить |
| Наблюдатель | Просмотр |
| Администратор | Управление конфигами и шаблонами, восстановление из архива |

## 6. Нефункциональные требования

Идемпотентность API. Надёжная доставка событий (Outbox). Транзакционность переходов. Аудит. Версионирование API и конфигов. Масштабирование. Наблюдаемость. SLA.

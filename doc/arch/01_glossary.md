## 1. Назначение

Глоссарий определяет единый язык для всех участников проекта: бизнеса, аналитики, разработки. Все термины приведены с русскими расшифровками. Англицизмы (латинские названия полей, статусов, режимов) сохранены для однозначной идентификации в коде и API.

**Правила использования:**
- В документации и коде — использовать термины из глоссария.
- Новые термины — добавлять в глоссарий.
- Изменения терминов — версионировать.

## 2. Предметная область

### 2.1 Сущность

Объект, для которого запускается согласование.

**Примеры:**
- Документ
- Перечень
- Проектная документация (ПД)

**Зачем термин.** Модуль «Согласование» работает с любой сущностью, поэтому нужен общий термин.

### 2.2 Ссылка на сущность (EntityRef)

Уникальный идентификатор, по которому модуль обращается к системе-владельцу.

**Состав:**
```
EntityRef
├── entityType        // Тип сущности
├── entitySubtype?    // Подтип (опционально)
└── entityId          // Идентификатор
```

**Зачем.** Модуль не хранит сущности — он ссылается на них.

### 2.3 Снимок сущности (EntitySnapshot)

Набор атрибутов сущности, передаваемый в модуль для подбора шаблона.

**Зачем.** Сервису нужны атрибуты, чтобы подобрать подходящий шаблон.

**Состав:**
```
EntitySnapshot
├── entityRef
├── attributes       // Атрибуты для matching
└── metadata         // Дополнительные данные
```

### 2.4 Организация / Подразделение

Узел дерева организаций. Может быть организацией, подразделением или филиалом.

**Зачем.** Используется для поиска пользователей и для аудита.

### 2.5 Агрегат документа

Семейство ревизий одного документа, связанных общим идентификатором `documentAggregateId`.

**Зачем.** Объединяет все версии документа для сквозной работы и отображения.

**Пример:**
```
Договор поставки №123 (агрегат)
├── Изм. 1 → процесс 1
├── Изм. 2 → процесс 2
└── Доп. 1 → процесс 3
```

### 2.6 Ревизия документа

Новая версия документа, созданная после серьёзных изменений.

**Примеры меток:**
- `Изм. 1` — изменение 1
- `Изм. 2` — изменение 2
- `Доп. 1` — дополнение 1
- `Зам. 3` — замена 3
- `ТР. 2` — техническое решение 2

**Правило.** Метка — **свободная строка**. Модуль не знает о нотации проектной документации и не проверяет формат.

## 3. Типы процессов

### 3.1 ProcessType (Тип процесса)

Тип процесса.

**Значения:**
- **STANDARD** — стандартный процесс
- **UNIFIED** — единый процесс

### 3.2 STANDARD (Стандартный процесс)

Классический процесс согласования с несколькими этапами и итерациями.

**Характеристики:**
- Несколько этапов.
- Итерации этапов.
- Режимы агрегации решений.
- Возврат на любой разрешённый этап при отклонении.
- Финального решения нет.
- Итог определяется последним этапом.

### 3.3 UNIFIED (Единый процесс)

Процесс, в котором все этапы проходятся последовательно, а итог определяет ответственный.

**Характеристики:**
- Несколько этапов.
- Ответственный обязателен.
- Ответственный может быть участником этапа.
- Финальное решение определяет итог.
- Возврата на доработку нет.
- Ревизии документа не применимы.

## 4. Шаблоны маршрутов

### 4.1 Template (Шаблон)

Многоразовое типовое описание маршрута согласования. Версионируется — см. §4.2.

**Содержит:**
- тип процесса;
- правила применимости;
- этапы;
- слоты;
- роли ответственного и признак согласования маршрута ответственным (только UNIFIED);
- флаги обязательности и редактирования;
- признак итерационности процесса;
- список этапов для возврата;
- `version`, `parentTemplateId` (версионирование, см. §4.2).

### 4.2 Версионирование шаблона (ADR-023)

**Отдельной сущности «TemplateVersion» не существует.** Ранее в этом разделе описывалась версия шаблона как отдельная сущность со статусами Draft/Published/Deprecated/Archived — это было **исправлено** (см. `11_adr.md`, ADR-023): такая модель дублировала версионирование самого `Template` и не имела аналога в `StateMachineConfig`.

**Как версионируется `Template` фактически:** каждое изменение опубликованного шаблона создаёт **новую строку `Template`** с новым `id`, `version = предыдущая + 1` и `parentTemplateId`, указывающим на предыдущую версию — по аналогии с `StateMachineConfig` (§13.6) и с механизмом форка. `stages`, `applicabilityRules`, `responsibleRoles` хранятся непосредственно на этой строке `Template` (а не в дочерней сущности). Процесс (`ProcessInstance.templateRef`) ссылается на конкретную версионную строку `Template` — этого достаточно для Snapshot-on-Start, отдельный номер версии в процессе не нужен.

**Статусы, применяемые к строке `Template`:**
- **Draft** (Черновик) — создаётся и редактируется
- **Published** (Опубликован) — доступен для использования
- **Deprecated** (Устаревший) — не применяется для новых процессов
- **Archived** (Архивирован) — выведен из оборота

### 4.3 ApplicabilityRule (Правило применимости)

Правило применимости шаблона. Хранится со ссылкой на конкретную версию `Template` (см. §4.2).

**Содержит:**
- `entityTypes` — список типов сущностей
- `entitySubtypes` — список подтипов
- `attributeConditions` — предикаты по атрибутам

### 4.4 StageTemplate (Этап шаблона)

Описание одного этапа в шаблоне. Хранится со ссылкой на конкретную версию `Template` (см. §4.2).

**Содержит:**
- порядок;
- наименование;
- описание;
- тип этапа;
- срок;
- режим агрегации (`decisionMode`, см. §4.9 и §11);
- порядок работы (`executionOrder`, см. §4.10 и §12);
- флаги обязательности;
- `allowedReturnStages`;
- слоты.

### 4.5 SlotTemplate (Слот шаблона)

Унифицированная позиция участника в шаблоне.

**Может быть:**
- `slotType = ACTOR` — основной участник
- `slotType = ADDITIONAL_APPROVER` — дополнительный согласующий

**Содержит:**
- пользователя;
- организацию;
- допустимые роли;
- флаги редактирования;
- `dueOffset` (только для доп. согласующих);
- `orderIdx` (порядок работы основного участника при `executionOrder = Sequential`, см. §4.10, §12.2).

### 4.6 AcceptableRoles (Допустимые роли)

Массив допустимых ролей для слота.

**Зачем.** Роли, которые могут занимать слот.

### 4.7 isMandatory (Обязательность этапа)

Признак, что этап нельзя удалить из маршрута.

### 4.8 isOrderMandatory (Обязательность порядка)

Признак, что этап нельзя переместить.

### 4.9 DecisionMode (Режим агрегации решений)

Правило, определяющее, когда этап считается завершённым.

**Значения:**
- **AND** — ждём всех
- **ANY_APPROVE** — первый согласовавший
- **ANY_REJECT** — первый отклонивший
- **ANY_DECISION** — первое решение
- **FIRST_REJECT_FAIL_FAST** — первый отказ прерывает

**Применяется:** только для STANDARD.

**Реализация.** Все 5 значений реализованы единой параметризуемой функцией `evaluateAggregation(stage)` в guards `AggregationApproved` / `AggregationApprovedWithComments` / `AggregationRework` — см. `05_guards_actions_registry.md` §4.2 и `11_adr.md` ADR-022.

### 4.10 ExecutionOrder (Порядок работы участников)

Порядок работы участников на этапе.

**Значения:**
- **Parallel** (Параллельно) — все одновременно
- **Sequential** (Последовательно) — по очереди

**Применяется:** только для STANDARD.

**Реализация.** `Sequential` реализован через поле `Participant.orderIdx`, состояние участника `Pending`, guard `CanAssignTask` и действие `AssignNextParticipantTask` — см. `05_guards_actions_registry.md` §4.3, §5.2 и `11_adr.md` ADR-022.

### 4.11 ResponsibleRoles (Роли ответственного)

Массив ролей ответственного.

**Применяется:** только для UNIFIED.

### 4.12 RequiresResponsibleApproval (Согласование маршрута ответственным)

Признак, что маршрут согласовывает ответственный.

**Применяется:** только для UNIFIED.

### 4.13 ProcessIterationEnabled (Признак итерационности процесса)

Признак, разрешающий создание ревизий документа.

| Значение | Что разрешено |
|---|---|
| `false` | Только правки в рамках одного документа (итерации этапов) |
| `true` | Можно создавать новые ревизии документа (новые процессы в агрегате) |

### 4.14 allowedReturnStages (Список этапов для возврата)

Список `orderIdx` этапов, на которые можно вернуть документ при возобновлении.

**Правила:**
- Только прошлые и текущий этапы.
- Без дублей.
- Если не задан — возврат только на текущий.

**Работает:** всегда, независимо от `processIterationEnabled`.

## 5. Слоты

### 5.1 UserId (Идентификатор пользователя)

Конкретный пользователь, заданный в слоте.

### 5.2 OrganizationId (Идентификатор организации)

Организация или подразделение — область поиска пользователя.

**Зачем.** Ограничивает поиск пользователя при резолвинге.

### 5.3 isUserEditable (Можно заменить пользователя)

Признак, что пользователя можно заменить в маршруте.

### 5.4 isOrganizationEditable (Можно заменить организацию)

Признак, что организацию можно заменить.

**Правило:** требует `isUserEditable = true`.

### 5.5 isDeletable (Можно удалить слот)

Признак, что слот можно удалить из маршрута.

### 5.6 Required (Обязательность слота)

Признак, что слот должен быть заполнен для запуска процесса.

### 5.7 SlotType (Тип слота)

Тип слота.

**Значения:**
- **ACTOR** — основной участник
- **ADDITIONAL_APPROVER** — дополнительный согласующий

### 5.8 dueOffset (Смещение срока)

Смещение срока доп. согласующего от срока основного.

**Значения:**
- **H0** — 0 часов
- **H3** — −3 часа
- **H8** — −8 часов

**Применяется:** только для доп. согласующих.

## 6. Маршрут и процесс

### 6.1 Route (Маршрут)

Конкретный маршрут для конкретной сущности.

**Отличие от шаблона.** В маршруте:
- роли заменены на конкретных пользователей;
- сроки пересчитаны в даты;
- зафиксирована организация для каждого участника.

### 6.2 RouteSnapshot (Снимок маршрута)

Снимок маршрута, зафиксированный при запуске процесса.

### 6.3 ProcessInstance (Экземпляр процесса)

Экземпляр согласования конкретной сущности.

**Содержит:**
- ссылку на сущность;
- ссылку на агрегат документа;
- метку ревизии;
- ссылку на родительский процесс;
- `templateRef` — ссылку на конкретную версию `Template` (версия зафиксирована самой ссылкой, отдельного номера версии не требуется, см. §4.2, ADR-023);
- версию конфига;
- статус;
- инициатора;
- ответственного (UNIFIED);
- этапы;
- итерации.

### 6.4 StageInstance (Этап)

Конкретный этап в маршруте.

**Содержит:**
- порядок;
- наименование;
- описание;
- тип этапа;
- срок;
- режим агрегации (`decisionMode`);
- порядок работы (`executionOrder`);
- флаги обязательности;
- `allowedReturnStages`;
- статус;
- даты;
- итерации.

### 6.5 StageIteration (Итерация этапа)

Круг выполнения одного этапа.

**Содержит:**
- номер итерации;
- статус;
- дату старта;
- дату завершения;
- участников.

**Ключевое правило:** при активации этапа, если у него уже есть итерации, создаётся новая.

### 6.6 ProcessIteration (Итерация процесса)

Вычисляемое представление — максимальный номер итерации этапа по всем этапам процесса.

**Формула:**
```
processIteration = max(stageIteration.iterationIdx)
```

**Зачем.** Для группировки и отображения в листе согласования.

**Не хранится физически.**

## 7. Этапы и итерации

### 7.1 Логика создания итераций

> При активации любого этапа: если у этапа уже есть итерации — создать новую. Иначе — Iter 1.

**Работает одинаково для всех случаев:**
- Нормальный переход на следующий этап.
- Возврат на любой этап.

### 7.2 Возврат на этап

Выбор этапа, с которого начнётся новая итерация после отклонения.

**Кто выбирает.** Инициатор.

**Когда.** При возобновлении процесса.

**Как работает.**
1. Инициатор обрабатывает замечания.
2. Нажимает «Возобновить».
3. Если `allowedReturnStages` содержит > 1 этап — модалка выбора.
4. Инициатор выбирает этап.
5. Создаётся новая итерация выбранного этапа.

### 7.3 Лимит итераций

**Отсутствует.** Итераций может быть сколько угодно.

## 8. Ревизии документа

### 8.1 Когда создаётся

Инициатор при получении замечаний решает, что они **серьёзные**, и создаёт новую ревизию.

### 8.2 Что происходит

1. Создаётся **новый процесс** для новой ревизии.
2. Инициатор выбирает — **прервать ли предыдущий процесс**.
3. Если прервать → предыдущий процесс → `Отозван`.
4. Если не прервать → оба процесса идут параллельно.
5. Оба процесса связаны через `documentAggregateId`.

### 8.3 Связь с `processIterationEnabled`

| Значение | Что разрешено |
|---|---|
| `false` | Ревизии запрещены |
| `true` | Ревизии разрешены |

### 8.4 Правила

| Правило | Значение |
|---|---|
| Ревизия = новый процесс | Да |
| Агрегат объединяет ревизии | Через `documentAggregateId` |
| Прерывание предыдущего | По выбору инициатора |
| Параллельные процессы | Допустимо |
| `revisionLabel` | Свободная строка, уникальна в агрегате |
| Формат метки | Не проверяется модулем |

## 9. Дополнительные согласующие

### 9.1 AdditionalApprover (Дополнительный согласующий)

Участник процесса, который:
- даёт **рекомендацию** («Согласовать» или «Отклонить»);
- может оставить замечание или комментарий;
- **не влияет** на статус этапа.

**Важно.** `AdditionalApprover` — отдельная сущность (не строка `Participant`), и его рекомендация — отдельный, не унифицированный с `Decision` механизм. Подробности и обоснование — см. §10.2 и `11_adr.md` ADR-016.

### 9.2 Иерархия

**Доп. согласующий может добавить другого доп. согласующего.**

**Пример:**
```
Согласующий (Начальник управления)
├── Доп. согласующий (Начальник отдела)
│   └── Доп. согласующий (Эксперт отдела)
└── Доп. согласующий (Помощник)
```

**Правила:**
- Глубина иерархии — **не ограничена**.
- Количество — **не ограничено**.
- Все замечания **поднимаются до уровня основного**.
- Основной решает, какие замечания принимать.

### 9.3 Видимость

| Кто видит / Что | Основной | Доп. | Инициатор |
|---|---|---|---|
| Своё | ✅ | ✅ | ✅ |
| Основных | ✅ | ✅ | ✅ |
| Других доп. (всех уровней) | ✅ | ✅ | ✅ (только Active) |
| Детей | — | ✅ | — |
| Замечания прошлых итераций | ✅ | ✅ | ✅ |

### 9.4 Клонирование при новой итерации

| Кто добавил | Клонируется? | Дети клонируются? |
|---|---|---|
| **Template** | ✅ Да | ✅ Да |
| **Initiator** | ✅ Да | ✅ Да |
| **Participant** (основной) | ❌ Нет | ❌ Нет |
| **AdditionalApprover** | ❌ Нет | ❌ Нет |

## 10. Решения и замечания

### 10.1 Decision (Решение)

Решение **основного** участника (`Participant` — согласующий или подписант).

**Значения:**
- **Approve** (Согласовать)
- **ApproveWithComments** (Согласовать с замечаниями)
- **Reject** (Отклонить)

**Почему это важно.** `Decision` — авторитетное решение, управляющее ходом процесса: именно на нём построена агрегация решений этапа (`evaluateAggregation(stage)`, см. §11, `05_guards_actions_registry.md` §4.2) и переходы `StageStateMachine`/`ProcessStateMachine`. Это принципиально отличает `Decision` от рекомендации доп. согласующего (`Recommendation`, см. §10.2), которая на ход процесса не влияет.

### 10.2 Recommendation (Рекомендация)

Рекомендация доп. согласующего (`AdditionalApprover.recommendation`).

**Не унифицирована с `Decision`.** Ранее этот раздел утверждал, что рекомендация «унифицирована с Decision — используется та же модель, отличается только `role`» — это было **исправлено** (см. `11_adr.md` ADR-016): фактически `AdditionalApprover` — отдельная таблица со своим `id` и полем `recommendation`, не связанная внешним ключом с `Decision`, и не создающая строку `Participant`.

**Почему это важно.** Рекомендация доп. согласующего имеет **чисто информационный характер** для основного согласующего (`Participant`): она видна ему как справочная информация, но **не участвует** ни в агрегации решений этапа, ни в переходах state machine — в отличие от `Decision` (см. §10.1), которая на ход процесса влияет напрямую.

### 10.3 FinalDecision (Финальное решение)

Финальное решение ответственного.

**Применяется:** только для UNIFIED.

**Значения:** Approve / ApproveWithComments / Reject.

**Неизменяемо.**

### 10.4 Remark (Замечание)

Комментарий, возможно файл, требующий реакции.

### 10.5 Comment (Комментарий)

Информационное сообщение, не требующее реакции.

### 10.6 Статусы замечания

| Статус | Описание |
|---|---|
| **Proposed** (Предложено) | От доп., ждёт решения |
| **Active** (Действующее) | Требует реакции |
| **InProgress** (В работе) | Инициатор взял |
| **NotRequired** (Не требуется) | Не требует реакции |
| **AutoProcessed** (Авто-обработано) | При закрытии этапа |
| **Resolved** (Исправлено) | Инициатор исправил |
| **Rejected** (Отклонено) | Инициатор отклонил |
| **Closed** (Закрыто) | При согласовании |

### 10.7 Кто создаёт

| Источник | Замечания | Комментарии |
|---|---|---|
| Основной согласующий | Да (Действующее) | Да |
| Доп. согласующий | Да (Предложено) | Да |
| Инициатор | Нет | Да |
| Ответственный | Нет | Да |

## 11. Режимы агрегации

### 11.1 AND («И»)

Ждём всех, отказ не прерывает.

### 11.2 ANY_APPROVE («Первый согласовавший»)

Первый согласовавший закрывает этап.

### 11.3 ANY_REJECT («Первый отклонивший»)

Первый отклонивший отправляет этап на доработку.

### 11.4 ANY_DECISION («Первое решение»)

Первое любое решение закрывает этап или отправляет на доработку.

### 11.5 FIRST_REJECT_FAIL_FAST («Первый отказ прерывает»)

Ждём всех, но первый отказ прерывает ожидание.

### 11.6 Ключевое правило

> Этап не может быть закрыт с итогом «Отклонён», если он идёт на новую итерацию этапа. В этом случае он получает статус **На доработке**.

### 11.7 Реализация (ADR-022)

Все 5 режимов реализованы единой функцией `evaluateAggregation(stage)`, читающей `stage.decisionMode` и возвращающей `WAIT` / `APPROVED` / `APPROVED_WITH_COMMENTS` / `REWORK`. Guards `AggregationApproved` / `AggregationApprovedWithComments` / `AggregationRework` (`05_guards_actions_registry.md` §4.2) делегируют этой функции. Подробности — `11_adr.md` ADR-022.

## 12. Порядок работы

### 12.1 Parallel (Параллельно)

Все участники получают задачи одновременно.

### 12.2 Sequential (Последовательно)

По очереди: следующий получает задачу только после решения предыдущего.

**Применяется:** только для STANDARD.

**Реализация (ADR-022).** Порядок задаётся полем `Participant.orderIdx`. Участники, кроме первого по `orderIdx`, создаются в состоянии `Pending`; guard `CanAssignTask` и действие `AssignNextParticipantTask` переводят следующего участника в `Assigned` после решения предыдущего — см. `04_state_machines.md` §7, `05_guards_actions_registry.md` §4.3/§5.2.

## 13. State machine

### 13.1 State (Состояние)

Состояние сущности (процесса, этапа, участника).

### 13.2 Transition (Переход)

Переход между состояниями.

### 13.3 Guard (Условие)

Предикат, который должен быть истинным для выполнения перехода.

### 13.4 Action (Действие)

Побочный эффект перехода.

### 13.5 Trigger (Триггер)

Что вызвало переход.

**Значения:**
- **userAction** — действие пользователя
- **systemAction** — действие системы
- **timer** — таймер

### 13.6 StateMachineConfig (Конфиг карты переходов)

Конфиг, описывающий состояния и переходы для конкретной сущности.

### 13.7 Snapshot-on-Start (Фиксация версии при запуске)

При запуске процесса фиксируется версия конфига и шаблона.

### 13.8 Fork & Drain (Изоляция версий)

Старые версии шаблонов и конфигов живут, пока есть активные процессы на них.

### 13.9 StatusRegistry (Реестр статусов)

Справочник всех возможных статусов для сущностей. Хранится в БД, добавление статуса — без миграции.

### 13.10 DecisionResultRegistry (Реестр результатов решений)

Справочник всех возможных результатов решений.

**Значения:**
- **Approve** — согласовать
- **ApproveWithComments** — согласовать с замечаниями
- **Reject** — отклонить

## 14. Адаптеры

### 14.1 RoleResolverAdapter (Адаптер подбора пользователей по ролям)

Адаптер для резолвинга ролей в конкретных пользователей.

**Методы:**
- `resolveRole(roleRef, organizationId, ctx)` → `UUID?`
- `resolveRoles(roleRefs, organizationId, ctx)` → `UUID?`
- `matches(userId, roleRefs, organizationId, ctx)` → `Boolean`

**Статус на старте:** пустой (возвращает `null` / `true`).

### 14.2 EntityAdapter (Адаптер сущностей)

Адаптер для получения снимка сущности.

**Методы:**
- `getSnapshot(entityRef)` → `EntitySnapshot`
- `exists(entityRef)` → `Boolean`

**Статус на старте:** реальный (обязателен).

### 14.3 KripAdapter (Адаптер проверки полномочий)

Адаптер для проверки полномочий пользователей.

**Методы:**
- `checkPermission(userId, entityRef, action)` → `Boolean`
- `checkPermissions(userIds, entityRef, action)` → `List<UUID>`

**Статус на старте:** пустой (возвращает `true`).

**Убрано (ADR-024):** `SubstitutionAdapter` (адаптер замещений). Функциональность замещения сотрудников убрана из модуля целиком — см. `11_adr.md` ADR-024 и `00_vision_scope.md` §3.

## 15. События

### 15.1 DomainEvent (Доменное событие)

Событие, публикуемое модулем.

**Формат:** `<module>.<entity>.<action>`.

**Пример:** `approval.process.started`.

### 15.2 Outbox (Механизм надёжной публикации)

Паттерн надёжной публикации событий. Событие сохраняется в БД в той же транзакции, что и изменение состояния, затем публикуется в брокер.

### 15.3 EventContract (Контракт события)

Формальное описание типа события, payload, версии.

### 15.4 Routing Key (Ключ маршрутизации)

Ключ в RabbitMQ, определяющий, в какую очередь попадёт событие.

**Значение:** `aggregateId` — для порядка событий по сущности.

## 17. Роли модуля

### 17.1 Admin (Администратор)

**Что может:**
- Управление шаблонами и конфигами.
- Публикация версий.
- Восстановление из архива.

### 17.2 Initiator (Инициатор)

**Что может:**
- Создать процесс.
- Редактировать маршрут.
- Запустить процесс (STANDARD).
- Отправить ответственному (UNIFIED).
- Отозвать.
- Создать ревизию.
- Выбрать целевой этап при возврате.

### 17.3 Responsible (Ответственный)

**Что может:**
- Согласовать маршрут (UNIFIED).
- Принять финальное решение (UNIFIED).
- Быть участником этапа и голосовать.

### 17.4 Approver (Согласующий)

**Что может:**
- Approve / ApproveWithComments / Reject.
- Добавить доп. согласующего.
- Оставить замечания и комментарии.

### 17.5 AdditionalApprover (Дополнительный согласующий)

**Что может:**
- Дать рекомендацию.
- Добавить другого доп. согласующего.
- Оставить замечания и комментарии.

### 17.6 Signer (Подписант)

**Что может:**
- Подписать.
- Отклонить.

### 17.7 Observer (Наблюдатель)

**Что может:**
- Просматривать карточку.
- Получать уведомления.

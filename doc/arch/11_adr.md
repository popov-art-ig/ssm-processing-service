## 1. Назначение и обоснование

### 1.1 Что такое ADR

**ADR** (Architecture Decision Record, запись об архитектурном решении) — короткий документ, фиксирующий **важное архитектурное решение** с его контекстом и последствиями.

### 1.2 Зачем нужны ADR

**Проблема.** Архитектурные решения принимаются коллегиально, но со временем забываются обоснования. Через полгода никто не помнит, почему выбрана та или иная технология.

**Решение.** Фиксировать каждое важное решение в ADR.

**ADR отвечает на вопросы:**
- Что решили?
- Почему решили?
- Что рассматривали как альтернативы?
- Какие последствия?

### 1.3 Что это даёт

| Что | Зачем |
|---|---|
| Память | Возможность восстановить обоснования |
| Онбординг | Новые разработчики понимают, почему так |
| Эволюция | Возможность пересмотреть решение осознанно |
| Аудит | Документированные обоснования для стейкхолдеров |
| Стабильность | Изменение решения — через новый ADR |

---

## 2. Формат ADR

### 2.1 Структура

Каждый ADR содержит:

- **Номер и название**
- **Статус** — Предложено / Принято / Устарело / Заменено
- **Дата**
- **Контекст** — какая проблема решается
- **Решение** — что выбрали
- **Альтернативы** — что рассматривали
- **Последствия** — положительные, отрицательные, нейтральные
- **Связанные решения** — ссылки на другие ADR

### 2.2 Статусы

| Статус | Описание |
|---|---|
| **Предложено** | Обсуждается |
| **Принято** | Действует |
| **Устарело** | Больше не актуально |
| **Заменено** | Заменено новым ADR |

## 3. ADR-001: Event-Driven вместо встроенных задач и уведомлений

**Статус:** Принято  
**Дата:** 2026-09-15

### 3.1 Контекст

Модуль «Согласование» должен порождать задачи для согласующих и уведомления. В системе уже есть:

- **Модуль задач** — единая точка управления задачами.
- **Модуль уведомлений** — единая точка отправки email и ЛК.

**Вопрос.** Создавать задачи и уведомления внутри модуля или через события?

### 3.2 Решение

**Модуль не создаёт задачи и уведомления сам.** Он публикует **доменные события**, на которые подписываются внешние модули.

**Как:**
- События публикуются через **Outbox**.
- Транспорт — **RabbitMQ**.
- Гарантия — **at-least-once**.
- Подписчики — **идемпотентны**.

### 3.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Встроенные задачи | Дублирование модуля задач |
| Встроенные уведомления | Дублирование модуля уведомлений |
| Синхронный вызов модулей | Связанность, блокировка |
| Прямая публикация без Outbox | Потеря событий при сбое |

### 3.4 Последствия

**Положительные:**
- Единая точка управления задачами и уведомлениями.
- Модуль не зависит от каналов доставки.
- Легко подключаются новые подписчики.
- Не теряются события при сбое брокера.

**Отрицательные:**
- Требуется инфраструктура Outbox + RabbitMQ.
- Асинхронность усложняет отладку.
- Подписчики должны быть идемпотентны.

### 3.5 Связанные решения

- ADR-012: RabbitMQ вместо Kafka
- ADR-020: Агрегированные эндпоинты для Front

## 4. ADR-002: Data-Driven State Machine

**Статус:** Принято  
**Дата:** 2026-09-15

### 4.1 Контекст

Модуль управляет жизненным циклом нескольких сущностей (процесс, этап, участник, замечание). Состояния и переходы со временем меняются.

**Вопрос.** Зашивать состояния и переходы в код или хранить как данные?

### 4.2 Решение

**Состояния и переходы — данные, а не код.**

**Как:**
- Конфиги карт переходов хранятся в БД.
- Guards и actions — зарегистрированные плагины.
- Композиция guards и actions — данные.
- Реализация guards и actions — код.
- Изменения через новую версию конфига.

### 4.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Захардкоженные состояния | Релиз на каждое изменение |
| Enum для состояний | Жёсткая связь с кодом |
| Код-генерация из схемы | Сложность, долгий цикл |

### 4.4 Последствия

**Положительные:**
- Гибкость: изменения без релиза.
- Разные типы процессов — разные конфиги.
- Аудит изменений конфига.
- Возможность UI-редактора.

**Отрицательные:**
- Требуется движок машины состояний.
- Сложнее отладка.
- Нужна дисциплина при публикации.

### 4.5 Связанные решения

- ADR-011: Spring State Machine как движок
- ADR-003: Snapshot-on-Start + Fork & Drain
- ADR-015: Реестры статусов

## 5. ADR-003: Snapshot-on-Start + Fork & Drain

**Статус:** Принято  
**Дата:** 2026-09-15

### 5.1 Контекст

Шаблоны и конфиги версионируются. Активные процессы могут работать, когда публикуется новая версия.

**Вопрос.** Как обеспечить, чтобы смена версии не сломала работающие процессы?

### 5.2 Решение

**Комбинация двух стратегий:**

| Стратегия | Что делает |
|---|---|
| **Snapshot-on-Start** | Процесс фиксирует версию шаблона и конфига при запуске |
| **Fork & Drain** | Старые версии живут, пока есть активные процессы |

**Как:**
- Процесс фиксирует версию через `templateRef` (ссылку на конкретную версионную строку `Template`, см. ADR-023) и `configVersion`.
- Процесс работает на зафиксированных версиях.
- Удаление версии — только при `activeProcessCount = 0`.
- Только additive-изменения для активных версий.

### 5.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Принудительная миграция всех процессов | Риск сбоя, сложно |
| Без версионирования | Сломанные процессы |
| Только Snapshot | Старые версии копятся без контроля |
| Только Fork & Drain | Неизвестно, когда процесс переключится |

### 5.4 Последствия

**Положительные:**
- Процесс не меняет поведение.
- Безопасное изменение шаблонов.
- Аудит: понятно, по какой версии шёл процесс.

**Отрицательные:**
- Старые версии живут долго.
- Нужна политика архивации версий.

### 5.5 Связанные решения

- ADR-002: Data-Driven State Machine
- ADR-011: Spring State Machine как движок
- ADR-023: Версионирование шаблонов через parent_template_id

## 6. ADR-004: Резолвинг ролей через адаптер

**Статус:** Принято  
**Дата:** 2026-09-15

### 6.1 Контекст

При генерации маршрута из шаблона роли нужно преобразовать в конкретных пользователей. Резолвинг ролей — внешняя ответственность (справочник ролей, КРИП).

**Вопрос.** Как организовать интеграцию с внешней системой?

### 6.2 Решение

**Один адаптер `RoleResolverAdapter`, без плагинов.**

**Как:**
- Интерфейс: `resolveRole`, `resolveRoles`, `matches`.
- Возвращает одного пользователя или `null`.
- По умолчанию — **пустая реализация**.
- Реализация подключается через Spring `@ConditionalOnProperty`.
- Кэш отключён по умолчанию.

### 6.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Плагины (множественные адаптеры) | Избыточно |
| Мультиадаптерность | Не нужно |
| Hot-swap адаптеров | Не нужно |
| Резолвинг в модуле | Требует справочника ролей |

### 6.4 Последствия

**Положительные:**
- Модуль работает без адаптера.
- Постепенное подключение внешних систем.
- Изоляция домена.
- Простота тестирования.

**Отрицательные:**
- Замена реализации — только через конфиг.
- Нет fallback между несколькими системами.

### 6.5 Связанные решения

- ADR-010: RoleResolverAdapter возвращает одного пользователя
- ADR-008: Модуль не блокирует по ролям и организациям

## 7. ADR-005: Только автоматическая архивация

**Статус:** Принято  
**Дата:** 2026-09-15

### 7.1 Контекст

Завершённые процессы копятся в активном реестре. Нужна стратегия архивации.

**Вопрос.** Ручная архивация, автоматическая или обе?

### 7.2 Решение

**Только автоматическая архивация через 180 дней после завершения.**

**Как:**
- Триггер — истечение 180 дней.
- Планировщик — Shedlock.
- Срок хранения в архиве — **бессрочно**.
- Удаление — **не предусмотрено**.
- Восстановление — только администратор.
- Уведомления — **не отправляются**.

### 7.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Ручная архивация | Требует действий пользователя |
| Оба варианта | Избыточно |
| Удаление процессов | Потеря истории |
| Уведомления об архивации | Избыточный шум |

### 7.4 Последствия

**Положительные:**
- Чистота активного реестра.
- Не требует действий пользователя.
- Бессрочная история.

**Отрицательные:**
- БД растёт со временем.
- Партиционирование обязательно.

### 7.5 Связанные решения

- ADR-013: Shedlock для планировщика

## 8. ADR-006: Отказ от мультитенантности

**Статус:** Принято  
**Дата:** 2026-09-15

### 8.1 Контекст

Изначально планировалась мультитенантность (несколько изолированных контуров). В процессе анализа решено отказаться.

**Вопрос.** Оставить мультитенантность или убрать?

### 8.2 Решение

**Полный отказ от мультитенантности.**

**Как:**
- Убрано поле `tenantId` из всех сущностей.
- Убран принцип мультитенантности.
- Единый набор шаблонов, процессов, конфигов.
- Адаптеры работают в одном контексте.

### 8.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Оставить мультитенантность | Усложняет модель без пользы |
| Отдельная БД на тенанта | Сложность инфраструктуры |

### 8.4 Последствия

**Положительные:**
- Проще модель.
- Меньше полей.
- Проще запросы.

**Отрицательные:**
- Нельзя изолировать контуры.
- Если понадобится мультитенантность — потребуется рефакторинг.

### 8.5 Связанные решения

- ADR-019: Только идентификаторы в API

## 9. ADR-007: Статус «Отклонён» у этапа

**Статус:** Принято  
**Дата:** 2026-09-15

### 9.1 Контекст

При отклонении этапа возможны разные сценарии: возврат на текущий этап, возврат на более ранний этап.

**Вопрос.** Когда этап получает статус «Отклонён», а когда — «На доработке»?

### 9.2 Решение

**Этап получает статус «Отклонён» только при возврате на другой (более ранний) этап.**

| Ситуация | Статус этапа |
|---|---|
| Возврат на **текущий** этап | **На доработке** |
| Возврат на **более ранний** этап | **Отклонён** |

**Обоснование.** Если мы вернёмся на этот же этап — он не закрыт. Если на другой — этап закрыт окончательно.

### 9.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Всегда «Отклонён» | Некорректно — этап ещё в работе |
| Всегда «На доработке» | Нельзя закрыть этап |
| Без статуса «Отклонён» | Теряется история |

### 9.4 Последствия

**Положительные:**
- Чёткая семантика статусов.
- Корректная история.
- Понятно, какие этапы закрыты.

**Отрицательные:**
- Требуется логика при возврате.

### 9.5 Связанные решения

- ADR-009: Единый механизм итераций
- ADR-025: Уточнение перехода StageRejectedByReturn

## 10. ADR-008: Модуль не блокирует по ролям и организациям

**Статус:** Принято  
**Дата:** 2026-09-15

### 10.1 Контекст

При замене пользователя нужно проверить, что он подходит под роль. Аналогично при смене организации.

**Вопрос.** Блокировать ли операцию, если пользователь не соответствует роли?

### 10.2 Решение

**Модуль не блокирует по ролям и организациям.** Валидация — ответственность UI.

**Как:**
- `RoleResolverAdapter.matches` возвращает `true` по умолчанию (пустая реализация).
- Если адаптер возвращает `false` — UI показывает предупреждение, но операция **разрешается**.
- Модуль не проверяет соответствие `userId` ↔ `organizationId`.
- Модуль не проверяет актуальность ролей.

### 10.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Блокировать несоответствие | Жёстко, требует актуальной матрицы |
| Строгая валидация | Не всегда возможно |

### 10.4 Последствия

**Положительные:**
- Гибкость.
- Модуль не зависит от актуальности ролей.
- UI сам решает, что показывать.

**Отрицательные:**
- Может привести к некорректным маршрутам.
- Ответственность на UI.

### 10.5 Связанные решения

- ADR-004: Резолвинг ролей через адаптер

## 11. ADR-009: Единый механизм итераций (только этапы)

**Статус:** Принято  
**Дата:** 2026-09-15

### 11.1 Контекст

Изначально было два уровня итераций: итерация этапа и итерация процесса. Появилось требование выбора целевого этапа при возврате.

**Вопрос.** Оставить два уровня или унифицировать?

### 11.2 Решение

**Итерации — только на уровне этапов.** «Итерация процесса» — вычисляемое представление.

**Как:**
- Таблица `stage_iteration` — физическая.
- `process_iteration` = `max(stageIteration)` — вычисляется на лету.
- При активации этапа: если есть предыдущие итерации — создать новую.
- Лимит итераций — **отсутствует**.

### 11.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Два уровня итераций | Сложная модель |
| Только итерации процесса | Нельзя вернуться на этап |
| Лимит итераций | Не нужен |

### 11.4 Последствия

**Положительные:**
- Единая модель.
- Гибкость: возврат на любой разрешённый этап.
- Простота.

**Отрицательные:**
- Нужно вычислять «итерацию процесса» при запросе.
- Может быть много итераций без лимита.

### 11.5 Связанные решения

- ADR-007: Статус «Отклонён» у этапа
- ADR-017: Ревизии документа

## 12. ADR-010: RoleResolverAdapter возвращает одного пользователя

**Статус:** Принято  
**Дата:** 2026-09-15

### 12.1 Контекст

Роль может соответствовать нескольким сотрудникам. Нужно решить, возвращать одного или список.

**Вопрос.** Сколько пользователей возвращает `resolveRole`?

### 12.2 Решение

**Адаптер возвращает одного пользователя (приоритетного).**

**Как:**
- `resolveRole` → `UUID?`
- `resolveRoles` → `UUID?`
- Адаптер сам решает, какой приоритет.
- Если пользователь не найден — `null`.
- UI заполняет вручную, если `null`.

### 12.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Список пользователей | Усложняет UI |
| Пользователь + UI выбирает | Избыточно |
| Автоматический выбор + UI | Двойной выбор |

### 12.4 Последствия

**Положительные:**
- Простота.
- UI получает готовое значение.
- Адаптер сам определяет приоритет.

**Отрицательные:**
- UI не видит альтернатив.
- Если нужен другой пользователь — замена вручную.

### 12.5 Связанные решения

- ADR-004: Резолвинг ролей через адаптер

## 13. ADR-011: Spring State Machine как движок

**Статус:** Заменено (см. ADR-028)  
**Дата:** 2026-09-15

### 13.1 Контекст

## 18. ADR-016: Decision и Recommendation — раздельные механизмы

**Статус:** Принято (пересмотрено — заменяет прежнюю формулировку от 2026-09-15)  
**Дата:** 2026-09-18

### 18.1 Контекст

Прежняя редакция этого ADR утверждала: «Унифицировать в одну сущность `decision`... Различие — только в `participant.role`. Для доп.: `role = ADDITIONAL_APPROVER`». Этот тезис был повторён в `03_domain_model.md` §7.8 и `06_event_contract.md` §9.1.

При архитектурной рецензии обнаружено, что фактическая модель этому не соответствует и никогда не соответствовала: `AdditionalApprover` — отдельная таблица со своим `id`, статусом и собственным полем `recommendation: Enum?`, которая ссылается на `Participant` через `participantId` как на **основного согласующего**, а не сама является строкой `Participant`. Не существует механизма, который создавал бы для доп. согласующего строку в таблице `participant` с `role=ADDITIONAL_APPROVER` — соответственно, `decision.participant_id → participant(id)` физически не может указывать на доп. согласующего. Контракты подтверждают то же самое: рекомендация доп. согласующего фиксируется отдельным эндпоинтом (`07_api_contract.md` §15.5), который пишет в `additional_approver.recommendation`, а не создаёт запись в `decision`; событие `approval.additional-approver.recommended` имеет самостоятельный, отличный от `approval.decision.recorded` payload.

Это важно не только терминологически: `Decision` (основного участника, `Participant`) — авторитетное решение, управляющее ходом процесса — именно на нём построена агрегация (`evaluateAggregation(stage)`, см. ADR-022) и переходы `StageStateMachine`/`ProcessStateMachine`. `AdditionalApprover.recommendation` — рекомендация доп. согласующего, имеющая **чисто информационный характер** для основного согласующего (`Participant`) и не участвующая ни в агрегации, ни в переходах state machine. Формулировка «унифицировано» скрывала это различие и создавала риск того, что разработка предположит единый механизм там, где он не существует.

**Вопрос.** Признать модели раздельными (что уже фактически так) или реально унифицировать их (что требует создания строки `participant` для каждого доп. согласующего)?

### 18.2 Решение

**Decision и Recommendation — два раздельных, не унифицированных механизма.** Прежнее решение об унификации отменяется; фактическая (и уже реализованная в схеме) модель фиксируется как целевая.

**Как:**
- `Decision` — таблица, связанная только с `Participant` (основной согласующий/подписант). Именно `Decision` управляет ходом процесса: используется в `evaluateAggregation(stage)` (ADR-022) и в guards `AggregationApproved`/`AggregationApprovedWithComments`/`AggregationRework`.
- `AdditionalApprover.recommendation` — отдельное поле отдельной таблицы `additional_approver`, не связанное с `decision` внешним ключом. Рекомендация видна основному согласующему как справочная информация и **не влияет** на состояние этапа/процесса.
- Значение `ADDITIONAL_APPROVER` в enum `Participant.role` признано **неиспользуемым** — ни одна строка `participant` не создаётся для доп. согласующих. Значение сохранено в enum как задокументированный неиспользуемый вариант (не удаляется из схемы, чтобы не менять `CHECK`-констрейнт без необходимости), но помечено как таковое во всех документах, где встречается.
- Формулировки «унифицировано» убраны из `03_domain_model.md` §7.8, `01_glossary.md` §10.2 и `06_event_contract.md` §9.1.
- API-контракт (`07_api_contract.md` §15.5) и событийная модель (`06_event_contract.md` §9.1, §11.2) остаются как есть — они уже корректно отражают раздельные механизмы.

### 18.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Реально унифицировать: создавать `participant` с `role=ADDITIONAL_APPROVER` для каждого доп. согласующего, перенести иерархию/`dueOffset` в поля этой строки | Требует существенного рефакторинга уже зафиксированной модели `AdditionalApprover` (иерархия через `parentAdditionalApproverId`, `level`) без явного запроса такого объединения; увеличивает риск регрессии в уже проработанном механизме |
| Удалить `ADDITIONAL_APPROVER` из `Participant.role` полностью | Требует изменения `CHECK`-констрейнта и ревизии всех мест, где enum перечисляется явно (событийная модель, глоссарий) — отдельная, более широкая правка вне текущего запроса |
| Оставить формулировку «унифицировано» и трактовать её как «унифицированы только по смыслу (оба — решение по документу), а не по хранению» | Формулировка вводит в заблуждение независимо от намерения — именно так она и была прочитана при рецензии |

### 18.4 Последствия

**Положительные:**
- Документация соответствует фактической схеме БД — устранено ложное утверждение об унификации.
- Явно зафиксировано, почему это различие важно: `Decision` управляет ходом процесса, `recommendation` — не управляет.
- Не требуется рефакторинг уже работающей модели `AdditionalApprover`.

**Отрицательные:**
- Два похожих, но разных механизма («решение» и «рекомендация») в модели — это осознанно принимаемая асимметрия, а не «унификация», упоминавшаяся ранее как архитектурное преимущество.
- Значение `ADDITIONAL_APPROVER` в `Participant.role` остаётся в enum как неиспользуемое — потенциальный источник путаницы, если не помечено явно комментарием в каждом месте, где enum документируется.

### 18.5 Связанные решения

- ADR-018: Иерархия доп. согласующих
- ADR-022: Параметризуемая агрегация решений и порядок работы участников

Причина этого решения — совместимость с Spring State Machine — перестала существовать: вся ветка Spring Boot 3.x полностью вышла из OSS-поддержки (2026-06-30), а сам SSM архивирован без поддержки Boot 4. Понижение версии, оправданное на момент принятия, стало недопустимым решением (работа на полностью не поддерживаемой платформе). Заменено **ADR-028**: Spring Boot поднимается до 4.0.3 одновременно с заменой движка машины состояний.

## 24. ADR-022: Параметризуемая агрегация решений и порядок работы участников

**Статус:** Принято  
**Дата:** 2026-09-18

### 24.1 Контекст

Шаблон этапа заявляет `decisionMode` (`AND`, `ANY_APPROVE`, `ANY_REJECT`, `ANY_DECISION`, `FIRST_REJECT_FAIL_FAST`) и `executionOrder` (`Parallel`, `Sequential`) как атрибуты этапа (см. `01_glossary.md` §4.9–4.10, §11–12), и оба заявлены в `02_process_types.md` как ключевая бизнес-ценность, отличающая STANDARD от UNIFIED. При архитектурной рецензии обнаружено, что `05_guards_actions_registry.md` реализовывал только семантику `AND`: guards `G-S-002 AllApproved` / `G-S-003 AllApprovedWithComments` / `G-S-004 AnyRejected` не читали `stage.decisionMode` и не ветвились по нему; действие `A-S-001 AssignParticipantTasks` не учитывало `executionOrder` и назначало задачи всем участникам одновременно независимо от режима.

**Вопрос.** Как реализовать все 5 режимов агрегации и `Sequential`-порядок без комбинаторного взрыва guards/actions?

### 24.2 Решение

Ввести единую параметризуемую функцию `evaluateAggregation(stage)`, читающую `stage.decisionMode` и возвращающую `WAIT` / `APPROVED` / `APPROVED_WITH_COMMENTS` / `REWORK`. Guards `G-S-002` (переименован в `AggregationApproved`), `G-S-003` (`AggregationApprovedWithComments`), `G-S-004` (`AggregationRework`) делегируют этой функции — таким образом на все 5 режимов остаются те же 3 guard'а, а не 5×3.

Для `executionOrder = Sequential` вводится новое состояние участника `Pending` (создан, но задача не назначена), guard `G-PA-007 CanAssignTask` (участник может получить задачу, если все участники с меньшим `orderIdx` уже приняли решение), переход `AssignTask` (`Pending → Assigned`) и действие `A-S-009 AssignNextParticipantTask`, вызываемое как побочный эффект переходов `Decide`/`AutoApprove`: назначает задачу следующему по `orderIdx` участнику при `Sequential`, no-op при `Parallel`.

**Как:**
- `evaluateAggregation(stage)` — общая функция (см. `05_guards_actions_registry.md` §4.2), корректно разграничивающая `AND` (ждёт решения всех, без короткого замыкания) и `FIRST_REJECT_FAIL_FAST` (ждёт всех, но отказ одного даёт немедленный `REWORK`) от `ANY_APPROVE`/`ANY_REJECT`/`ANY_DECISION` (досрочный выход при первом подходящем решении).
- `Participant.orderIdx` — новое поле (порядок работы при `Sequential`; не используется при `Parallel`).
- `Participant.status` — добавлено значение `Pending`.
- `A-S-001 AssignParticipantTasks` — ветвится по `executionOrder`: при `Parallel` назначает всех участников сразу (`Assigned`), при `Sequential` — только первого по `orderIdx` (`Assigned`), остальные создаются в `Pending`.

### 24.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Отдельный guard на каждую комбинацию `decisionMode` × переход | Комбинаторный взрыв (5 × 3 = 15 guards) |
| Реализовать только `AND` + `Parallel`, остальные режимы — задокументированное ограничение MVP в ADR | Отклонено пользователем в пользу полной реализации — режимы агрегации и порядок работы — заявленная ключевая ценность STANDARD-процесса |
| Sequential через отдельную StateMachine на этап | Избыточная сложность, дублирование `ParticipantStateMachine` |
| `orderIdx` вычисляется на лету из `slot_template`, без явного поля у `Participant` | Теряется при клонировании/ручном добавлении участника вне шаблона |

### 24.4 Последствия

**Положительные:**
- Все 5 заявленных в `01_glossary.md` режимов агрегации теперь фактически реализованы в guards/actions.
- `Sequential`-порядок реализован без изменения `StageStateMachine` — вся логика в `ParticipantStateMachine` плюс одно новое поле.
- Guards остаются переиспользуемыми (3 guard на 5 режимов), в духе ADR-002.

**Отрицательные:**
- `evaluateAggregation` — более сложная функция, чем прежние тривиальные guard-предикаты; требует полного набора unit-тестов на все 5 режимов × оба порядка выполнения.
- Добавлено новое состояние участника (`Pending`), что усложняет `ParticipantStateMachine`.

### 24.5 Связанные решения

- ADR-002: Data-Driven State Machine
- ADR-016: Decision и Recommendation — раздельные механизмы

## 25. ADR-023: Версионирование шаблонов через parent_template_id

**Статус:** Принято  
**Дата:** 2026-09-18

### 25.1 Контекст

Версионирование шаблона было реализовано двумя параллельными механизмами одновременно: (1) `Template.version` + `Template.parentTemplateId` — цепочка версий/форков самого `Template`, и (2) отдельная сущность `TemplateVersion` (1:N от `Template`) со статусами `Draft`/`Published`/`Deprecated`/`Archived`, в которой на самом деле хранились `stages`/`applicabilityRules`/`responsibleRoles`. Оба механизма решали одну и ту же задачу, что противоречило принципу единого источника истины и не имело аналога в `StateMachineConfig` (§8.2), которая версионируется проще — каждая версия — отдельная строка с уникальным `(entityType, processType, version)`, без дочерней «ConfigVersion»-сущности. Дополнительный симптом: `ProcessInstance` хранил одновременно `templateRef` (UUID) и `templateVersion` (Int) как два отдельных поля, из которых было неясно, какое из них — источник истины.

**Вопрос.** Оставить оба механизма, выбрать один — и какой?

### 25.2 Решение

**Убрана отдельная сущность/таблица `template_version`.** `stages` (через `stage_template.template_id`), `applicabilityRules` и `responsibleRoles` перенесены непосредственно на `Template`. Версионирование `Template` выполняется по той же схеме, что уже использовалась для форка и для `StateMachineConfig`: каждое изменение опубликованного шаблона создаёт новую строку `Template` с новым `id`, `version = предыдущая + 1` и `parentTemplateId`, указывающим на предыдущую версию. `ProcessInstance.templateRef` указывает на конкретную строку `Template` (конкретную версию) — этого достаточно для Snapshot-on-Start (ADR-003); отдельное поле `templateVersion` в процессе убрано, так как версия зафиксирована самой ссылкой.

**Как:**
- Удалена таблица `template_version`.
- Добавлены поля `template.responsible_roles` (`uuid[]`), `template.requires_responsible_approval` (`boolean`).
- `stage_template.template_version_id` → `stage_template.template_id`.
- `applicability_rule.template_version_id` → `applicability_rule.template_id`.
- `process_instance.template_version` (integer) — удалено.
- Fork & Drain (ADR-003) применяется к `Template` напрямую, без промежуточного слоя `TemplateVersion`.

### 25.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Оставить `TemplateVersion`, убрать `parent_template_id`/`version` с `Template` | Ломает уже описанный и используемый механизм форка |
| Оставить оба механизма как есть | Двойная модель версионирования, дублирование `stages`/`applicabilityRules`/`responsibleRoles` — источник рецензионной находки |
| Версионировать через отдельный JSON-снапшот на процессе | Дублирование данных шаблона на каждый процесс, сложные миграции при изменении структуры снапшота |

### 25.4 Последствия

**Положительные:**
- Единый механизм версионирования, симметричный `StateMachineConfig` (ADR-002).
- Меньше таблиц и JOIN'ов при чтении активного шаблона.
- Snapshot-on-Start реализуется одной ссылкой (`templateRef`), без отдельного номера версии.

**Отрицательные:**
- Каждое изменение шаблона — новая строка `template` (а не строка в дочерней таблице), из-за чего таблица `template` растёт быстрее; требуется тот же контроль активных версий (Fork & Drain), что и раньше.
- Интеграции/экраны, ожидавшие отдельное числовое поле `templateVersion`, должны быть переписаны на работу с `templateRef`/`parentTemplateId`-цепочкой.

### 25.5 Связанные решения

- ADR-003: Snapshot-on-Start + Fork & Drain
- ADR-002: Data-Driven State Machine

## 26. ADR-024: Отказ от функциональности замещений (Substitution)

**Статус:** Принято  
**Дата:** 2026-09-18

### 26.1 Контекст

В документации присутствовали упоминания механизма замещения участников: guard `G-PA-005 SubstitutionActive`, действие `A-PA-003 UpdateAssignee`, переход `ReassignParticipant` (`ParticipantStateMachine`), событие `approval.task.reassigned`, адаптер `SubstitutionAdapter` и слушатель `SubstitutionListener` (`09_adapters.md` §8). При рецензии обнаружено, что guard `SubstitutionActive` ссылался на несуществующую в схеме БД сущность `Substitution` (с полями `periodFrom`/`periodTo`) — что согласуется с явным более ранним решением «убрано `substitutionRef`» в доменной модели, но не было доведено до конца: guard и переход остались, хотя данных, на которые они опираются, никогда не существовало. Кроме того, судя по описанию адаптеров (`09_adapters.md` §8.5, §8.8), реальное замещение выполнялось не через переход `ReassignParticipant`, а напрямую — слушатель вызывал `participant.setUserId(...)` в коде, минуя state machine.

**Вопрос.** Описать сущность `Substitution` в схеме (устранить несоответствие достройкой) или убрать функциональность замещений целиком?

### 26.2 Решение

**Функциональность замещений полностью убирается из модуля на текущем этапе.** Она деприоритизирована — не переносится в backlog как заготовка, а исключается из документации целиком, чтобы не оставлять описания несуществующего/наполовину реализованного механизма.

**Как:**
- Убраны: guard `G-PA-005 SubstitutionActive`, действие `A-PA-003 UpdateAssignee`, переход `ReassignParticipant` (`04_state_machines.md` §7.2, `05_guards_actions_registry.md`).
- Убрано событие `approval.task.reassigned` (`06_event_contract.md` §8.4 и строка в сводной таблице событий).
- Убран адаптер `SubstitutionAdapter` и слушатель `SubstitutionListener` (`09_adapters.md` §8 целиком, диаграммы, конфигурация Spring-бинов).
- Убраны упоминания «Substitution System» из контекстной и контейнерной диаграмм и сценария надёжности (`10_architecture.md`).
- Убраны термины из глоссария (`01_glossary.md` §14.4, §18.11) и из границ модуля (`00_vision_scope.md` §3, §4).
- Если замещение понадобится в будущем — оно должно быть спроектировано заново (включая полноценную сущность `Substitution` в БД, а не guard, ссылающийся на несуществующие поля) и оформлено новым ADR, заменяющим этот.

### 26.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Добавить таблицу `substitution` и описать её в схеме | Функциональность признана неприоритетной для текущей итерации; расширяет объём модуля без текущей необходимости |
| Оставить guard как заглушку (всегда `false`) | Оставляет мёртвый код и вводящую в заблуждение документацию (та же проблема, что и была найдена при рецензии) |
| Зафиксировать как «отложено» без удаления из документов | Документация должна отражать фактическое поведение системы, а не намерения на будущее |

### 26.4 Последствия

**Положительные:**
- Устранено расхождение «guard ссылается на несуществующую сущность».
- Меньше поверхность API/адаптеров/событий для реализации в текущей итерации.

**Отрицательные:**
- Замещение участников (отпуск, больничный и т.п.) не поддерживается модулем; при необходимости переназначения участника используется существующий ручной механизм администратора (изменение `actor_slot_ref`), не описанный как отдельный сценарий замещения.
- При повторном запросе на замещение потребуется полноценное проектирование «с нуля», включая новый ADR.

### 26.5 Связанные решения

- ADR-004: Резолвинг ролей через адаптер

## 27. ADR-025: Уточнение перехода StageRejectedByReturn

**Статус:** Принято, подтверждено пользователем  
**Дата:** 2026-09-18 (решение); подтверждено пользователем 2026-09-18

### 27.1 Контекст

При рецензии обнаружено расхождение между таблицей переходов `StageStateMachine` (`04_state_machines.md` §5.2) и описанным алгоритмом возврата на целевой этап (§11.4–11.5 того же документа). §5.2 описывал `StageRejectedByReturn` (`Active → Rejected`, `systemAction`, guard `ReturnToPriorStage`) как самостоятельный, независимо срабатывающий переход этапа. При этом алгоритм §11.5 описывает перевод промежуточных этапов в `Rejected` как результат действия `A-RT-002 RejectStagesFrom`, выполняемого внутри перехода `ResumeProcess` **на уровне процесса**. Guard `G-S-007 ReturnToPriorStage` (`05_guards_actions_registry.md` §4.2, логика `returnTargetStage.orderIdx < currentStage.orderIdx`) сам по себе определён корректно — проблема не в отсутствующем guard'е, а в том, что таблица переходов не проясняла, кто и как фактически инициирует эту транзакцию: независимая проверка на уровне этапа или программный вызов от процесса.

Это расхождение — не редакционная опечатка, а вопрос о механизме: должен ли `StageStateMachine` каждого этапа самостоятельно, независимо оценивать guard `ReturnToPriorStage` (для этого требовался бы неочевидный источник `returnTargetStage` на уровне отдельного этапа), или переход инициируется процессом, который уже знает выбранный `target` из алгоритма §11.5.

При первом прохождении этой находки пользователь, инициировавший исправление, явно указал на неуверенность в правильном решении («тут не знаю»). Решение ниже было принято как разумная техническая трактовка, сохраняющая архитектурный принцип ADR-002, и представлено пользователю для подтверждения на отдельном ревью 2026-09-18. Пользователь подтвердил решение как финальное («Подтверждаю как есть»).

### 27.2 Решение

**`StageRejectedByReturn` остаётся явным переходом `StageStateMachine`, защищённым guard'ом `ReturnToPriorStage` (G-S-007), но инициируется программно действием процесса, а не независимой оценкой на уровне этапа.** Набор этапов, которые должны получить `Rejected`, вычисляется алгоритмом возврата на уровне процесса (§11.5), уже защищённым guards `G-RT-001 IsValidReturnTarget` и `G-RT-002 AllActiveRemarksHandled`. Действие `A-RT-002 RejectStagesFrom`, выполняемое как часть перехода `ResumeProcess`, находит все `Active`-этапы с `orderIdx > target` и явно посылает каждому такому `StageInstance` системный триггер `StageRejectedByReturn` на его собственной `StageStateMachine`, передавая выбранный алгоритмом `target` как `returnTargetStage` — так guard `ReturnToPriorStage` получает нужный ему контекст и штатно проверяется при каждом срабатывании перехода, вместо того чтобы оставаться недостижимым для независимой оценки на уровне отдельного этапа.

Это решение выбрано, чтобы сохранить принцип ADR-002 («любое изменение состояния — только через явный переход state machine, а не прямая запись в БД»): переход `StageRejectedByReturn` остаётся явным, проходит штатную обработку (guard, persist, AuditEvent, публикация events), но инициируется программно действием процесса, которое одно располагает контекстом, необходимым guard'у.

**✅ Подтверждено пользователем (2026-09-18).** Решение выше рассматривалось как открытое для пересмотра ввиду изначальной неуверенности пользователя в правильном решении этой находки. При отдельном ревью 2026-09-18 пользователь явно подтвердил это решение как финальное («Подтверждаю как есть»). Альтернативная трактовка (см. §27.3) рассмотрена и не выбрана.

### 27.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Убрать `StageRejectedByReturn` как отдельный переход; действие `RejectStagesFrom` напрямую устанавливает `stage.status = Rejected`, минуя `StageStateMachine` | Нарушает принцип ADR-002 («состояние меняется только через явный переход»); усложняет аудит (переход не проходит штатный `AuditEvent`-путь) |
| Считать guard `ReturnToPriorStage` избыточным и убрать его из перехода (поскольку набор этапов уже выбран алгоритмом §11.5 до вызова действия) | Guard `G-S-007` определён корректно и является содержательной проверкой (`returnTargetStage.orderIdx < currentStage.orderIdx`), а не дублирующей формальностью — его сохранение не создаёт лишней работы, если `returnTargetStage` передаётся действием как часть контекста триггера |
| StageStateMachine самостоятельно, независимо от процесса, вычисляет и оценивает `ReturnToPriorStage` при получении обычного пользовательского/системного события | `returnTargetStage` — результат алгоритма §11.5 (выбор пользователя + `allowedReturnStages`), не выводимый из состояния одного этапа; независимая оценка на уровне этапа потребовала бы дублирования логики выбора цели возврата |

### 27.4 Последствия

**Положительные:**
- Устранено расхождение между §5.2 и §11.5 — оба описывают один и тот же механизм, и явно указано, кто вызывает переход и передаёт контекст guard'у.
- Guard `G-S-007 ReturnToPriorStage` сохранён как содержательная, а не формальная проверка.
- Принцип «изменение состояния только через явный переход SM, с проверкой guard'а» (ADR-002) сохранён без исключений.
- Решение прошло отдельное подтверждение пользователем (2026-09-18) — открытый вопрос закрыт, дальнейшего ревью не требуется.

**Отрицательные:**
- Переход, инициируемый программно действием другого уровня (процесса), а не напрямую пользователем/таймером, требует явного указания в документации (см. текст `04_state_machines.md` §5.2), чтобы не создавать впечатление, что это обычный самостоятельно срабатывающий переход этапа.

### 27.5 Связанные решения

- ADR-002: Data-Driven State Machine
- ADR-007: Статус «Отклонён» у этапа
- ADR-009: Единый механизм итераций

## 28. ADR-026: Завершение описания схемы БД (Shedlock, Idempotency-Key, отказ от attachment-таблиц)

**Статус:** Принято  
**Дата:** 2026-09-18

### 28.1 Контекст

`08_db_schema.md` §4 («Общая схема по группам») называл таблицы `shedlock`, `idempotency_key`, `remark_attachment`, `comment_attachment` как часть схемы, но ни для одной из этих 4 таблиц не было блока `CREATE TABLE` — сами секции документа (соответствующие «Группа 14» и «Группа 16») отсутствовали, из-за чего сводная таблица (§27/§29) содержала пропуски в нумерации и неверный итоговый подсчёт. Отдельно — модель вложений была противоречива уже внутри самого пакета документов: `03_domain_model.md` описывал `Remark.attachments`/`Comment.attachments` как поле `UUID[]` прямо в сущности, а `08_db_schema.md` предполагал (через названия в §4 и сводной таблице) нормализованные дочерние таблицы `remark_attachment`/`comment_attachment` — при этом ни один из двух вариантов не был доведён до конца в самой DDL таблицы `remark`.

`shedlock` — не новая функциональность: планировщик через Shedlock уже принят в ADR-013; отсутствовала только DDL-секция самой таблицы. Аналогично `idempotency_key` уже описан на уровне контракта в `07_api_contract.md` §7 (`Idempotency-Key`-заголовок, 24 часа хранения, `409 IDEMPOTENCY_CONFLICT`), но не имел таблицы в схеме БД.

### 28.2 Решение

**Восстановлены и полностью описаны таблицы `shedlock` и `idempotency_key`. Таблицы `remark_attachment` и `comment_attachment` не вводятся** — модель вложений фиксируется как поле `attachments uuid[]` непосредственно на `remark`/`comment` (симметрично тому, как это было изначально описано в `03_domain_model.md`), без отдельных нормализованных таблиц.

**Как:**
- `shedlock`: стандартная 4-колоночная схема (`name` PK, `lock_until`, `locked_at`, `locked_by`) — соответствует ADR-013 и стандартной схеме библиотеки Shedlock 7.7.0.
- `idempotency_key`: `key` (PK, значение заголовка `Idempotency-Key`), `request_hash` (для обнаружения конфликтующего повторного использования ключа), `response_status`, `response_body`, `created_at`, `expires_at` (+ индекс `ix_idempotency_key_expires` для очистки по истечении 24 часов) — соответствует `07_api_contract.md` §7.
- `remark.attachments` / `comment.attachments`: `uuid[] not null default '{}'` — ссылки на файлы во внешнем хранилище файлов (модуль не хранит сами файлы); без дочерних таблиц.
- Восстановлена целостность нумерации: добавлены секции §18 (Shedlock) и §20 (Idempotency) документа `08_db_schema.md`, сводная таблица (§27) перенумерована 1–27 без пропусков.

### 28.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Нормализованные таблицы `remark_attachment`/`comment_attachment` (id, remark_id/comment_id, file_id, file_name, created_at) | Явное указание: «они должны быть вообще убраны» — модель вложений как массив UUID проще и достаточна, поскольку модуль не управляет метаданными файлов (это ответственность внешнего файлового хранилища) |
| Оставить `shedlock`/`idempotency_key` только упомянутыми в прозе, без DDL | Именно это и было найдено как недостаток при рецензии — таблицы заявлены, но не описаны |
| Хранить `idempotency_key.response_body` как ссылку на файл вместо inline | Излишняя сложность для тела ответа, которое хранится всего 24 часа и обычно небольшое (JSON) |

### 28.4 Последствия

**Положительные:**
- Схема БД полна: каждая таблица, упомянутая в §4, имеет DDL.
- Модель вложений однозначна и согласована между `03_domain_model.md` и `08_db_schema.md`.
- Сводная таблица (§27) даёт корректный итоговый подсчёт таблиц.

**Отрицательные:**
- Массив `uuid[]` для вложений не защищён ссылочной целостностью на уровне БД (в отличие от нормализованной таблицы с `FOREIGN KEY` на `file_id`) — обоснованно принятое ограничение, так как сами файлы модулю не принадлежат.
- `idempotency_key.response_body` как `text`/`jsonb` может расти в размере при крупных ответах API — требуется мониторинг и, при необходимости, лимит на размер сохраняемого тела.

### 28.5 Связанные решения

- ADR-013: Shedlock для планировщика
- ADR-002: Data-Driven State Machine

## 29. ADR-027: Настраиваемая периодичность напоминаний

**Статус:** Принято  
**Дата:** 2026-09-18

### 29.1 Контекст

`business_context_v1.3.md` §17.2 заявляет требование: периодичность напоминаний о застоявшихся согласованиях должна быть **настраиваемой администратором**. При архитектурной рецензии (`claude/gap-analysis-business-context-vs-architecture.md`, раздел «Внутренние пробелы пакета 00–12», пункт «Напоминания») это требование было зафиксировано как пробел: `10_architecture.md` §11.1 описывал задачу планировщика `ReminderJob` с захардкоженной периодичностью «раз в день», без какого-либо механизма настройки — ни таблицы в БД, ни эндпоинта API. Хардкод в коде/конфиге приложения (`application.yml`) не удовлетворяет требованию буквально: изменение значения потребовало бы релиза, а не действия администратора.

Пользователю было предложено три варианта проектирования: минимальный дизайн (одна глобальная настройка, без гранулярности), гранулярный дизайн (настройка на уровне шаблона/типа процесса) и предварительные уточняющие вопросы. **Пользователь явно выбрал минимальный дизайн** («Минимальный дизайн (рекомендуется)»).

### 29.2 Решение

**Вводится одна глобальная, настраиваемая администратором настройка периодичности напоминаний — без гранулярности по шаблонам или типам процессов.** Дизайн симметричен уже принятому паттерну `ArchiveSettings` (`04_state_machines.md` §13.3): singleton-таблица в БД + пара admin-эндпоинтов на чтение/запись + планировщик читает значение при каждом запуске вместо использования хардкода.

**Как:**
- Новая singleton-таблица `notification_settings` (`08_db_schema.md` §22): `id smallint primary key default 1` с `check (id = 1)`, `reminder_enabled boolean not null default true`, `reminder_interval_hours integer not null default 24 check (reminder_interval_hours > 0)`, `updated_at`, `updated_by`.
- Новая группа эндпоинтов «Группа 17: Настройки уведомлений» (`07_api_contract.md` §26): `GET /admin/notification-settings` и `PUT /admin/notification-settings`, доступны только роли Admin (RBAC). `PUT` валидирует `reminderIntervalHours > 0`, иначе `400 REMINDER_INTERVAL_INVALID` (`07_api_contract.md` §9.3).
- `ReminderJob` (`10_architecture.md` §11.1) при каждом запуске читает `notification_settings` через новый `NotificationSettingsRepository` (`10_architecture.md` §9.1) вместо использования захардкоженного значения. Если `reminder_enabled = false`, задача остаётся запланированной (Shedlock, ADR-013), но не выполняет рассылку в этом запуске.
- Изменение периодичности или отключение напоминаний администратором вступает в силу при следующем запуске `ReminderJob` — без релиза и без перезапуска приложения.

**Замена движка машины состояний (ADR-028) не затрагивает это решение.** `NotificationSettingsRepository` — обычный Spring Data JPA репозиторий над таблицей `notification_settings`, не связанный с движком карты переходов; замена SSM на собственный `TransitionEngine` (ADR-028) не требует изменений в этом ADR.

### 29.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Гранулярная настройка на уровне шаблона/типа процесса (отдельная периодичность для каждого `Template` или `processType`) | Пользователь явно отклонил в пользу минимального дизайна; отсутствует зафиксированное бизнес-требование к такой гранулярности — `business_context_v1.3.md` §17.2 говорит о настройке в целом, не по шаблонам |
| Значение в `application.yml`/конфиге приложения | Не удовлетворяет требованию «настраивается администратором» буквально — изменение требует релиза/деплоя, а не действия администратора через UI/API |
| Настройка через существующий реестр `status_registry`/`decision_result_registry` (ADR-015) или через механизм guard/action Data-Driven State Machine (ADR-002) | Периодичность напоминаний — не часть модели переходов состояний (не guard и не action), а операционная настройка планировщика; переиспользование этих механизмов было бы искусственным |
| Отдельная таблица настроек на каждый вид уведомления (напоминания, эскалации и т.п.) | На данный момент существует только один вид периодического уведомления (`ReminderJob`); вводить обобщённую многострочную таблицу настроек преждевременно — будет расширено новым ADR при появлении второго вида |

### 29.4 Последствия

**Положительные:**
- Закрывает пробел, зафиксированный в `claude/gap-analysis-business-context-vs-architecture.md` (раздел «Внутренние пробелы», пункт «Напоминания»).
- Минимальный дизайн, симметричный уже принятому `ArchiveSettings` — не вводит новый архитектурный паттерн.
- Изменение периодичности не требует релиза — ключевое требование `business_context_v1.3.md` §17.2 выполнено буквально.

**Отрицательные:**
- Отсутствует гранулярность по шаблонам/типам процессов — если она понадобится позже, потребуется новый ADR и миграция схемы `notification_settings`.
- Небольшой дополнительный overhead: чтение `notification_settings` на каждый запуск планировщика (незначительно, singleton-таблица из одной строки).

### 29.5 Связанные решения

- ADR-013: Shedlock для планировщика
- ADR-005: Только автоматическая архивация (аналогичный паттерн настроек — `ArchiveSettings`)

## 30. ADR-028: Spring Boot 4.0.3 и собственный движок машины состояний (замена ADR-011, ADR-021)

**Статус:** Принято  
**Дата:** 2026-09-18

### 30.1 Контекст

ADR-021 понизил Spring Boot до 3.2.7 исключительно для совместимости со Spring State Machine (SSM) 4.0.0, которая на тот момент не была протестирована с Boot 4.x. С тех пор оба фактора, обосновывавшие это решение, изменились необратимо:

- **Spring Boot 3.2.7 (и вся ветка Boot 3.x) полностью вышла из OSS-поддержки** (Boot 3.2.7 — с 2024-12-31, вся линия 3.x — с 2026-06-30). Проект, зафиксированный на 3.2.7, с середины 2026 года работает на платформе без патчей безопасности.
- **Spring State Machine официально архивирован** сопровождающей командой 2026-07-05 («no longer maintained»), с явной записью в issue-трекере (issue #1207) об отсутствии планов поддержки Spring Boot 4 — JPA- и Redis-персистентность SSM ломаются под Boot 4. Ожидание «SSM догонит Boot 4» более не является рабочей гипотезой: библиотека не развивается.

Таким образом, оба решения — ADR-011 (выбор SSM как движка) и ADR-021 (понижение Boot ради совместимости с SSM) — держались на общей предпосылке, которая перестала выполняться одновременно для обоих. Заменять только одно из них (например, поднять Boot, оставив SSM) невозможно: сама причина понижения Boot была специфична для SSM, а альтернативы обновления самого SSM не существует.

Проверена коллекция версий, зафиксированная как целевая: Spring Boot 4.0.3 (в рамках линии 4.0.x, поддерживаемой до 2026-12-31), Spring Cloud 2025.1.1 («Oakwood», релиз 2026-01-29, парная линия релизов 2025.1.0 → 2025.1.2), Hibernate 7.4.0 (актуальная мажорная линия ORM для baseline Jakarta EE 11 / JPA 3.2, на котором построен Spring Framework 7 / Boot 4). Gradle остаётся на версии 8.8 — сборочный инструмент не завязан на совместимость SSM/Boot и изменений не требует.

**Вопрос.** Поднять Spring Boot до 4.0.3 и заменить движок машины состояний — на что?

### 30.2 Решение

**Spring Boot 4.0.3, Spring Cloud 2025.1.1, Hibernate 7.4.0, Gradle 8.8 (без изменений). Вместо Spring State Machine — собственный, специально написанный движок машины состояний**, реализующий уже существующий и не зависящий от конкретного фреймворка контракт ADR-002 (Data-Driven State Machine).

**Почему это низкий риск.** Модель ADR-002 изначально была engine-agnostic: состояния и переходы хранятся как данные (`state_machine_config`/`state_config`/`transition_config`), guards и actions — зарегистрированные Spring-бины, резолвящиеся по коду через `guard_registry`/`action_registry`. Алгоритм перехода уже полностью специфицирован в `04_state_machines.md` §3.3 и не содержит ни одной SSM-специфичной детали:

```
1. Найти переходы по (entityType, fromState, trigger, processType)
2. Отсортировать по priority
3. Для каждого:
   a. Проверить guards
   b. Если все true → actions, сменить state, опубликовать events
   c. AuditEvent
   d. Выход
4. Если ни один не сработал → ошибка/игнор
```

Замене подлежит только компонент, исполняющий этот алгоритм и хранящий текущее состояние машины — не сама модель конфигурации и не guards/actions.

**Как:**
- Компоненты `ModelFactory`/`ComponentResolver`/`GuardRegistry`/`ActionRegistry` (`10_architecture.md` §7) сохраняются по назначению — они уже были кастомными надстройками поверх SSM, а не частью самого SSM, и переносятся на новый движок без изменений в контракте.
- Компонент `StateMachineFactory` заменяется на `TransitionEngine` — центральный класс, напрямую реализующий алгоритм §3.3 (без промежуточного SSM-специфичного API создания/жизненного цикла stateMachine-инстансов).
- Компонент `Persister` (обёртка над `JpaRepositoryStateMachinePersist`) **убирается полностью**. Текущее состояние сущности хранится не в отдельной таблице (сериализованный `extended_state`/`state_machine_context` bytea), а **непосредственно в поле `status` самой сущности** (`process_instance.status`, `stage_instance.status` и т.д.), уже валидируемом через `status_registry` (ADR-015) — механизм для этого существовал и использовался ещё до принятия ADR-011, просто не был задействован как единственный источник истины, пока состояние параллельно хранилось в `ssm_state_machine_context`.
- Таблица `ssm_state_machine_context` (`08_db_schema.md` §17) удаляется из схемы; репозиторий `SSMContextRepository` (`10_architecture.md` §9.1) удаляется.
- Смена состояния и выполнение actions — в одной транзакции с записью `AuditEvent` и записью в `outbox_event` (Outbox, ADR-001), как и было; оптимистичная блокировка — через существующее поле `version` каждой сущности (`08_db_schema.md` §3.5), ранее также использовавшееся параллельно с SSM-версионированием контекста.
- Guards/actions, зарегистрированные в `05_guards_actions_registry.md`, переносятся без изменения сигнатур и семантики.

### 30.3 Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Остаться на Spring Boot 3.2.7 + SSM 4.0.0 (сохранить ADR-011/ADR-021 как есть) | Работа на полностью не поддерживаемой, не патчащейся платформе бессрочно — неприемлемо для production; у SSM нет пути вперёд (библиотека архивирована) |
| Spring Boot 4.1.x (актуальная активно развиваемая линия, была первоначально предложена при ревизии) | Решение пользователя: 4.0.3 остаётся в рамках официальной OSS-поддержки (до 2026-12-31), это более ранний и, соответственно, дольше находящийся в обороте патч-релиз линии 4.0, что снижает риск попасть на менее обкатанную минорную версию |
| Сторонний движок, поддерживающий Boot 4 (например, Camunda, Temporal, иной BPM/оркестратор) | Тяжёлая внешняя инфраструктурная зависимость и отдельный рантайм ради задачи, которая уже полностью решена моделью ADR-002 (данные + плагины); собственный движок над уже специфицированным алгоритмом дешевле и не добавляет инфраструктуры |
| Собственный движок, но с сохранением отдельной JPA-таблицы персистентности контекста (по образцу `ssm_state_machine_context`) | Избыточно: `status_registry` (ADR-015) уже даёт валидируемое персистентное состояние прямо на сущности; отдельная таблица с сериализованными bytea-блобами непрозрачна для запросов и аудита и дублирует уже имеющееся поле `status` |

### 30.4 Последствия

**Положительные:**
- Устранён самый существенный архитектурный риск модуля — зависимость от архивированной библиотеки на неподдерживаемой версии платформы.
- Больше нет внешней зависимости от движка машины состояний, чей цикл поддержки нужно отдельно отслеживать при будущих обновлениях Boot/Jakarta EE.
- Персистентность состояния упрощается: состояние — обычное поле сущности, без сериализованных blob-полей, что упрощает запросы, отладку и аудит.
- Spring Boot 4.0.3 / Spring Cloud 2025.1.1 / Hibernate 7.4.0 — актуальные версии в пределах официальных окон поддержки (Boot 4.0.x — до 2026-12-31).
- Алгоритм переходов и модель guards/actions не меняются (ADR-002 был engine-agnostic с самого начала) — миграция ограничена исполняющим движком и слоем персистентности, а не доменной логикой.

**Отрицательные:**
- Инженерные затраты на реализацию и тестирование `TransitionEngine`, несмотря на то что алгоритм полностью специфицирован; команда теряет «обкатанность» библиотеки, даже архивированной.
- Отсутствие внешней поддержки/сообщества — вся ответственность за корректность движка (в т.ч. конкурентные переходы, race conditions) лежит на команде.
- Логика оптимистичной блокировки и конкурентного доступа, ранее частично инкапсулированная в `JpaRepositoryStateMachinePersist`, должна быть реализована и протестирована самостоятельно через `version`-поле сущностей.
- Boot 4.0.3, а не последняя 4.1.x, означает, что команда обязана будет отслеживать и в дальнейшем обновиться в пределах окна поддержки линии 4.0.x (до 2026-12-31), то есть апгрейд откладывается, а не снимается с повестки.

### 30.5 Связанные решения

- ADR-002: Data-Driven State Machine (модель не меняется, меняется только исполняющий движок)
- ADR-011: Spring State Machine как движок (заменено этим ADR)
- ADR-015: Реестры статусов и результатов решений (механизм персистентности состояния движка)
- ADR-021: Понижение Spring Boot до 3.2.7 (заменено этим ADR)

### 30.6 Примечание об уточнении версии Gradle (2026-09-19)

При первой реальной попытке сборки (`./gradlew build`) кода Фазы 1 — выполненной Claude Code, поскольку облачная среда, в которой готовился код, не имела сетевого доступа к Maven Central/Gradle Plugin Portal для проверки — обнаружено, что утверждение §30.1 «Gradle остаётся на версии 8.8 — сборочный инструмент не завязан на совместимость SSM/Boot» было неверным в одной конкретной части: **плагин `org.springframework.boot` версии 4.0.3 требует Gradle 8.14 или новее** (сборка с Gradle 8.8 завершается ошибкой уже на этапе резолва плагина, до какой-либо доменной логики). Ограничение исходит от самого Spring Boot Gradle-плагина, а не от движка машины состояний/SSM — то есть причина, по которой §30.1 объявлял Gradle независимым от «совместимости SSM/Boot», остаётся верной; просто выбор версии Boot (4.0.3) сам по себе предъявляет отдельное, не связанное с SSM требование к Gradle, не учтённое на момент принятия решения.

**Уточнение:** Gradle зафиксирован на версии **8.14** (`gradle-wrapper.properties`: `gradle-8.14-bin.zip`), а не 8.8. Это не пересматривает решение §30.2 по составу стека (Spring Boot 4.0.3 / Spring Cloud 2025.1.1 / Hibernate 7.4.0 / собственный движок остаются в силе без изменений) — меняется только версия сборочного инструмента, зафиксированная как фактическое ограничение платформы, обнаруженное при первой реальной сборке.

При том же прогоне уточнены ещё две технические детали build-конфигурации, не являющиеся архитектурными решениями и не требующие отдельного ADR:
- `ext['hibernate.version']` записывается как `7.4.0.Final` — это полная Maven-координата, под которой Hibernate ORM 7.4.0 фактически публикуется в репозитории; версия та же, что и в §30.2, изменилось только написание координаты.
- В `settings.gradle` добавлен плагин `org.gradle.toolchains.foojay-resolver-convention`, чтобы Gradle мог автоматически подтягивать JDK 21 toolchain, если он не установлен локально на машине сборки — техническая надстройка над уже принятым Java 21, не отдельное решение.

**Версия:** 2.0
**Назначение:** описание бизнес-логики и правил работы модуля управления процессами согласования, утверждения и подписания

## Изменения в версии 2.0 (2026-09-18)

Версия 2.0 приводит бизнес-контекст в соответствие с фактической архитектурой модуля (`00_vision_scope.md` … `12_test_scenarios.md`, `11_adr.md`). Версия 1.4 описывала более раннюю модель, разошедшуюся с архитектурой по шести пунктам (см. `claude/gap-analysis-business-context-vs-architecture.md`). По решению заказчика соответствующие разделы **переписаны полностью** — старые формулировки не сохраняются как исторические, а заменяются действующей моделью:

- **§5, §6.2/6.3, §7.8, §11, §14.3, §16, §19, §20, §21.6, §21.8, §21.9, §22, §25** — лимит итераций процесса и продление лимита убраны целиком. Возврат при отклонении работает через точечный выбор целевого этапа (`allowedReturnStages`) без ограничения по количеству кругов. Статус процесса `OnProcessRework` убран; статус процесса `Rejected` применяется только к единому процессу.
- **§9, §21.3** — иерархия дополнительных согласующих: убрано ограничение «10 человек», убран запрет назначать других доп. согласующих, убрана изоляция видимости (доп. согласующий видит и основных, и всех доп. согласующих процесса, без ограничения итерацией).
- **§11.7 (новый раздел)** — ревизии документа: механизм, ранее не описанный в бизнес-контексте вовсе.
- **§17.1** — убрана ссылка на несуществующий статус «Ожидает новой итерации процесса».
- **§23, §24, §2.2** — убраны события и адаптер, связанные с функциональностью замещений (`Substitution`), убранной целиком (ADR-024): `approval.task.reassigned`, «Система замещений», «Адаптер замещений», термин `SubstitutionAdapter`; убраны события `approval.process.iteration-started`/`iteration-max-reached`.
- **§4** — из ролей инициатора и администратора убрано «продление лимита итераций»; добавлены «выбрать целевой этап», «создать ревизию документа», «добавить дочернего доп. согласующего».

Формулировки, не затронутые этими расхождениями (§1, §2.1 частично, §3, §6.1/6.4/6.5, §8, §10, §12, §13, §15.1, §18, §20.6–20.7, §21.1 частично, §21.2/21.4/21.5/21.7/21.10/21.11, §23.2/23.5–23.7, §24.3), оставлены без содержательных изменений.

## 1. Назначение и границы модуля

### 1.1 Назначение

Модуль «Согласование» — самостоятельный сервис для управления процессами согласования, утверждения и подписания различных сущностей внутри Системы и связанных систем.

Модуль отвечает за:
- настройку типовых маршрутов согласования;
- подбор подходящего маршрута под конкретную сущность;
- ведение процесса от запуска до завершения;
- фиксацию решений, замечаний и комментариев;
- управление сроками и автосогласованием;
- формирование итогового результата;
- автоматическую архивацию завершённых процессов.

Модуль **не хранит** сами сущности — работает через **ссылку на сущность** (уникальный идентификатор, по которому модуль обращается к системе-владельцу за атрибутами).

### 1.2 Что входит в модуль

| Блок | Описание |
|---|---|
| Шаблоны маршрутов | Создание, версионирование, публикация, архивация |
| Подбор шаблона | По типу, подтипу и атрибутам сущности |
| Генерация маршрута | Из шаблона в конкретный маршрут |
| Управление процессом | Запуск, отзыв, возобновление, завершение |
| Этапы и итерации | Порядок, сроки, режимы, круги выполнения |
| Участники | Согласующие, подписанты, наблюдатели |
| Дополнительные согласующие | Рекомендации, замечания, комментарии |
| Решения | Согласовать, Согласовать с замечаниями, Отклонить |
| Замечания и комментарии | Полный жизненный цикл |
| Сроки | Расчёт, автосогласование, напоминания |
| Финальное решение | Только для единого процесса |
| Карта переходов | Настраиваемая, версионируется |
| Аудит и события | Для задач, уведомлений, аналитики |
| Архивация | Автоматическая архивация завершённых процессов |

### 1.3 Что не входит в модуль

| Блок | Кто отвечает |
|---|---|
| Хранение бизнес-сущностей | Система-владелец |
| Создание и доставка задач согласующим | Внешний модуль задач |
| Уведомления на почту и в личный кабинет | Внешний модуль уведомлений |
| Справочник сотрудников | Внешняя система |
| Справочник ролей | Внешняя система |
| Проверка полномочий | Внешняя система через адаптер |
| Замещения сотрудников (отпуск, больничный) | Внешняя система (модуль не содержит даже заготовки адаптера — убрано целиком, ADR-024) |
| Электронная подпись | Внешняя система |
| Бизнес-логика типов сущностей | Система-владелец |

## 2. Глоссарий

### 2.1 Предметная область

| Термин | Значение |
|---|---|
| **Сущность** | Документ, Перечень, Проектная документация и т.д. — объект, для которого запускается согласование |
| **Ссылка на сущность** | Уникальный идентификатор, по которому модуль обращается к системе-владельцу |
| **Снимок сущности** | Набор атрибутов сущности, передаваемый в модуль для подбора маршрута |
| **Тип сущности** | Категория сущности (например, «Документ») |
| **Подтип сущности** | Уточнение категории (например, «ПД» — проектная документация) |
| **Организация / Подразделение** | Структурная единица дерева организаций. Может быть как организация, так и её подразделение или филиал |
| **Процесс** | Экземпляр согласования конкретной сущности |
| **Маршрут** | Конкретный путь согласования с этапами и участниками для конкретной сущности |
| **Шаблон** | Типовое описание маршрута, многоразового использования |
| **Этап** | Один шаг маршрута, на котором один или несколько участников принимают решение |
| **Итерация** | Круг выполнения этапа |
| **Разрешённые этапы возврата** | Список этапов (из пройденных и текущего), на которые можно вернуться при отклонении текущего этапа (новый термин, см. §11.3) |
| **Участник** | Конкретный сотрудник, назначенный на этап |
| **Слот действующего лица** | Позиция участника в шаблоне, для которой могут быть заданы пользователь, роль или организация в произвольном составе |
| **Дополнительный согласующий** | Участник, который даёт рекомендацию, но не влияет на статус этапа |
| **Замечание** | Комментарий, возможно файл, требующий реакции (исправить или отклонить) |
| **Комментарий** | Информационное сообщение, не требующее реакции |
| **Ответственный** | Роль в едином процессе, принимающая финальное решение |
| **Ревизия документа** | Отдельный новый процесс для серьёзных изменений документа, связанный с предыдущим через общий идентификатор агрегата (новый термин, см. §11.7) |
| **Адаптер** | Программный интерфейс для интеграции модуля с внешней системой |
| **Архивация** | Автоматический перевод завершённого процесса в неизменяемое состояние |

## 3. Ключевые принципы работы

| Принцип | Описание |
|---|---|
| **Абстрактность** | Модуль не знает о типах сущностей и работает через ссылку на сущность |
| **Событийная модель** | Модуль не создаёт задачи и уведомления сам, а публикует события для внешних модулей |
| **Настраиваемая карта переходов** | Состояния и переходы хранятся как данные, не зашиты в код |
| **Фиксация версии при запуске** | Процесс при запуске фиксирует версию шаблона и настроек карты переходов |
| **Изоляция версий** | Старые версии шаблонов и карт переходов живут, пока есть активные процессы на них |
| **Аудит** | Каждое действие и изменение конфигурации фиксируется |
| **Автоматическая архивация** | Завершённые процессы архивируются автоматически через 180 дней |

## 4. Роли пользователей

| Роль | Действия |
|---|---|
| **Инициатор** | Создать процесс, редактировать маршрут, запустить (для стандартного процесса), отправить ответственному (для единого процесса), отозвать, выбрать целевой этап при возобновлении (§11.3), создать ревизию документа (§11.7) |
| **Ответственный** | Согласовать маршрут и принять финальное решение (только для единого процесса) |
| **Согласующий** | Согласовать, Согласовать с замечаниями, Отклонить, добавить дополнительного согласующего, замечания и комментарии |
| **Дополнительный согласующий** | Дать рекомендацию, оставить замечание или комментарий, добавить дочернего дополнительного согласующего (§9.3) |
| **Подписант** | Подписать, отклонить |
| **Наблюдатель** | Просмотр карточки процесса |
| **Администратор** | Управление шаблонами, картами переходов, публикация версий, восстановление процессов из архива |

**Убрано:** «запросить/продлить лимит итераций» — у инициатора и администратора соответственно. Лимита итераций больше не существует (см. §11.4, §16).

## 5. Типы процессов

### 5.1 Стандартный процесс (STANDARD)

**Что это:** классический процесс согласования с несколькими этапами и участниками.

**Характеристики:**

| Свойство | Описание |
|---|---|
| Этапы | Несколько, проходятся последовательно |
| Участники этапа | Один или несколько, работают параллельно или последовательно |
| Режим агрегации решений | По правилам внутри этапа (см. раздел 6) |
| Возврат на доработку | Есть — на любой из разрешённых для текущего этапа этапов (`allowedReturnStages`), включая сам текущий |
| Итерация этапа | Создаётся при каждой активации этапа, в том числе повторной |
| Итерация процесса | Вычисляемое представление для отображения (см. §11.6), не ограничивается лимитом |
| Ревизии документа | Возможны при включённом признаке `processIterationEnabled` (см. §7.8, §11.7) |
| Финальное решение | Нет |
| Итог процесса | Определяется **последним этапом**. До последнего этапа процесс доходит только после успешного согласования всех предыдущих |

**Поведение при отклонении:**

Отклонение на любом этапе переводит процесс в статус **На доработке**. Дальнейшее поведение не зависит от того, промежуточный это этап или последний, и не ограничено количеством кругов:

| Что делает инициатор | Что происходит |
|---|---|
| Обрабатывает замечания, нажимает «Возобновить» | Если у отклонённого этапа в `allowedReturnStages` больше одного варианта — модальное окно «На какой этап направить?» |
| Выбирает целевой этап = текущий (отклонённый) этап | Новая итерация текущего этапа; более ранние этапы не меняются |
| Выбирает целевой этап раньше текущего | Все этапы между целевым (не включительно) и текущим (включительно) получают статус **Отклонён** (терминальный, без повторного рассмотрения); целевой этап получает новую итерацию и активируется |
| Выбирает целевой этап = этап 1 | Фактический перезапуск всего маршрута — промежуточные этапы получают статус Отклонён, этап 1 — новую итерацию |

**Важно.** Стандартный процесс **не имеет статуса «Отклонён» на уровне процесса** — этот статус существует только на уровне этапа (для этапов, которые пропускаются при возврате на более ранний этап). Сам процесс завершается только в статусах Согласован, Согласован с замечаниями или архивируется; при возврате на доработку он временно находится в статусе **На доработке**. Лимита количества кругов согласования **не существует**.

### 5.2 Единый процесс (UNIFIED)

**Что это:** процесс, в котором все этапы проходятся последовательно, а итоговое решение принимает ответственный.

**Характеристики:**

| Свойство | Описание |
|---|---|
| Этапы | Несколько, проходятся последовательно |
| Участники этапа | Все параллельно |
| Влияние решений участников на движение | Нет (решения фиксируются) |
| Итерация этапа | Одна, невидимая пользователю |
| Ревизии документа | Не применимы — возврата на доработку нет |
| Ответственный | Обязателен |
| Финальное решение | Обязательно |
| Возврат на доработку | Нет |
| Срок финального решения | Нет |

**Поведение при финальном отклонении:**

Финальное решение «Отклонить» переводит процесс в статус **Отклонён** — это финальный, терминальный статус процесса. Других исходов у отклонения нет: возврата на доработку, повторных итераций или лимитов в едином процессе не существует. Если требуется повторное согласование той же сущности — запускается новый процесс (механизм ревизий документа, §11.7, доступен только для стандартного процесса).

**Особенности единого процесса:**
- Маршрут согласовывает и запускает ответственный, а не инициатор.
- Ответственный не может быть участником этапа.
- Ответственный может быть инициатором.
- Ответственный может быть назначен несколькими ролями.
- Финальное решение **неизменяемо**.
- Дополнительные согласующие на финальное решение **не назначаются**.

### 5.3 Сравнительная таблица

| Характеристика | Стандартный | Единый |
|---|---|---|
| Итерации этапа | Много | Одна невидимая |
| Итерации процесса | Вычисляемое представление, без лимита | Не применимо (нет возврата) |
| Режим агрегации | Да | Нет |
| Порядок работы | Да | Нет (всегда параллельно) |
| Возврат на доработку | Есть | Нет |
| Возобновление | Есть | Нет |
| Ответственный | Нет | Да |
| Финальное решение | Нет | Да |
| Согласование маршрута ответственным | Нет | Да |
| Срок финального решения | — | Нет |
| Ревизии документа | По флагу `processIterationEnabled` | Нет |
| Отзыв инициатором | До завершения | До финала |
| Итог | Определяется последним этапом | Определяется финальным решением ответственного |

## 6. Режимы агрегации решений

Применяются только для стандартного процесса.

### 6.1 Описание режимов

| Режим | Русское название | Поведение |
|---|---|---|
| **AND** | «И» | Ждём всех, отказ не прерывает. Этап закрывается, когда все приняли решение |
| **ANY_APPROVE** | «Первый согласовавший» | Первый согласовавший закрывает этап |
| **ANY_REJECT** | «Первый отклонивший» | Первый отклонивший отправляет этап на доработку |
| **ANY_DECISION** | «Первое решение» | Первое любое решение закрывает этап или отправляет на доработку |
| **FIRST_REJECT_FAIL_FAST** | «Первый отказ прерывает» | Ждём всех, но первый отказ прерывает ожидание |

### 6.2 Ключевое правило

**Этап не может быть закрыт с итогом «Отклонён»**, если инициатор при возобновлении направляет его на новую итерацию этого же этапа. В этом случае он получает статус **На доработке**.

**Этап закрывается со статусом «Отклонён»** только тогда, когда при возобновлении инициатор выбирает более ранний целевой этап (см. §5.1, §11.3) — то есть когда этот этап пропускается без повторного рассмотрения. Понятия «лимит итераций процесса» больше не существует — оно не участвует в этом правиле.

### 6.3 Примеры

**Исходные данные:** этап «Проверка», участники — Иванов, Петров, Сидоров.

#### Пример 1 — Режим «И» (AND), промежуточный этап

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | Ждём остальных |
| t2 | Петров → Отклонено | Ждём Сидорова |
| t3 | Сидоров → Согласовано | Этап **не закрыт** → статус **На доработке** |
| t4 | Инициатор исправляет замечания | — |
| t5 | **Новая итерация этапа** | Участники те же |

**Если инициатор при возобновлении выбирает более ранний целевой этап (а не повторяет этот же этап):**

| t3 | Сидоров → Согласовано | Этап всё равно сначала получает статус **На доработке** (правило §6.2 не зависит от позиции этапа в маршруте) |
| — | Инициатор выбирает целевой этап раньше текущего и возобновляет процесс | Этот этап получает статус **Отклонён** — терминально, без повторного рассмотрения (см. §5.1, §11.3) |

#### Пример 2 — Режим «И» (AND), все согласовали

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | Ждём остальных |
| t2 | Петров → Согласовано | Ждём Сидорова |
| t3 | Сидоров → Согласовано | **Этап закрыт. Итог: Согласовано** |

#### Пример 3 — Режим «Первый согласовавший» (ANY_APPROVE)

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | **Этап закрыт. Итог: Согласовано** |
| t2 | Петров → Отклонено | Игнорируется |
| t3 | Сидоров → Отклонено | Игнорируется |

**Логика:** достаточно одного согласования. Отказы остальных не учитываются.

#### Пример 4 — Режим «Первый отклонивший» (ANY_REJECT), промежуточный этап

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | Ждём остальных |
| t2 | Петров → Отклонено | Этап **не закрыт** → статус **На доработке** |
| t3 | — | — |
| t4 | Инициатор исправляет замечания | — |
| t5 | **Новая итерация этапа** | — |

**Если инициатор при возобновлении выбирает более ранний целевой этап:**

| t2 | Петров → Отклонено | Этап всё равно получает статус **На доработке**; **Отклонён** он получит только после того, как инициатор выберет более ранний целевой этап при возобновлении (§11.3) |

#### Пример 5 — Режим «Первое решение» (ANY_DECISION)

**Сценарий А: первым отклонил, промежуточный этап**

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Петров → Отклонено | Этап **не закрыт** → статус **На доработке** |
| t2 | Инициатор исправляет замечания | — |
| t3 | **Новая итерация этапа** | — |

**Сценарий Б: первым согласовал**

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Петров → Согласовано | **Этап закрыт. Итог: Согласовано** |

#### Пример 6 — Режим «Первый отказ прерывает» (FIRST_REJECT_FAIL_FAST)

**Сценарий А: кто-то отклонил, промежуточный этап**

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | Ждём остальных |
| t2 | Петров → Отклонено | Этап **не закрыт** → статус **На доработке** |
| t3 | Инициатор исправляет замечания | — |
| t4 | **Новая итерация этапа** | — |

**Сценарий Б: никто не отклонил**

| Момент | Событие | Реакция системы |
|---|---|---|
| t1 | Иванов → Согласовано | Ждём остальных |
| t2 | Петров → Согласовано | Ждём Сидорова |
| t3 | Сидоров → Согласовано | **Этап закрыт. Итог: Согласовано** |

### 6.4 Сводная таблица поведения

| Режим | Если кто-то отклонил | Если все согласовали |
|---|---|---|
| AND | Ждём всех → На доработке → новая итерация этапа | Этап закрыт: Согласовано |
| ANY_APPROVE | Игнорируется, если уже есть согласование | Этап закрыт при первом согласовании |
| ANY_REJECT | Первый отказ → На доработке → новая итерация этапа | Этап закрыт: Согласовано |
| ANY_DECISION | Если отказ первый → На доработке | Если согласование первое → этап закрыт |
| FIRST_REJECT_FAIL_FAST | Первый отказ → На доработке | Ждём всех → этап закрыт |

### 6.5 Порядок работы участников

| Режим | Русское название | Описание |
|---|---|---|
| **Parallel** | Параллельно | Все участники получают задачи одновременно |
| **Sequential** | Последовательно | По очереди: следующий получает задачу только после решения предыдущего |

## 7. Шаблоны маршрутов

### 7.1 Структура шаблона

Шаблон содержит:
- тип процесса (стандартный или единый);
- правила применимости;
- набор этапов с порядком следования;
- слоты действующих лиц;
- флаги обязательности и редактирования;
- признак `processIterationEnabled` (ревизии документа, см. §7.8).

### 7.2 Жизненный цикл шаблона

| Состояние (английское название) | Русское название | Описание |
|---|---|---|
| **Draft** | Черновик | Шаблон создаётся и редактируется |
| **Published** | Опубликован | Шаблон доступен для использования |
| **Deprecated** | Устаревший | Шаблон не применяется для новых процессов, старые продолжают работать |
| **Archived** | Архивирован | Шаблон выведен из оборота |

### 7.3 Правила версионирования

- Опубликованный шаблон **не редактируется**. Изменения — только через новую версию.
- Новая версия создаётся через функцию «Форк» (создание копии с новым номером версии).
- Версии — глобальные (единая нумерация).
- Удаление версии разрешено только при отсутствии активных процессов на ней.

### 7.4 Правила применимости

Шаблон применяется к сущности, если совпадают:
- тип сущности (например, «Документ»);
- подтип сущности (например, «ПД» — проектная документация);
- значения атрибутов (например, сумма > 1 млн рублей).

**Примеры типов и подтипов:**

| Тип сущности | Пример подтипа |
|---|---|
| Документ | Договор поставки |
| Документ | Служебная записка |
| Перечень | Перечень замечаний |
| Проектная документация (ПД) | Раздел АР |
| Проектная документация (ПД) | Раздел КЖ |

### 7.5 Атрибуты этапа в шаблоне

| Атрибут | Описание |
|---|---|
| Порядковый номер | Позиция этапа в маршруте |
| Наименование | Опциональное название этапа |
| Описание | Опциональное описание |
| Тип этапа | Согласование / Подписание / Утверждение |
| Срок | В рабочих днях |
| Режим агрегации | Только для стандартного процесса |
| Порядок работы участников | Только для стандартного процесса |
| Обязательность этапа | Нельзя ли удалить этап из маршрута |
| Обязательность порядка | Нельзя ли переместить этап |
| Разрешённые этапы возврата (`allowedReturnStages`) | На какие этапы можно вернуться при отклонении этого этапа |
| Слоты действующих лиц | Список слотов |

### 7.6 Обязательность и порядок

| Правило | Описание |
|---|---|
| Обязательный этап | Нельзя удалить из маршрута |
| Обязательный этап без слотов | Блокирует запуск процесса |
| Обязательный по порядку этап №N | Все этапы до N тоже обязательны по порядку |
| Признак обязательности порядка | Фиксация среди всех этапов, не только обязательных по порядку |

**Пример:** если этап №3 обязателен по порядку, то этапы №1 и №2 тоже нельзя удалять или перемещать. Иначе шаблон считается некорректным.

### 7.7 Сроки в шаблоне

**Сроки задаются только в днях (рабочих).**

| Ситуация | Поведение |
|---|---|
| Срок задан в шаблоне | Переносится в маршрут автоматически |
| Срок не задан | Инициатор указывает вручную при запуске |
| Срок не задан и не указан | Запуск процесса блокируется |
| Срок меньше или равен нулю | Ошибка валидации шаблона |

### 7.8 Признак `processIterationEnabled` (ревизии документа)

**Важно: смысл этого признака изменился по сравнению с более ранней версией бизнес-контекста.** Раньше он включал/выключал лимит повторных запусков всего маршрута. Лимита итераций процесса в текущей модели **не существует вовсе** — возврат на доработку работает всегда, через точечный выбор целевого этапа (`allowedReturnStages`, см. §5.1, §11), независимо от этого признака.

Сейчас `processIterationEnabled` управляет только **ревизиями документа** (см. §11.7):

| Значение | Что разрешено |
|---|---|
| `false` | Только правки в рамках одного и того же процесса/документа — без создания отдельной ревизии |
| `true` | Инициатор может создать отдельную **ревизию документа** — новый процесс, связанный с предыдущим через `documentAggregateId` |

Для единого процесса (UNIFIED) ревизии не применяются (см. §5.2) независимо от значения этого признака.

## 8. Слоты действующих лиц

### 8.1 Определение

**Слот действующего лица** — позиция участника в шаблоне, для которой могут быть заданы пользователь, роль или организация в произвольном составе.

В одном слоте может быть задано:
- конкретный пользователь (опционально);
- организация или подразделение (опционально);
- допустимые роли (опционально, может быть несколько);
- флаги редактирования.

### 8.2 Атрибуты слота

| Атрибут | Описание |
|---|---|
| Порядковый номер | Позиция слота в этапе |
| Пользователь | Конкретный сотрудник |
| Организация | Организация или подразделение — область поиска пользователя |
| Допустимые роли | Список ролей, которые могут занимать этот слот |
| Обязательность | Должен ли слот быть заполнен для запуска |
| Можно заменить пользователя | Признак |
| Можно заменить организацию | Признак |
| Можно удалить слот | Признак |
| Предустановленные доп. согласующие | Список доп. согласующих из шаблона |

### 8.3 Логика подбора пользователя

| Ситуация | Поведение |
|---|---|
| Задан конкретный пользователь | Используется он |
| Задан пользователь и роли | Используется пользователь, роли — ограничение для замены |
| Заданы только роли | Интерфейс запрашивает подбор пользователя через адаптер |
| Задана организация и роли | Поиск пользователя в рамках организации |
| Ничего не задано, слот необязательный | Слот может быть пустым |
| Ничего не задано, слот обязательный | Ошибка шаблона |

### 8.4 Флаги редактирования

| Замена пользователя | Замена организации | Удаление слота | Поведение |
|---|---|---|---|
| Да | Да | Да | Полная свобода |
| Да | Да | Нет | Замена пользователя и организации разрешена, слот не удаляется |
| Да | Нет | Да | Замена пользователя, организация неизменна, слот можно удалить |
| Да | Нет | Нет | Замена пользователя, организация и слот неизменны |
| Нет | Да | Любое | Некорректный шаблон |
| Нет | Нет | Да | Слот только удаляется |
| Нет | Нет | Нет | Полностью зафиксирован |

### 8.5 Правило валидации флагов

Если разрешена замена организации, то должна быть разрешена и замена пользователя. Обратное неверно: пользователя можно менять без изменения организации.

### 8.6 Смена организации

| Шаг | Что происходит |
|---|---|
| 1 | Интерфейс проверяет, разрешена ли смена организации |
| 2 | Интерфейс сбрасывает текущего пользователя |
| 3 | Интерфейс запрашивает подбор нового пользователя через адаптер |
| 4 | Если пользователь не найден — интерфейс предлагает выбрать вручную |
| 5 | Сохраняются новый пользователь и новая организация |

**Модуль не блокирует** замену пользователя по ролям и организациям. Проверка соответствия пользователя ролям и организации — ответственность интерфейса.

### 8.7 Разделение ответственности

| Задача | Кто отвечает |
|---|---|
| Хранение пользователя, организации, ролей, флагов | Модуль |
| Проверка обязательности и флагов | Модуль |
| Подбор пользователя по ролям | Интерфейс через адаптер |
| Проверка соответствия пользователя ролям | Интерфейс (опционально) |
| Актуальность справочников ролей и организаций | Внешние системы |

## 9. Дополнительные согласующие

### 9.1 Назначение

**Дополнительный согласующий** — участник процесса, который:
- даёт рекомендацию («Согласовать» или «Отклонить»);
- может оставить замечание или комментарий;
- **не влияет** на статус этапа.

### 9.2 Атрибуты

| Атрибут | Описание |
|---|---|
| Пользователь | Сотрудник |
| Организация | Организация или подразделение |
| Кто назначил | Из шаблона / инициатор / основной согласующий / другой доп. согласующий (иерархия, см. §9.3) |
| Родитель в иерархии | Ссылка на доп. согласующего, который назначил (если назначен не из шаблона/инициатором/основным) |
| Уровень в иерархии | Вычисляется: уровень родителя + 1, либо 1 при отсутствии родителя |
| Срок | Дата и время для рекомендации |
| Смещение срока | 0 / −3 часа / −8 часов от срока основного согласующего |
| Статус | Текущее состояние |
| Рекомендация | Согласовать или Отклонить |
| Можно заменить пользователя | Признак |
| Можно заменить организацию | Признак |
| Можно удалить | Признак |

### 9.3 Правила

| Правило | Значение |
|---|---|
| Влияние на статус этапа | Нет. Рекомендация — чисто информационная для основного согласующего |
| Рекомендация | Согласовать или Отклонить |
| Срок | Не позднее срока основного согласующего |
| Смещение срока | 0 / −3 часа / −8 часов |
| Кто назначает | Из шаблона / инициатор / основной согласующий (уровень 1) / любой доп. согласующий — дочернего себе (уровень 2+) |
| Может назначать других доп. согласующих | **Да, без ограничения глубины иерархии** (изменено — раньше было «Нет») |
| Видит других доп. согласующих | **Да, всех — по всему процессу**, не только в рамках текущей итерации (изменено) |
| Видит основных согласующих | **Да** (изменено — раньше был изолирован) |
| Удаление во время работы | Запрещено |
| Удаление в статусах Отозван / На доработке | Разрешено |
| Основной может удалить доп. согласующего, назначенного инициатором | Да |
| Ограничение количества | **Не ограничено** (изменено — раньше было 10 человек на одного основного) |
| Отображение в листе согласования | Да |
| Внешние подрядчики | Обычные пользователи с учётной записью |

### 9.4 Расширение

- Основной согласующий **всегда** может добавить дополнительного согласующего к себе.
- Флаги редактирования применяются только к **предустановленным** доп. согласующим (заданным в шаблоне).
- Иерархия неограниченной глубины: **любой** доп. согласующий может добавить дочернего доп. согласующего себе — не только основной участник (изменено).
- Динамически добавленные доп. согласующие — под контролем того, кто их добавил.

### 9.5 Клонирование при новой итерации

Клонирование зависит от того, кто назначил доп. согласующего:

| Кто назначил | Клонируется при новой итерации этапа |
|---|---|
| Из шаблона | Да |
| Инициатором | Да |
| Основным согласующим | Нет |
| Другим доп. согласующим (дочерний) | Нет |

При клонировании родителя (назначенного из шаблона или инициатором) его дочерние доп. согласующие клонируются вместе с ним, с привязкой к новому родителю.

## 10. Маршрут процесса

### 10.1 Что такое маршрут

**Маршрут** — конкретная реализация шаблона для конкретной сущности. В маршруте:
- роли заменены на конкретных пользователей;
- сроки пересчитаны в даты;
- зафиксирована организация для каждого участника.

### 10.2 Что можно редактировать до запуска

| Элемент | Условие |
|---|---|
| Замена пользователя в слоте | Разрешено флагом |
| Замена организации | Разрешено флагом |
| Удаление слота | Разрешено флагом и необязательностью |
| Добавление дополнительного согласующего | Всегда |
| Удаление дополнительного согласующего | Разрешено флагом |
| Добавить или удалить этап | Если этап необязательный |
| Переместить этап | Если порядок не обязателен |
| Изменить название этапа | Да |
| Изменить срок этапа | Да |
| Изменить режим агрегации | Да (для стандартного процесса) |
| Изменить порядок работы участников | Да (для стандартного процесса) |

### 10.3 Что нельзя редактировать

| Элемент | Причина |
|---|---|
| Тип процесса | Фиксирован шаблоном |
| Обязательные этапы | Обязательность задана в шаблоне |
| Обязательный порядок | Обязательность задана в шаблоне |
| Обязательные слоты без участников | Блокирует запуск |

### 10.4 Редактирование после запуска

| Состояние | Что можно |
|---|---|
| Этапы, взятые в работу | Не изменяются |
| Этапы, не взятые в работу | Редактируются, если процесс не дошёл до этапа подписания |
| После отзыва | Маршрут снова доступен для редактирования |
| После отклонения на этапе | Маршрут снова доступен для редактирования |
| Во время новой итерации этапа при возврате | Маршрут доступен для редактирования |

## 11. Итерации

### 11.1 Модель

В отличие от более ранней версии бизнес-контекста, здесь **нет двух независимых уровней итераций с лимитом на верхнем**. Физически хранится только **итерация этапа**. «Итерация процесса» — это не отдельная сущность и не ограниченный ресурс, а **вычисляемое представление** для отображения (см. §11.6).

Повторное прохождение маршрута (в старой терминологии — «итерация процесса») достигается не через отдельный лимитируемый механизм, а через обычный **возврат на этап** — в том числе на этап 1, если инициатор выбирает его как целевой (см. §11.3, §5.1).

### 11.2 Итерация этапа

**Когда создаётся:** при каждой активации этапа — как при обычном переходе к следующему этапу, так и при возврате на уже пройденный этап.

**Что происходит:**
- Участники клонируются (либо создаются заново, если этап активируется впервые).
- Дополнительные согласующие клонируются по правилам §9.5 (зависит от того, кто их назначил).
- Замечания не клонируются — живут в истории с привязкой к своей итерации.
- Срок пересчитывается.
- Создаётся новый круг выполнения этапа (счётчик итерации этого этапа увеличивается на 1).

### 11.3 Возврат при отклонении

Заменяет прежнюю модель «повторить текущий этап или перезапустить весь маршрут с этапа №1». Теперь у каждого этапа в шаблоне задан список **разрешённых этапов возврата** (`allowedReturnStages`) — этапы (из уже пройденных и текущего), на которые можно вернуться при отклонении на этом этапе.

**Правило:** доступны только этапы с порядковым номером ≤ текущего. Дублей нет. Работает всегда, без переключателя и без ограничения по количеству кругов.

**Что происходит при возврате:**

| Целевой этап | Результат |
|---|---|
| = текущий (отклонённый) этап | Новая итерация текущего этапа; более ранние этапы не меняются |
| Раньше текущего (в т.ч. этап 1) | Все этапы от целевого (не включая) до текущего (включительно) получают статус **Отклонён** (терминальный); целевой этап получает новую итерацию и активируется; этапы до целевого не меняются |

**Кто выбирает целевой этап:** только инициатор, и только в момент возобновления процесса (после обработки замечаний). Если у отклонённого этапа в `allowedReturnStages` больше одного варианта — интерфейс показывает модальное окно выбора.

**Условие возобновления:** нет активных (Действующее / В работе) замечаний.

### 11.4 Лимит итераций

**Убран целиком.** Круг согласования (в старом смысле — повторный проход всего маршрута) можно повторять неограниченное количество раз; отдельного счётчика, лимита или процедуры продления (см. прежний §16) больше не существует.

### 11.5 Отображение в листе согласования

Лист согласования отображается в виде дерева — так же, как раньше:

```
Итерация маршрута 1
├── Этап 1
│   ├── Согласующий 1
│   ├── Согласующий 2
│   └── Доп. согласующий 1
└── Этап 2
    └── Согласующий 3

Итерация маршрута 2
├── Этап 1
│   └── ...
└── Этап 2
    └── ...
```

Группировка по «итерации маршрута» — это группировка по вычисленному значению из §11.6, а не по отдельно хранимой сущности.

### 11.6 Вычисление «итерации процесса»

**Не хранится физически.**

**Формула:**
```
processIteration = max(stageIteration.iterationIdx по всем этапам процесса)
```

**Зачем:** только для группировки и отображения в UI (лист согласования, §11.5).

### 11.7 Ревизии документа

**Что это.** Отдельный механизм для случаев, когда изменения в документе настолько серьёзные, что их нельзя оформить как обычную доработку в рамках того же процесса. Ранее в бизнес-контексте не описывался — расхождение зафиксировано в `claude/gap-analysis-business-context-vs-architecture.md`.

**Условие применения:** только для стандартного процесса (STANDARD), только если у шаблона включён признак `processIterationEnabled` (см. §7.8 — смысл этого признака изменился, теперь это переключатель именно ревизий, а не лимита итераций).

**Как это работает:**
1. Инициатор решает, что замечания серьёзные и требуют новой ревизии документа, а не доработки в рамках текущего процесса.
2. Создаёт новую ревизию, указывая метку ревизии (свободная строка: «Изм. 1», «Доп. 2», «ТР. 3» и т.п.) и решает, прерывать ли предыдущий процесс.
3. Создаётся **новый процесс** (не итерация существующего), связанный с предыдущим через общий идентификатор агрегата документа (единый для всех ревизий одного документа) и ссылку на непосредственно предыдущий процесс.
4. Если предыдущий процесс прерывается — он переходит в статус Отозван; если нет — оба процесса могут идти параллельно.
5. Публикуется событие `approval.process.revision-created`.

**Ограничения:** метка ревизии должна быть уникальна в рамках одного документа (агрегата); при `processIterationEnabled = false` создание ревизий запрещено.

## 12. Замечания и комментарии

### 12.1 Разделение понятий

| Понятие | Описание | Требует реакции |
|---|---|---|
| **Комментарий** | Информационное сообщение | Нет |
| **Замечание** | Комментарий, возможно файл, требующий реакции (исправить или отклонить) | Да |

### 12.2 Кто создаёт

| Источник | Может создавать замечания | Может создавать комментарии |
|---|---|---|
| Основной согласующий | Да (сразу Действующее) | Да |
| Дополнительный согласующий | Да (статус Предложено) | Да |
| Инициатор | Нет | Да |
| Ответственный (единый процесс) | Нет | Да |

### 12.3 Статусы замечания

| Статус (английское название) | Русское название | Описание |
|---|---|---|
| **Proposed** | Предложено | Создано доп. согласующим, ожидает решения основного |
| **Active** | Действующее | Требует реакции инициатора |
| **InProgress** | В работе | Инициатор взял в работу |
| **NotRequired** | Не требуется | Не требует реакции |
| **AutoProcessed** | Авто-обработано | Обработано автоматически при закрытии этапа |
| **Resolved** | Исправлено | Инициатор исправил |
| **Rejected** | Отклонено | Инициатор отклонил с обоснованием |
| **Closed** | Закрыто | Закрыто при согласовании |

### 12.4 Жизненный цикл замечания

```
Предложено
├──→ Действующее
│       ├──→ Исправлено
│       ├──→ В работе
│       │       ├──→ Исправлено
│       │       └──→ Отклонено
│       ├──→ Отклонено
│       └──→ Закрыто (при Согласовать / Согласовать с замечаниями)
├──→ Не требуется
└──→ Авто-обработано
```

**Терминальные статусы:** Исправлено, Отклонено, Не требуется, Авто-обработано, Закрыто.

**Блокируют возобновление процесса:** Действующее, В работе.

### 12.5 Правила

| Правило | Значение |
|---|---|
| Замечание основного согласующего | Сразу Действующее |
| Замечание доп. согласующего | Предложено, ожидает решения основного |
| Основной решает по Предложено | Перевести в Действующее или Не требуется |
| Основной может активировать замечание после своего согласования | Нет |
| Необработанные замечания при закрытии этапа | Авто-обработано |
| Возврат из Не требуется в Действующее | Нет |
| Вложенность замечаний | Нет |
| Инициатор видит Предложено | Нет |
| Инициатор видит Действующее | Да |
| Инициатор исправляет Действующее | → Исправлено |
| Инициатор отклоняет Действующее | → Отклонено (с обоснованием) |
| Инициатор комментирует Исправлено | Да |
| Возобновление процесса | Только если все замечания обработаны |
| Согласовать | Все Действующее автора → Закрыто |
| Согласовать с замечаниями | Замечания считаются несущественными → Закрыто |
| Отклонить | Действующее уходят инициатору |
| Клонирование при новой итерации | Нет |
| Лист согласования | Не включает замечания |
| Отчёт | Включает, в том числе Авто-обработанные |
| Сортировка | По этапу, итерации, автору |

### 12.6 Комментарии

- Могут быть вложенными (ответ на комментарий).
- Не влияют на процесс.
- Отображаются в отдельном инструменте вместе с замечаниями.
- Могут содержать файлы.

## 13. Сроки и автосогласование

### 13.1 Сроки

| Тип срока | Описание |
|---|---|
| Срок этапа | От старта этапа до планового завершения |
| Срок итерации | Часть срока этапа (не отдельный срок) |
| Срок доп. согласующего | Не позднее срока основного согласующего |
| Срок финального решения (единый процесс) | Отсутствует |

**Сроки в шаблоне задаются только в днях (рабочих).**

### 13.2 Автосогласование

**Что это:** автоматическое согласование участника, который не принял решение до истечения срока этапа.

**Правила:**
- Срабатывает по истечении срока этапа.
- Незавершившие получают статус **Автосогласовано**.
- Для единого процесса — то же самое.
- Финальное решение единого процесса **не покрывается** автосогласованием.

### 14.1 Отзыв стандартного процесса

|---|---|

| Когда | В любой момент до завершения |
| Результат | Процесс в статусе Отозван |
| Из Отозван | В Черновик (для доработки) или Архив |
| Активные задачи | Прекращаются |

### 14.2 Отзыв единого процесса

| Правило | Значение |
|---|---|
| Кто | Инициатор |
| Когда | В любой момент до финального решения |
| Из состояний | Черновик, Ожидает согласования маршрута ответственным, В процессе |
| Результат | Процесс в статусе Отозван |

### 14.3 Возобновление стандартного процесса

| Правило | Значение |
|---|---|
| Триггер | Кнопка «Возобновить» |
| Условие | Все замечания обработаны (нет Действующее и В работе) |
| Целевой этап | Инициатор выбирает из `allowedReturnStages` отклонённого этапа (модальное окно, если вариантов больше одного) — см. §11.3 |
| Если целевой этап = отклонённый этап | Новая итерация только этого этапа; более ранние этапы не меняются |
| Если целевой этап раньше отклонённого (в т.ч. этап 1) | Этапы между целевым и отклонённым получают статус Отклонён; целевой этап получает новую итерацию и активируется |

**Убрано:** прежняя развилка «повторить текущий этап или перезапустить с 1-го этапа при включённой итерационности процесса» — заменена единым механизмом точечного возврата (§11.3), который не зависит от какого-либо переключателя.

### 14.4 Возобновление единого процесса

Возобновления как отдельной операции **нет**. После отзыва процесс возвращается в Черновик для полного перезапуска.

## 15. Финальное решение (единый процесс)

### 15.1 Правила

| Правило | Значение |
|---|---|
| Кто принимает | Ответственный |
| Когда | После прохождения всех этапов |
| Срок | Нет |
| Изменение | Запрещено |
| Доп. согласующие | Не назначаются |
| Влияние решений участников | Нет |

### 15.2 Возможные решения и итоги

| Решение | Итог процесса |
|---|---|
| Согласовать | Согласован |
| Согласовать с замечаниями | Согласован с замечаниями |
| Отклонить | **Отклонён** — терминальный статус процесса |

**Убрано:** развилка «с итерационностью / без итерационности, лимит достигнут / не достигнут» — в едином процессе нет ни возврата на доработку, ни повторных итераций, ни лимитов; отклонение всегда терминально (см. §5.2).

## 16. Продление лимита итераций

**Убрано целиком.** Лимита итераций процесса больше не существует (см. §11.4), поэтому и механизм его продления администратором стал неприменим. Возврат на доработку работает без ограничения количества кругов через точечный выбор целевого этапа (§11.3) — согласовывать продление с администратором больше не требуется.

## 17. Напоминания и просрочки

### 17.1 Область применения

Напоминания инициатору, если процесс долго находится в состоянии **На доработке** (после отклонения на этапе).

**Убрано:** упоминание статуса «Ожидает новой итерации процесса» — такого статуса в текущей модели не существует (см. §11.4, §19.1).

### 17.2 Правила

| Правило | Значение |
|---|---|
| Тип механизма | Напоминания инициатору |
| Автоматические переходы | Отсутствуют |
| Периодичность | Настраивается администратором |
| Канал доставки | Внешний модуль уведомлений |

### 17.3 Что НЕ происходит

- Процесс не переводится автоматически в Отклонён.
- Процесс не архивируется автоматически (до истечения 180 дней).
- Никаких принудительных действий.

**Примечание (обновлено 2026-09-18).** Настраиваемость периодичности напоминаний (§17.2) теперь описана технически: **ADR-027** (`11_adr.md` §29) вводит глобальную настройку — singleton-таблицу `notification_settings` (`08_db_schema.md` §22) и эндпоинты `GET`/`PUT /admin/notification-settings` (`07_api_contract.md` §26), доступные администратору. `ReminderJob` (`10_architecture.md` §11.1) читает периодичность из этой таблицы при каждом запуске — изменение вступает в силу без релиза. Дизайн минимальный: настройка глобальная, без гранулярности по шаблонам или типам процессов (выбор пользователя, см. ADR-027 §29.3). Ранее этот пункт был зафиксирован как открытый пробел в `claude/gap-analysis-business-context-vs-architecture.md` — там же теперь отмечено его закрытие.

## 18. Архивация процессов

### 18.1 Общее описание

**Архивация** — автоматический перевод завершённого процесса в неизменяемое состояние, в котором он остаётся доступным для просмотра, экспорта и аудита, но не может быть изменён или возобновлён.

**Только автоматическая архивация.** Ручная архивация не предусмотрена.

### 18.2 Когда происходит

**Триггер:** истечение **180 дней** с момента завершения процесса.

**Что считается завершением:**

| Состояние | Считается завершением |
|---|---|
| Согласован | Да |
| Согласован с замечаниями | Да |
| Отклонён | Да |
| Отозван | Да |

### 18.3 Алгоритм

| Шаг | Что происходит |
|---|---|
| 1 | Процесс достиг финального состояния |
| 2 | Фиксируется дата завершения |
| 3 | Ежедневная проверка: прошло ≥ 180 дней |
| 4 | Процесс → Архивирован |
| 5 | Событие `approval.process.auto-archived` |
| 6 | Read-only |
| 7 | Аудит |

**Уведомления инициатору не отправляются.**

### 18.4 Что происходит при архивации

| Область | Что меняется |
|---|---|
| Статус процесса | → Архивирован |
| Активные задачи | Отзываются |
| События | Публикуется `approval.process.auto-archived` |
| Доступ на изменение | Запрещён |
| Доступ на просмотр | Сохраняется |
| Доступ на экспорт | Сохраняется |
| Данные | Не удаляются |
| Отображение | В реестре Архив |
| Фильтры | Исключается из активных списков |

### 18.5 Что доступно в архиве

| Действие | Доступно |
|---|---|
| Просмотр карточки процесса | Да |
| Просмотр истории решений | Да |
| Просмотр замечаний и комментариев | Да |
| Просмотр листа согласования | Да |
| Экспорт листа согласования | Да |
| Экспорт отчёта по замечаниям | Да |
| Восстановление администратором | Да |
| Изменение | Нет |
| Возобновление | Нет |
| Новая итерация | Нет |
| Отзыв | Нет |

### 18.6 Срок хранения

**Бессрочно.** Удаление процессов из архива не предусмотрено.

### 18.7 Восстановление из архива

| Правило | Значение |
|---|---|
| Кто может восстановить | Только администратор |
| Когда | В любой момент |
| В какое состояние | В то, из которого архивировали |
| Что дальше | Процесс снова живёт по обычным правилам и архивируется через 180 дней после завершения |
| Аудит | Каждое восстановление фиксируется |

**Если после восстановления инициатор ничего не делает** — процесс снова архивируется через 180 дней после завершения.

### 18.8 Отображение в реестрах

**Активный реестр:**
- Черновик
- Ожидает согласования маршрута
- В процессе
- На доработке
- Ожидает финального решения
- Отозван

**Архивный реестр:**
- Архивирован

### 18.9 События архивации

| Событие | Когда |
|---|---|
| `approval.process.auto-archived` | Процесс архивирован автоматически |
| `approval.process.restored` | Процесс восстановлен администратором |

### 18.10 Настройки архивации

```
ArchiveSettings
├── autoArchiveEnabled: Boolean   // включена
└── autoArchiveDays: Int           // 180
```

**Только глобально.**

## 20. Карты переходов

### 20.1 Что это

**Карта переходов** — набор правил, определяющих:
- какие состояния есть у каждой сущности;
- какие переходы между состояниями возможны;
- при каких условиях переход разрешён;
- какие действия выполняются при переходе;
- какие события публикуются.

### 20.2 Принципы

| Принцип | Описание |
|---|---|
| Настраиваемость | Карта переходов — данные, а не код |
| Версионирование | Каждая версия имеет номер |
| Публикация | Только администратором |
| Изоляция версий | Активные процессы работают на своей версии |
| Аудит | Каждое изменение фиксируется |

### 20.3 Переходы процесса STANDARD

| Откуда | Куда | Триггер | Роль |
|---|---|---|---|
| Черновик | В процессе | Запуск процесса | Инициатор |
| В процессе | На доработке | Отклонение на любом этапе | Система |
| На доработке | В процессе | Возобновление — активация выбранного целевого этапа (§11.3) | Инициатор |
| В процессе | Согласован | Последний этап согласован | Система |
| В процессе | Согласован с замечаниями | Последний этап согласован с замечаниями | Система |
| В процессе, На доработке | Отозван | Отзыв | Инициатор |
| Отозван | Черновик | Взятие в работу | Инициатор |
| Согласован, Согласован с замечаниями, Отозван | Архивирован | Автоархивация (180 дней) | Система |
| Архивирован | Предыдущий статус | Восстановление | Администратор |

**Убрано:** переходы, связанные со статусом «Ожидает новой итерации» и лимитом итераций — такого разветвления больше нет. Возобновление всегда ведёт в «В процессе», независимо от того, на какой этап вернулся инициатор.

### 20.4 Переходы процесса UNIFIED

| Откуда | Куда | Триггер | Роль |
|---|---|---|---|
| Черновик | Ожидает согласования маршрута | Отправка маршрута | Инициатор |
| Ожидает согласования маршрута | В процессе | Согласование маршрута | Ответственный |
| Ожидает согласования маршрута | Черновик | Отклонение маршрута | Ответственный |
| В процессе | Ожидает финального решения | Все этапы пройдены | Система |
| Ожидает финального решения | Согласован | Финальное решение «Согласовать» | Ответственный |
| Ожидает финального решения | Согласован с замечаниями | Финальное решение «Согласовать с замечаниями» | Ответственный |
| Ожидает финального решения | **Отклонён** | Финальное решение «Отклонить» | Ответственный |
| Ожидает согласования маршрута, В процессе | Отозван | Отзыв | Инициатор |
| Отозван | Черновик | Взятие в работу | Инициатор |
| Согласован, Согласован с замечаниями, Отклонён, Отозван | Архивирован | Автоархивация | Система |
| Архивирован | Предыдущий статус | Восстановление | Администратор |

**Убрано:** переход в «Ожидает новой итерации» и развилка по лимиту итераций при отклонении финального решения — в едином процессе отклонение всегда и сразу ведёт в терминальный статус «Отклонён», без исключений.

### 20.5 Переходы этапа STANDARD

| Откуда | Куда | Триггер | Условие |
|---|---|---|---|
| Ожидает | Активен | Активация | Предыдущий согласован (или выбран как целевой при возврате) |
| Активен | Согласован | Все согласовали | По режиму агрегации |
| Активен | Согласован с замечаниями | Все согласовали с замечаниями | По режиму |
| Активен | **На доработке** | Отклонение | Возврат на этот же этап |
| Активен | **Отклонён** | Пропуск этапа при возврате инициатора на более ранний целевой этап (§11.3) | Инициатором выбран целевой этап раньше данного |
| Активен | Автосогласован | Истечение срока | — |
| Активен | Отменён | Отзыв процесса | — |
| На доработке | Активен | Возобновление | Новая итерация этапа |

### 20.6 Переходы этапа UNIFIED

| Откуда | Куда | Триггер |
|---|---|---|
| Ожидает | Активен | Активация |
| Активен | Завершён | Все приняли решение / истёк срок |
| Активен | Отменён | Отзыв процесса |

### 20.7 Валидация карты переходов

Перед публикацией проверяется:
- Ровно одно начальное состояние.
- Все переходы ссылаются на существующие состояния.
- Все условия и действия зарегистрированы.
- Из каждого нефинального состояния есть исходящий переход.
- Нет удаления используемых состояний, пока есть активные процессы.

## 21. Бизнес-правила

### 21.1 Шаблоны

- Опубликованный шаблон не редактируется.
- Удаление версии — только при отсутствии активных процессов.
- Обязательность порядка — среди всех этапов.
- Обязательный этап должен иметь хотя бы один обязательный слот.
- Обязательный по порядку этап №N требует обязательности всех этапов до N.
- Срок этапа должен быть больше нуля.
- Сроки задаются только в днях (рабочих).
- Замена организации требует разрешения на замену пользователя.
- Для единого процесса режим агрегации и порядок работы не применяются.
- `processIterationEnabled` управляет ревизиями документа (§7.8, §11.7), а не лимитом итераций — лимита не существует (см. §11.4).

### 21.2 Слоты

- Конкретный пользователь имеет приоритет над ролями.
- Организация — область поиска пользователя.
- Модуль не проверяет соответствие пользователя ролям.
- Модуль не проверяет актуальность ролей и организаций.
- Уникальность участника в рамках (этап, итерация).
- Один человек — одна роль в рамках (этап, итерация).

### 21.3 Дополнительные согласующие

- Не влияют на статус этапа — рекомендация чисто информационная.
- Срок не позднее срока основного согласующего.
- **Могут назначать других доп. согласующих** — иерархия без ограничения глубины (изменено).
- **Видят и других доп. согласующих, и основных согласующих** — видимость сквозная по всему процессу, не изолирована и не ограничена итерацией (изменено).
- Удаление — только в статусах Отозван и На доработке.
- **Ограничения по количеству нет** (изменено — раньше было 10 человек на одного основного).
- Основной всегда может добавить доп. согласующего себе.
- Клонируются при новых итерациях этапа по правилам §9.5 (зависит от того, кто назначил).

### 21.4 Замечания

- Основной создаёт сразу Действующее.
- Доп. создаёт Предложено.
- После согласования основного активация запрещена.
- Необработанные → Авто-обработано.
- Возобновление — только если все замечания обработаны.
- При Согласовать с замечаниями — замечания считаются несущественными.
- Замечание может содержать файл.

### 21.5 Отзыв

- Стандартный: инициатор до завершения.
- Единый: инициатор до финального решения.
- Из Отозван → Черновик или Архив.

### 21.6 Возобновление

- Только для стандартного процесса.
- Целевой этап — по выбору инициатора из `allowedReturnStages` отклонённого этапа (§11.3), а не «всегда с этапа отзыва/отклонения» и не «всегда с 1-го этапа».
- Этапы до целевого (не включая) остаются согласованными, их решения не обнуляются.
- Этапы между целевым и отклонённым получают статус Отклонён.

### 21.7 Финальное решение

- Принимает ответственный.
- Без срока.
- Неизменяемо.
- Доп. согласующие не назначаются.

### 21.8 Возврат на доработку

- Работает всегда, без переключателя и без лимита.
- Целевой этап задаётся списком `allowedReturnStages` в шаблоне (для каждого этапа — свой список из уже пройденных и текущего).
- Клонирует участников и доп. согласующих (по правилам §9.5) для целевого этапа при его новой итерации.
- Не клонирует решения и замечания.
- Запускается только явным действием инициатора («Возобновить»), никогда автоматически.
- Лимита и уведомления о его достижении не существует (см. §11.4).

### 21.9 Продление лимита

**Убрано целиком** — лимита итераций, который можно было бы продлевать, больше не существует (см. §11.4, §16).

### 21.10 Напоминания

- Инициатору о долгом нахождении в статусе На доработке.
- Автоматические переходы отсутствуют.
- Периодичность настраивается администратором через `GET`/`PUT /admin/notification-settings` (`07_api_contract.md` §26, ADR-027) — без релиза.

### 21.11 Архивация

- Только автоматическая.
- Через 180 дней после завершения.
- Бессрочное хранение.
- Удаление не предусмотрено.
- Восстановление — только администратором.
- Уведомления не отправляются.
- Настройки — только глобальные.

## 23. Доменные события

Модуль публикует события, на которые подписываются внешние системы.

### 23.1 Процесс

- `approval.process.created` — процесс создан
- `approval.process.started` — процесс запущен
- `approval.process.recalled` — процесс отозван
- `approval.process.resumed` — процесс возобновлён
- `approval.process.completed` — процесс завершён
- `approval.process.revision-created` — создана новая ревизия документа (§11.7) — **добавлено**
- `approval.process.rework-required` — процесс требует доработки
- `approval.process.auto-archived` — процесс архивирован автоматически
- `approval.process.restored` — процесс восстановлен администратором

**Убрано:** `approval.process.iteration-started`, `approval.process.iteration-max-reached` — были привязаны к убранному лимиту итераций процесса (§11.4).

### 23.2 Этап

- `approval.stage.activated` — этап активирован
- `approval.stage.completed` — этап завершён
- `approval.stage.rejected` — этап отклонён
- `approval.stage.auto-approved` — этап автосогласован

### 23.3 Задачи

- `approval.task.assigned` — задача назначена
- `approval.task.revoked` — задача отозвана
- `approval.task.expired` — задача просрочена

**Убрано:** `approval.task.reassigned` — использовалось только функциональностью замещений, убранной целиком (ADR-024).

### 23.4 Решения

- `approval.decision.recorded` — решение основного согласующего/подписанта зафиксировано
- `approval.additional-approver.recommended` — рекомендация доп. согласующего зафиксирована — **добавлено**. Отдельное событие с собственным payload; не путать с `approval.decision.recorded` — рекомендация доп. согласующего не унифицирована с решением основного согласующего (см. архитектурный ADR-016).

### 23.5 Замечания и комментарии

- `approval.remark.created` — замечание создано
- `approval.remark.activated` — замечание активировано
- `approval.remark.marked-not-required` — замечание помечено «не требуется»
- `approval.remark.auto-processed` — замечание авто-обработано
- `approval.remark.resolved` — замечание исправлено
- `approval.remark.rejected` — замечание отклонено
- `approval.remark.closed` — замечание закрыто
- `approval.comment.created` — комментарий создан

### 23.6 Единый процесс

- `approval.unified.route.submitted` — маршрут отправлен на согласование ответственному
- `approval.unified.route.approved` — маршрут согласован
- `approval.unified.route.rejected` — маршрут отклонён
- `approval.unified.awaiting-final-decision` — ожидает финального решения
- `approval.unified.final-decision.recorded` — финальное решение зафиксировано

### 23.7 Сущность

- `approval.entity.status.changed` — рекомендация для системы-владельца изменить статус сущности

## 24. Внешние интеграции и адаптеры

### 24.1 Внешние системы

| Система | Направление | Что передаётся |
|---|---|---|
| Система сущностей | Вход | Снимок сущности |
| Справочник сотрудников | Вход | Данные о сотрудниках |
| Справочник ролей | Вход | Данные о ролях |
| Проверка полномочий (КРИП) | Вход | Правила доступа |
| Модуль задач | Выход | События о назначении задач |
| Модуль уведомлений | Выход | События об уведомлениях |
| Система аудита | Выход | События аудита |
| Аналитика | Выход | События аналитики |

**Убрано:** «Система замещений» — функциональность замещений убрана из модуля целиком (ADR-024), интеграции с этой системой не будет.

### 24.2 Адаптеры

**Адаптер** — программный интерфейс, через который модуль общается с внешней системой.

| Адаптер | Статус на старте | Назначение |
|---|---|---|
| Адаптер подбора пользователей по ролям | Пустой | Преобразование ролей в конкретных пользователей |
| Адаптер сущностей | Реальный | Получение снимка сущности |
| Адаптер проверки полномочий | Пустой | Проверка полномочий |

**Убрано:** «Адаптер замещений» — функциональность замещений убрана из модуля целиком (ADR-024).

### 24.3 Адаптер подбора пользователей по ролям

**Что делает:**
- преобразует роль в конкретного пользователя;
- проверяет, подходит ли пользователь под роль;
- учитывает организацию при подборе.

**Правила:**
- Возвращает одного пользователя (приоритетного).
- При недоступности возвращает пустой результат.
- Кэширование отключено по умолчанию.
- Не поддерживает плагины.

**Пустая реализация (на старте):**
- Все методы возвращают пустой результат.
- Модуль работает без адаптера.
- Подбор пользователей — на интерфейсе.

**Поведение модуля без адаптера:**
- Маршрут генерируется с пустыми участниками там, где заданы только роли.
- Интерфейс заполняет участников вручную.
- Валидация по ролям не блокирует.

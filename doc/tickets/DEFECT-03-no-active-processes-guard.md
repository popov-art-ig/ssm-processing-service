# DEFECT-03 — Архивация шаблона: неверный список финальных статусов процессов

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-03-no-active-processes`.
> Связанные тикеты: DEFECT-07 (отзыв процесса), DEFECT-14 (жизненный цикл шаблона).

## Статус

`Не начато`

## Контекст

Шаблон можно перевести в `ARCHIVED` только если по нему не осталось незавершённых процессов —
это единственная защита от «архивировали шаблон, а по нему идут согласования». Guard проверяет
завершённость по локальному списку строк, и список неверен: в нём нет статуса `Recalled`,
который сама схема объявляет терминальным, зато есть `Canceled`, которого нет ни в одной
миграции. Пока карта не содержит перехода процесса в `Recalled` (PHASE-09), дефект скрыт; после
реализации отзыва любой отозванный процесс навсегда заблокирует архивацию своего шаблона.

## Дефект

```java
private static final List<String> TERMINAL_STATUSES = List.of(
        "Approved", "Rejected", "Canceled", "ApprovedWithComments");
```

Проблемы:

1. **`Recalled` отсутствует.** V23 объявляет этот статус процесса терминальным
   (`is_terminal = true`). Отозванный процесс навсегда останется «незавершённым» для guard'а →
   архивация шаблона вернёт отказ, который невозможно устранить (процесс уже отозван).
2. **`Canceled` не существует.** Такого кода нет ни в `status_registry`, ни в карте переходов:
   отмена задач процесса выражается статусами `Recalled` (процесс) и `Rejected`/`Canceled`
   у этапа — то есть строка мертва и создаёт ложное ощущение покрытия.
3. Список дублирует данные реестра: источник истины по терминальности — `status_registry.is_terminal`,
   а не константа в коде.

## Явно не входит (Out of scope)

- Реализация перехода процесса в `Recalled` и PHASE-09 целиком — тикет только про guard.
- Автоархивация процессов по времени (`A-P-007 ScheduleAutoArchive`, PHASE-18).
- Восстановление процесса из архива (`A-P-009 RestoreProcess`).

## Технические требования

1. Определять завершённость процесса по реестру статусов, а не по локальному списку: выбрать
   статусы `entity_type = 'PROCESS'` с `is_terminal = true` (запрос к `status_registry` через
   существующий репозиторий) и считать процесс завершённым, если его `status` входит в этот
   набор. Список терминальных статусов допустимо кэшировать на уровне бина, но не хардкодить.
2. Убрать `Canceled`; если такой статус нужен бизнесу — завести его миграцией со ссылкой на
   требование, а не оставлять в константе.
3. Сохранить текущий контракт guard'а: `true` — архивировать можно, `false` — есть активный
   процесс (или сущность перехода не `Template`). Побочных эффектов нет.
4. Никаких изменений в уже применённых миграциях: если понадобится правка данных
   `status_registry`, делать новой миграцией (см. DEFECT-16).

## Критерии приёмки

1. Юнит/интеграционный тест: процесс в статусе `Recalled` **не блокирует** архивацию шаблона.
2. Тест: процесс в статусе `InProgress`/`OnRework`/`Draft` **блокирует** архивацию.
3. Тест: шаблон без процессов архивируется.
4. В коде класса отсутствует список строк-статусов; источник — `status_registry`.
5. `./gradlew build` зелёный; `DebugTemplateLifecycleIntegrationTest`/`TemplateLifecycleIntegrationTest`
   (существующие тесты жизненного цикла шаблона) не сломаны.

## Тестирование

- Юнит: `NoActiveProcessesGuardTest` — параметризованный набор статусов процесса, включая
  `Recalled` и `Canceled`.
- Интеграционные: `TemplateLifecycleIntegrationTest` — сценарий «процесс отозван → архивация
  проходит»; сценарий «процесс активен → архивация отклонена с осмысленным ответом».

## Открытые вопросы

1. Должен ли отозванный процесс считаться завершённым для целей архивации **шаблона**, если
   процесс можно возобновить после отзыва (PHASE-09 предполагает такой сценарий)? Если да —
   нужен признак «окончательно закрыт» помимо статуса.
2. Нужен ли административный обход guard'а (принудительная архивация)? Сейчас обхода нет.

# DEFECT-09 — Боевые заглушки адаптеров сущностей и ролей

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-09-adapters`.
> Связанные тикеты: DEFECT-06 (маппинг ошибок), DEFECT-11 (валидация маршрута), PHASE-20.

## Статус

`Не начато`

## Контекст

Оба порта внешних интеграций подключены заглушками, и заглушки — **единственные** реализации:
`@Component` без профиля и без `@ConditionalOnProperty`. То есть в любом окружении, включая
условно-продуктивное, сервис поднимается с фиктивными данными: шаблон подбирается по
придуманным атрибутам сущности, а резолвинг ролей всегда возвращает «никого» — из-за чего
шаблон с обязательным «ролевым» слотом вообще невозможно использовать для создания процесса.

## Источники (для истории, не для перехода)

- `09_adapters.md` §4–6 — контракты `EntityAdapter`, `RoleResolverAdapter`, статус реализаций.
- `11_adr.md` ADR-004, ADR-010 (`RoleResolverAdapter` возвращает одного пользователя), ADR-008

- `10_architecture.md` §8 — Adapters Layer, «единственный адаптер без пустой реализации».

## Что уже есть в репозитории

- `src/main/java/ru/coordination/approval/adapter/EntityAdapter.java`,
  `EntityAdapterStub.java` — `fetchEntitySnapshot(entityType, entityId)` возвращает фиксированные
  `amount = 1000000`, `priority = "HIGH"`, `entitySubtype = null`.
- `src/main/java/ru/coordination/approval/adapter/RoleResolverAdapter.java`,
  `RoleResolverAdapterStub.java` — `resolveRole(...)` всегда возвращает `List.of()`.
- `src/main/java/ru/coordination/approval/service/RouteGenerationService.java` — перегрузка
  `generateRoute(request)` берёт снимок из адаптера, перегрузка
  `generateRoute(request, snapshot)` принимает снимок извне (её использует
  `ProcessService.createProcess`, чтобы обойти заглушку).
- `src/main/java/ru/coordination/approval/service/RouteValidatorService.java` — бросает
  `RequiredSlotNotResolvedException`, если обязательный слот не разрешён.

## Дефекты в объёме тикета

### 1. `EntityAdapterStub` — фиктивные атрибуты в любом окружении

Снимок сущности собирается из констант, поэтому:
- подбор шаблона по правилам применимости (`ApplicabilityRule.attributeConditions`) работает по
  фиктивным данным, а не по данным документа;
- любой шаблон, требующий конкретного `amount`/`priority`, выбирается неверно.

Обходной путь уже применён в `ProcessService.createProcess` (атрибуты берутся из тела запроса),
но публичный путь `generateRoute(request)` остаётся доступным и опасным.

### 2. `RoleResolverAdapterStub` — всегда пустой список

Следствия по коду:
- слот с `acceptableRoles` не получает участников;
- при обязательном слоте `RouteValidatorService` бросает `RequiredSlotNotResolvedException` →
  создание процесса по такому шаблону невозможно (и клиент получит 500, см. DEFECT-06);
- слот с явным `userId` от адаптера не зависит и работает.

Тесты мокают адаптер, поэтому путь с реальным пустым ответом не покрыт.

### 3. Отклонения от контрактов спецификации

| Порт | Спецификация | Код |
|---|---|---|
| `EntityAdapter` | `getSnapshot(EntityRef)`, `exists(EntityRef)` (§6.3) | `fetchEntitySnapshot(String, UUID)`, нет способа выразить «сущность не найдена» |
| `RoleResolverAdapter` | один приоритетный `UUID` или `null`; методы `resolveRole`, `resolveRoles`, `matches` (ADR-010, §5.3) | `List<UUID> resolveRole(...)`, методов `resolveRoles`/`matches` нет |
| `KripAdapter` (§7, §10_architecture §8.2) | заявлен | отсутствует в коде полностью |

## Явно не входит (Out of scope)

- Реализация реальных интеграций (HTTP-клиенты, справочник ролей) — это PHASE-20; здесь
  устраняется опасность «заглушка в проде» и приводятся в порядок контракты.
- Изменение правил применимости шаблонов.

## Технические требования

1. Сделать заглушки **условными**: `@ConditionalOnProperty` (например
   `approval.adapters.stub=true`, значение по умолчанию — `false`) либо `@Profile`. Настройку
   внести в `application.yml` с явным значением для профиля `test`.
2. **Важно:** сейчас `EntityAdapter` и `RoleResolverAdapter` — `@Component`-бины без
   квалификаторов. Если добавить вторую реализацию (например «реальную») при активной
   заглушке, получится `NoUniqueBeanDefinitionException` и приложение не поднимется. Поэтому
   вместе с условиями нужно пометить основной бин `@Primary` (или разнести по профилям так,
   чтобы активной была ровно одна реализация) и проверить старт в обоих режимах.
3. Привести сигнатуры к спецификации — либо в этом тикете, либо зафиксировать отступление
   аддендумом и вынести переделку контракта в PHASE-20. Минимально: `resolveRole` должен
   возвращать одного пользователя (`UUID`) либо явно документировать расширение контракта.
4. Опасный путь `generateRoute(request)` (со снимком из заглушки) сделать недостижимым при
   выключенных заглушках: либо через условие на бин, либо через явную проверку конфигурации на
   старте с падением, если адаптер — заглушка, а профиль не тестовый.
5. Добавить стартовую валидацию конфигурации адаптеров по образцу
   `TransitionMapStartupValidator`: если активна заглушка и профиль не `test`/`local` — не
   поднимать приложение (fail-fast) или писать `WARN` уровня ERROR, по решению Cowork.

## Критерии приёмки

1. При `approval.adapters.stub=false` (или профиле без заглушек) приложение поднимается и не
   содержит бин-заглушку; тестовая конфигурация по-прежнему использует заглушку.
2. Тест `@SpringBootTest` на конфигурацию с двумя реализациями порта проверяет отсутствие
   `NoUniqueBeanDefinitionException` (проверка `@Primary`/профилей).
3. Тест: при активной заглушке и не тестовом профиле старт приложения завершается ошибкой
   (или логируется предупреждение — по п. 5) с явным текстом про фиктивные атрибуты ролей.
4. В Javadoc каждого адаптера и его заглушки однозначно указано: это заглушка, что подменяет,
   что произойдёт в проде (сделано в PR #17 — сохранить формулировки при правке).
5. `./gradlew build` зелёный, `RouteGenerationServiceTest` проходит без моков заглушки (через
   активный тестовый бин).

## Открытые вопросы

1. **Что делать со слотом, который не разрешился по ролям:** отказ в создании процесса
   (сейчас так) или создание с пустым участником для заполнения через UI? ADR-008 говорит, что
   модуль не должен блокировать работу по ролям, — это аргумент за второй вариант.
2. **Расширять ли контракт `RoleResolverAdapter` до `List<UUID>`** официально (аддендум к
   ADR-010) или возвращать одного пользователя, как в спецификации?
3. Нужен ли `KripAdapter` в этом репозитории вообще (он заявлен в `09_adapters.md` §7), или это
   часть внешней системы и здесь только потребитель?

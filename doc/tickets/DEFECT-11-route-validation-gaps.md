# DEFECT-11 — Генерация маршрута: обязательные слоты, операторы условий и число участников

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-11-route-validation`.
> Связанные тикеты: DEFECT-06 (маппинг ошибок), DEFECT-09 (адаптеры ролей), PHASE-15.

## Статус

`Не начато`

## Контекст

PHASE-15 задаёт три проверяемых правила при создании процесса: все обязательные слоты шаблона
заполнены, сроки этапов монотонны, а условия применимости шаблона поддерживают операторы
сравнения. Ни одно из них не реализовано полностью: валидатор проверяет «есть ли участники
вообще», сопоставление атрибутов умеет только равенство, а число участников на слот зависит от
того, сколько кандидатов вернул адаптер ролей. Из-за этого процесс может быть создан по
шаблону, который не подходит документу, или без обязательного согласующего.

## Дефекты в объёме тикета

### 1. Обязательный слот проверяется «по этапу», а не по слоту

`RouteValidatorService` проверяет, что у обязательного этапа есть участник, но не сверяет
каждый слот с `SlotTemplate.required`. В шаблоне с двумя обязательными слотами достаточно
заполнить один — проверка пройдёт.

### 2. Слот с несколькими допустимыми ролями использует только первую

```java
UUID roleId = slot.getAcceptableRoles().get(0);
```

Остальные роли игнорируются: если пользователь есть только по второй роли, слот останется
пустым (и, при обязательности, процесс не создастся). См. также DEFECT-19.

### 3. Число участников на слот не ограничено

`resolveParticipants` создаёт участника на каждого кандидата, возвращённого адаптером ролей,
хотя ADR-010 и открытый вопрос 1 PHASE-15 требуют одного приоритетного пользователя.

### 4. Операторы условий применимости не реализованы

`MatchService.attributeMatches` умеет только сравнение на равенство. Критерий 7 PHASE-15 требует
поддержки `gt`, `lt`, `contains`; неизвестный оператор сейчас молча даёт «не совпало» вместо
явной ошибки конфигурации.

### 5. Сроки этапов не проверяются на монотонность

Критерий 5 PHASE-15 требует проверять, что сроки этапов не убывают (с учётом `dueOffset`).
Такой проверки нет ни в `RouteValidatorService`, ни в `ValidateTemplateStructureAction`.

### 6. Процесс без этапов и другие граничные случаи

- `RouteValidatorService` бросает `IllegalArgumentException` вместо доменного исключения при
  отсутствии этапов (ожидался `IllegalStateException` по критерию 5 PHASE-15) — то есть ошибка
  классифицируется как клиентская (400), хотя это дефект шаблона.
- `RouteGenerationService.selectTemplate` не проверяет статус **явно указанного** шаблона:
  процесс можно создать по `DRAFT`/`DEPRECATED`/`ARCHIVED` версии, тогда как решение открытого
  вопроса 5 PHASE-15 требует только `PUBLISHED`.

## Явно не входит (Out of scope)

- Поддержка `ADDITIONAL_APPROVER`-слотов (PHASE-10).
- `UNIFIED`-процессы (PHASE-12/13).
- Реализация реального `RoleResolverAdapter` (PHASE-20, см. DEFECT-09).

## Технические требования

1. Валидировать **каждый** слот этапа: если `SlotTemplate.required == true`, в соответствующем
   слоте маршрута должен быть участник. Проверку вести по слотам слота-источника
   (`StageTemplate` → `SlotTemplate`), а не «есть ли участник у этапа».
2. Для слота с `acceptableRoles` перебирать роли по порядку и брать первого найденного
   пользователя; если ни одна роль не дала результата — слот пуст (и это ошибка при
   `required`).
3. Создавать ровно одного участника на слот (ADR-010). Если бизнесу нужны все кандидаты —
   зафиксировать отступление аддендумом и описать правило в спецификации слотов.
4. Реализовать операторы условий: `eq` (по умолчанию), `gt`, `lt`, `contains`; для неизвестного
   оператора — исключение конфигурации с указанием шаблона и правила (а не «не совпало»).
5. Проверять монотонность сроков: `dueAt` этапа N+1 ≥ `dueAt` этапа N с учётом `duration` и
   `dueOffset`; при нарушении — доменная ошибка шаблона.
6. Заменить `IllegalArgumentException` в валидаторе на доменное исключение шаблона (см.
   DEFECT-06) и проверять статус явно указанного шаблона (`PUBLISHED`), если тикет PHASE-15
   подтверждает это требование.

## Критерии приёмки

1. Тест: шаблон с двумя обязательными слотами, заполнен один → создание процесса отклонено с
   указанием незаполненного слота.
2. Тест: слот с `acceptableRoles = [roleA, roleB]`, где пользователь есть только по `roleB` →
   слот разрешён, участник создан.
3. Тест: адаптер вернул трёх кандидатов по роли → в слоте ровно один участник.
4. Тест: правило применимости `amount gt 500000` отбирает шаблон при `amount = 1000000` и не
   отбирает при `amount = 100`; неизвестный оператор приводит к явной ошибке с указанием
   правила.
5. Тест: шаблон с убывающими сроками этапов отклоняется при создании процесса.
6. Тест: явно указанный `templateId` в статусе `DRAFT` отклоняется (или фиксируется иное
   решение Cowork).
7. `./gradlew build` зелёный; `RouteValidatorServiceTest`, `MatchServiceTest`,
   `RouteGenerationServiceTest` обновлены осознанно.

## Тестирование

- Юнит: `RouteValidatorServiceTest` (кейсы слотов), `MatchServiceTest` (операторы),
  `RouteGenerationServiceTest` (число участников, статус шаблона).
- Интеграционные: `ProcessServiceIntegrationTest` — создание процесса по шаблонам с разными
  наборами слотов.
- Регрессия: `ProcessApiIntegrationTest` — ответы `4xx` вместо `500` на невалидных шаблонах.

## Открытые вопросы

1. **Один или все кандидаты роли** (ADR-010 vs текущий код)? Тикет исходит из ADR-010.
2. **Создавать ли процесс по `DRAFT`-шаблону** для тестовых/предпросмотровых сценариев?
3. Нужна ли проверка монотонности сроков на уровне шаблона (при публикации), а не только при
   создании процесса? Логичнее валидировать на публикации (`ValidateTemplateStructureAction`).

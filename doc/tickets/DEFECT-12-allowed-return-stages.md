# DEFECT-12 — Возврат на этап, запрещённый шаблоном

> **2026-10-28:** механизм `allowedReturnStages` заменяется политикой возврата (ADR-029,
> `doc/arch/11_adr.md` §31); реализация — [PHASE-30](PHASE-30-return-policy.md). Описание ниже
> остаётся как история дефекта и источник требований к проверке цели.

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-12-return-stages`.
> Связанные тикеты: DEFECT-07 (итерации и возврат), DEFECT-11 (валидация шаблона), PHASE-15.

## Статус

`Не начато`

## Контекст

Шаблон этапа хранит список этапов, на которые разрешено вернуть процесс при доработке
(`allowedReturnStages`). Это ограничение бизнес-логики: например, с этапа «Подписание» можно
вернуться только на «Проверку», но не в самое начало маршрута. Сейчас guard возврата этот
список не читает: разрешён любой этап не позже ушедшего на доработку, то есть запрещённый
шаблоном возврат проходит. Дополнительно: у `StageInstance` нет ссылки на `StageTemplate`,
поэтому для проверки «по данным шаблона» не хватает связи — её нужно либо добавить, либо
копировать список в этап маршрута при генерации (снимок на старте, ADR-003).

## Дефекты в объёме тикета

### 1. Список запрещённых целей не читается

```java
return targetStageOrderIdx >= 0 && targetStageOrderIdx <= onReworkStage.getOrderIdx();
```

Требуется `targetStageOrderIdx ∈ allowedReturnStages` этапа (для самого этапа на доработке —
по «текущему этапу» из §11.3). Проверить, заполняется ли `StageInstance.allowedReturnStages`
при генерации маршрута; если поле в этапе есть, но не заполняется — это часть дефекта.

### 2. Нет признака «есть несколько целей возврата»

`G-RT-002 HasMultipleReturnTargets` нужен клиенту, чтобы показать модалку выбора этапа. Сейчас
такого условия нет ни в guard'ах, ни в API-ответе, поэтому UI не знает, нужно ли спрашивать
пользователя, и вынужден угадывать.

### 3. Неизвестный `targetStageId` даёт 404 «этап не найден в процессе»

`ProcessController.resumeProcess` ищет этап по `id` в рамках процесса и бросает
`EntityNotFoundException`. Если этап существует, но **не разрешён** шаблоном, ответ будет `200`
с прежним статусом процесса (переход не выполнен) — клиент не понимает, что цель запрещена. По
контракту это бизнес-отказ (`422 BUSINESS_ERROR`, см. DEFECT-06), а не «успех».

## Явно не входит (Out of scope)

- Изменение набора переходов возврата в карте.
- Клонирование участников при возврате (см. DEFECT-07).
- Ревизии документа (PHASE-26).

## Технические требования

1. Проверять цель возврата по данным шаблона: `targetStageOrderIdx` должен входить в
   `allowedReturnStages` этапа, с которого процесс ушёл на доработку (или текущего этапа в
   статусе `OnRework`). Семантику «пустой/`null` список» зафиксировать: по `03_domain_model.md`
   §6.4 это «только текущий этап».
2. Обеспечить наличие данных для проверки: заполнять `StageInstance.allowedReturnStages` при
   генерации маршрута (снимок на старте — ADR-003) либо читать из `StageTemplate` через
   сохранённую связь. Выбрать вариант и обосновать в PR: снимок в этапе устойчивее к правке
   шаблона, связь — компактнее.
3. Реализовать условие «несколько целей возврата» и отдавать признак клиенту: добавить поле в
   ответ процесса/этапа (например `multipleReturnTargets: boolean`) либо отдельный эндпоинт по
   образцу `07_api_contract.md` §12.9. Название и место — согласовать с контрактом.
4. Заменить «тихий» успех на явный отказ: если цель не разрешена, сервис возвращает
   `performed == false`, контроллер — `422 BUSINESS_ERROR` с текстом «этап X не разрешён как
   цель возврата» (см. DEFECT-06).
5. Не расширять проверку до «любой этап раньше текущего»: список из шаблона — единственный
   источник допустимых целей.

## Критерии приёмки

1. Тест: шаблон с `allowedReturnStages = [0]` для этапа 2; попытка вернуться на этап 1
   отклоняется (`422`), процесс остаётся `OnRework`.
2. Тест: возврат на разрешённый этап проходит, целевой этап активируется новой итерацией.
3. Тест: при `allowedReturnStages = []` (или `null`) разрешён только возврат на текущий этап.
4. Тест: для этапа с двумя разрешёнными целями признак «несколько целей» в ответе `true`; для
   одной цели — `false`.
5. `./gradlew build` зелёный; `RouteValidatorServiceTest`, `ProcessResumeIntegrationTest`,
   `IsTargetStageAllowedGuardTest` обновлены осознанно.

## Открытые вопросы

1. **Какой этап считать источником `allowedReturnStages`:** тот, что ушёл на доработку, или
   текущий этап в статусе `OnRework` (они совпадают, но не всегда — см. `ReactivateStage`)?
2. **Где хранить снимок списка:** в `StageInstance` (снимок на старте) или читать шаблон на
   момент возврата (тогда правка шаблона меняет поведение идущего процесса)?
3. Нужен ли API-эндпоинт «список допустимых целей возврата» отдельно от карточки процесса?

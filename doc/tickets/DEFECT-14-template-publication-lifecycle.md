# DEFECT-14 — Публикация шаблона: Fork & Drain, депрекация без проверок, правка архивированного

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-14-template-lifecycle`.
> Связанные тикеты: DEFECT-03 (архивация шаблона), DEFECT-10 (версия карты), PHASE-14.

## Статус

`Не начато`

## Контекст

Жизненный цикл шаблона описан ADR-023: опубликованная версия неизменяема, правка создаёт новую
версию, а прежняя снимается с публикации (Fork & Drain). В коде снятие с публикации привязано к
методу `update`, но не к публикации новой версии: `fork` → `publish` оставляет обе версии
`PUBLISHED`, и автоподбор (`MatchService`) видит две конкурирующие версии. Дополнительно
депрекация не проверяет, что по шаблону не идут процессы, а правка архивированного шаблона
создаёт новую версию, не снимая исходную с архивации.

## Дефекты в объёме тикета

### 1. Fork & Drain при публикации не работает

`createNewVersion` вызывает `deprecate(oldTemplate.getId(), ...)`, но это происходит только при
`update` **опубликованного** шаблона. Публикация ранее созданного форка (`fork` → `publish`) не
снимает прежнюю версию: в `PUBLISHED` остаются две версии одной цепочки. `MatchService`
дедуплицирует кандидатов по корню цепочки, поэтому выбор версии становится неочевидным для
пользователя и зависит от реализации сортировки.

Javadoc `fork` обещает снятие прежней версии — обещание не выполняется (зафиксировано как
«известный пробел»).

### 2. `deprecate` не проверяет активные процессы

`07_api_contract.md` §10.7 и PHASE-14 требуют, чтобы версию нельзя было снять с публикации, пока
по ней идут процессы. Сейчас guard `NoActiveProcesses` навешен только на `ArchiveTemplate`;
`DeprecateTemplate` его не содержит, поэтому возможно снять с публикации версию работающего
процесса (процесс продолжит исполняться по снимку — здесь снимок спасает, но новые процессы по
этой версии создаваться перестанут, а поведение админ-операции станет необратимым без явного
предупреждения).

### 3. Правка архивированного шаблона

`TemplateService.update` для статуса, отличного от `DRAFT`, создаёт **новую версию** с
`parentTemplateId` исходного. Для `ARCHIVED`-шаблона это означает: исходная версия остаётся
`ARCHIVED`, появляется новая `DRAFT`-версия «из архива». Ни §10.4, ни ADR-023 не описывают
такой сценарий; в Javadoc это зафиксировано как открытый вопрос. Требуется решение: запрещать
правку архивированного, разрешать только «клонирование с новым именем» или считать поведение
штатным и описать его.

### 4. `CreateTemplate` в карте отсутствует

Создание шаблона идёт в обход движка: `TemplateService.create` ставит `DRAFT` напрямую, поэтому
guards и действия перехода `CreateTemplate` (если он нужен) не выполняются, а README перечисляет
этот переход как существующий. Нужно либо завести переход, либо поправить документацию и
Javadoc (см. DEFECT-20).

## Явно не входит (Out of scope)

- Реализация отзыва шаблона из архива.
- UI-редактор карт (`metadata` в состояниях).
- Миграция существующих данных при изменении правил версионирования.

## Технические требования

1. Реализовать Fork & Drain **при публикации**: при переходе `PublishTemplate` снимать с
   публикации предыдущую версию цепочки (`parentTemplateId` вверх до корня). Реализовать как
   action карты (новый `DeprecatePreviousVersion`/`A-T-*`), а не как скрытый вызов из
   `TemplateService`, чтобы поведение было видно в карте переходов и в аудите.
2. Добавить guard `NoActiveProcesses` (или его аналог по цепочке версий) на `DeprecateTemplate`;
   если бизнес допускает депрекацию с активными процессами — вернуть предупреждение в ответе и
   описать это в §10.7.
3. Определиться с правкой `ARCHIVED`: по умолчанию предлагается **запрещать** (доменная ошибка
   `422`), обоснование — архивированная версия не должна возвращаться в оборот под тем же
   именем. Решение зафиксировать в PR и, при необходимости, аддендумом к ADR-023.
4. `update` для `PUBLISHED` должен создавать новую версию и снимать прежнюю с публикации **в
   той же транзакции** (сейчас вызов `deprecate` идёт внутри `createNewVersion` — проверить
   атомарность и отсутствие частичных состояний).
5. Привести README/Javadoc в соответствие: либо переход `CreateTemplate` реализован, либо
   упоминание убрано (см. DEFECT-20).

## Критерии приёмки

1. Тест: `fork` версии 1 → `publish` версии 2 ⇒ версия 1 в статусе `DEPRECATED`, версия 2 в
   `PUBLISHED`; в цепочке ровно одна опубликованная версия.
2. Тест: `deprecate` версии, по которой идёт процесс (`Draft`/`InProgress`/`OnRework`),
   отклоняется; после завершения процессов — проходит.
3. Тест: `update` шаблона в статусе `ARCHIVED` даёт ожидаемое поведение по п. 3 (отказ или
   новую версию — согласно принятому решению), и это поведение описано в Javadoc и §10.
4. Тест: `update` опубликованного шаблона создаёт новую версию и снимает прежнюю **в одной
   транзакции** (при ошибке на любом шаге состояние не меняется).
5. `./gradlew build` зелёный; `TemplateLifecycleIntegrationTest` обновлён осознанно.

## Тестирование

# DEFECT-19 — Приоритет ролей слота и неиспользуемый импорт

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-19-slot-priority`.
> Связанные тикеты: DEFECT-11 (валидация маршрута), DEFECT-09 (адаптеры), DEFECT-17 (мёртвый код).

## Статус

`Не начато`

## Контекст

Разрешение слота участника идёт по приоритету источников: роли (`acceptableRoles`), затем
фиксированный пользователь (`userId`). Когда у слота задано несколько допустимых ролей,
используется только первая — остальные молча игнорируются. Это приводит к незаполненным слотам
(а при обязательном слоте — к невозможности создать процесс), при том что подходящий
пользователь по второй роли существует. Дополнительно в `SchedulingConfig` остался
неиспользуемый импорт: мелочь, но такие вещи ловятся только ревью.

## Дефекты в объёме тикета

### 1. Из `acceptableRoles` берётся только первая роль

```java
UUID roleId = slot.getAcceptableRoles().get(0);
return roleResolverAdapter.resolveRole(roleId, organizationId, snapshot);
```

Если пользователь по первой роли не найден, слот остаётся пустым, хотя вторая роль в списке
могла бы его заполнить. Спецификация слота не устанавливает приоритет ролей — она перечисляет
допустимые, поэтому перебор обязателен.

### 2. Число участников не ограничено одним

`resolveParticipants` создаёт участника на каждого кандидата из ответа адаптера. ADR-010 и
открытый вопрос 1 PHASE-15 требуют одного приоритетного пользователя. Это же описано в
DEFECT-11 (п. 3) — здесь фиксируется связь с приоритетом ролей: даже корректный перебор ролей
без ограничения даст лишних участников.

### 3. Неиспользуемый импорт

`import java.time.Duration` в `SchedulingConfig` не используется (проверено: единственное
вхождение в файле). Удаляется без последствий; пересекается с DEFECT-17 (мёртвый код) — здесь
как минимальная правка, если тикет берётся отдельно.

### 4. Приоритет источников не задокументирован в спецификации

Код реализует порядок «роли → фиксированный пользователь → пусто», Javadoc это фиксирует, но в
`03_domain_model.md` §6.4 порядок не описан. Нужно либо описать его в спецификации (задача
Cowork), либо считать текущее поведение решением реализации и закрепить тестом.

## Явно не входит (Out of scope)

- Реализация настоящего `RoleResolverAdapter` (PHASE-20, DEFECT-09).
- Слоты доп. согласующих (`ADDITIONAL_APPROVER`, PHASE-10).
- Последовательный порядок участников (PHASE-27).

## Технические требования

1. Перебирать `acceptableRoles` по порядку: для каждой роли вызывать адаптер, брать первого
   найденного пользователя; при отсутствии результата по всем ролям — переходить к следующему
   источнику (`userId`), затем оставить слот пустым.
2. Ограничить число участников на слот одним (согласно ADR-010). Если бизнес подтвердит, что
   нужны все кандидаты, — зафиксировать это аддендумом и в спецификации слотов, а не оставлять
   поведение «как получится».
3. Порядок источников вынести в явный, тестируемый метод (например `resolveSlotCandidates`) с
   Javadoc, описывающим приоритет; это упростит покрытие тестами.
4. Удалить `import java.time.Duration` из `SchedulingConfig`.
5. Зафиксировать фактический приоритет в Javadoc `SlotTemplate.acceptableRoles` (кто первый —
   тот и используется) и, при согласии Cowork, в `03_domain_model.md` §6.4.

## Критерии приёмки

1. Тест: слот с `acceptableRoles = [roleA, roleB]`, пользователь есть только по `roleB` → слот
   разрешён, участник создан.
2. Тест: слот с `acceptableRoles = [roleA, roleB]`, есть пользователи по обеим ролям →
   создан **один** участник (по `roleA`, приоритет первой роли).
3. Тест: слот без `acceptableRoles`, но с `userId` → участник — указанный пользователь.
4. Тест: слот без ролей и без `userId` → пустой слот; при `required = true` создание процесса
   отклоняется с внятной ошибкой (см. DEFECT-11).
5. В `SchedulingConfig` нет неиспользуемых импортов (проверяется компиляцией с `-Xlint` или
   ревью).
6. `./gradlew build` зелёный; `RouteGenerationServiceTest` обновлён осознанно.

## Открытые вопросы

1. **Приоритет ролей** — это порядок в `acceptableRoles` (массив) или требуется отдельное поле
  приоритета? Сейчас порядок массива нигде не документирован как значимый.
2. **Один участник или все кандидаты** — финальное решение бизнеса (ADR-010 против текущего
   поведения).
3. Нужно ли логировать факт «слот не разрешён по ролям» на уровне `INFO` для диагностики
   шаблонов?

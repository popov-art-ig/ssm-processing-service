# DEFECT-20 — Консистентность README и Javadoc с фактическим кодом

> Найден при документировании кода (PR #17). Исправление — ветка `fix/defect-20-docs`.
> Связанные тикеты: DEFECT-15 (коды реестров), DEFECT-16 (миграции), DEFECT-18 (планировщик).

## Статус

`Не начато`

## Контекст

Документация репозитория местами описывает то, чего в коде нет, либо ссылается на
несуществующие артефакты. Читатель (и следующий исполнитель) приходит к неверной картине: ищет
методы и переходы, которых нет, или считает работающим то, что является заглушкой. Тикет
приводит README и Javadoc в соответствие с кодом; сами дефекты поведения устраняются в
профильных тикетах.

## Источники (для истории, не для перехода)

- `README.md` — сводка по фазам, список действий/guard'ов, раздел о валидации карт.
- `doc/JAVADOC_COVERAGE.md` — отчёт о покрытии и реестр находок (§4).
- `doc/REST_API_COMPLETION.md` — статус REST API и заглушек.

## Явно не входит (Out of scope)

- Правки `doc/arch/*.md` — это спецификации, их ведёт Cowork (в тикете только перечень
  расхождений, требующих аддендума).
- Реализация недостающих guard'ов/actions — профильные тикеты (DEFECT-01, 02, 07, 14).
- Обновление `doc/tickets/INDEX.md` по фазам — отдельная задача (здесь только консистентность
  фактов).

## Технические требования

1. Убрать из README упоминания несуществующих компонентов либо пометить их как «не реализовано
   (PHASE-NN)»: `IsValidDecisionType`, `HasCommentWhenRequired`, `SetDecidedAt`,
   `RecordAutoDecision`, переход `CreateTemplate`.
2. Исправить ссылку на миграцию в `StatusRegistry` (существующий Javadoc): либо указать
   `V1__registries.sql`, либо убрать номер миграции и оставить описание ключа.
3. Привести комментарии в заглушках адаптеров к фактическому состоянию: они боевые бины, а не
   тестовые; ссылка «PHASE-20» должна указывать на существующий артефакт
   (`doc/tickets/PHASES_09-28_BRIEF.md#phase-20` или отдельный тикет).
4. Проверить, что в README нет других утверждений, противоречащих коду: пройти по разделу
   «Статус» и сверить перечисленные guard'ы/actions/переходы с содержимым
   `src/main/resources/db/migration/V18–V25` и `service/guard|action`.
5. Свести фактические расхождения «спецификация ↔ код» в один список (для Cowork): набор
   статусов замечания (DEFECT-01), финальные статусы процесса (DEFECT-03), операторы условий
   (DEFECT-11), контракт адаптеров (DEFECT-09), коды реестров (DEFECT-15). Это вход для
   аддендумов к ADR.

## Критерии приёмки

1. Поиск по README не находит упоминаний компонентов, отсутствующих в коде (или каждое
   сопровождается пометкой «не реализовано, PHASE-NN»).
2. `StatusRegistry` не ссылается на несуществующую миграцию (проверяется поиском по имени файла
   в `src/main/resources/db/migration`).
3. Комментарии-«маркеры» в адаптерах соответствуют фактическому поведению (боевые заглушки) и
   ссылаются на существующие артефакты.
4. Составлен список расхождений «спецификация ↔ код» и приложен к PR (в описании или в
   `doc/JAVADOC_COVERAGE.md` §4).
5. `./gradlew build` зелёный (правки только в комментариях и markdown).

## Тестирование

- Специальных тестов не требуется: изменения касаются документации. Достаточно
  `./gradlew verifyTestCompilation` (и `build`), чтобы убедиться, что Javadoc-правки не сломали
  компиляцию.
- Полезно добавить в `doc/tools/` проверку ссылок на файлы миграций в Javadoc (аналогично
  существующему `VerifyJavadocLinks.ps1`, но с проверкой существования упомянутых
  `V*.sql`) — по желанию.

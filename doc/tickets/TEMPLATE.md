# PHASE-NN — <название фазы>

> Шаблон постановки. Один тикет = одна фаза плана разработки. Автор постановки — Cowork
> (владеет бизнес- и архитектурным контекстом проекта в Claude Project
> «coordination-processing-module»); исполнение и отладка — Claude Code, в этом репозитории.
>
> **Тикет должен быть полностью самодостаточным.** Claude Code, работающий в этом
> репозитории, **не имеет доступа** к Claude Project «coordination-processing-module» —
> файлы `00_vision_scope.md` … `12_test_scenarios.md`, `11_adr.md` физически не существуют
> в этом git-репозитории и никуда из Project не экспортируются. Поэтому:
> - Нельзя писать «см. `10_architecture.md` §7.2.1» как единственное описание требования —
>   такая ссылка ведёт в документ, которого у исполнителя нет.
> - Весь текст, алгоритм, DDL, таблица guards/actions и т.п., необходимые для реализации
>   фазы, **копируются прямо в тело тикета** (разделы «Контекст», «Технические требования»
>   и т.д. ниже), а не пересказываются кратко со ссылкой на источник.
> - Имя документа и номер раздела в скобках после инлайненного фрагмента (например,
>   «...(источник: `04_state_machines.md` §3.3)») — это **атрибуция происхождения для
>   истории/ревью**, а не рабочая ссылка, которую нужно куда-то переходить. Claude Code
>   ориентируется только на текст, который реально присутствует в тикете.
> - Риск дублирования и расхождения текста между тикетами — принятый компромисс: см.
>   `claude/ticket-process-notes.md` в Project (если создан) или коммит, где принято это
>   решение. Ответственность за то, чтобы инлайненные фрагменты не разошлись с
>   первоисточником при его изменении, — на Cowork при подготовке следующего тикета/ревью.
>
> Процесс (зафиксирован по итогам обсуждения 2026-09-19):
> 1. Cowork готовит тикет `docs/tickets/PHASE-NN-<slug>.md` — самодостаточным, без внешних
>    ссылок как единственного источника — и передаёт его пользователю (файлом в чат) для
>    размещения в репозитории.
> 2. Claude Code реализует и отлаживает фазу в отдельной ветке, открывает PR в `main`.
> 3. После мержа Cowork через `git fetch`/чтение GitHub сверяет запушенный код со спекой
>    в Claude Project и либо подтверждает соответствие, либо фиксирует расхождение и вносит
>    уточнение в спеку по правилам ADR (никогда не переписывая её тихо — только явным
>    addendum/новым ADR).
> 4. Cowork готовит следующий тикет с учётом найденного, заново инлайня актуальный текст
>    затронутых фрагментов спеки.

`Не начато | В работе | На проверке (PR открыт) | Проверено Cowork | Есть расхождения со спекой`

## Контекст

Кратко: что это за фаза, почему она следующая, что от неё зависит и что зависит от неё
(ссылки на предыдущие тикеты в этом же репозитории — на них ссылаться можно, они доступны).

## Источники (для истории, не для перехода)

Список документов Claude Project, из которых скопирован материал этого тикета — только для
атрибуции и для последующей сверки Cowork при ревью. Не предполагается, что исполнитель
будет их открывать.

- `10_architecture.md` §X
- `11_adr.md` ADR-0NN
- ...

## Объём фазы (Scope)

Список того, что **входит** в эту фазу, в терминах компонентов/классов. Весь необходимый
контекст (алгоритмы, контракты, DDL) — инлайнить сюда же или в «Технические требования»,
не оставлять в виде голой ссылки на документ.

## Явно не входит (Out of scope)

Список смежного функционала, который сознательно откладывается на другие фазы — чтобы
Claude Code не расширял объём фазы по собственной инициативе.

## Что уже есть в репозитории на момент постановки

Краткая сверка с текущим состоянием кода (какие сущности/таблицы/классы фаза может
использовать как готовые, без изменений) — со ссылками на реальные пути файлов в этом
репозитории (это ссылки, которые работают).

## Технические требования

Конкретные требования к реализации: пакеты, интерфейсы, сигнатуры, поведение в граничных
случаях, вставленные фрагменты алгоритмов/DDL/таблиц из спецификации — насколько это нужно
для однозначной реализации без обращения к внешним документам.

## Критерии приёмки

Проверяемый список условий, при выполнении которых фаза считается завершённой.
По возможности — в форме, которую можно превратить в тест.
